# Spike 11: harness landscape for an early release

Date: 2026-11-04. Web research only; no code changes. Everything below comes from vendor docs, repos and release pages read on this date, plus secondary sources where noted. Anything I could not confirm from a primary source is marked **unverified**.

## Question

CrossTalk supports Claude Code and Codex CLI. Which other harnesses should the next release add? A harness is viable only if it (a) loads a stdio MCP server so our tools appear, (b) exposes a way for an outside process to deliver a message into a RUNNING interactive session, and (c) lets us identify which session an MCP request came from.

## Terms

- **MCP** (Model Context Protocol): the JSON-RPC protocol a harness uses to load external tool servers. "stdio MCP" means the harness spawns the server as a child process and talks over its stdin/stdout, which is how CrossTalk's tools get into a session and how we can see the harness's process id as our parent.
- **ACP** (Agent Client Protocol): a separate JSON-RPC-over-stdio (sometimes TCP/HTTP) protocol, started by Zed, in which an editor or other *client* launches the agent and drives it: the client creates sessions, sends prompts, receives updates. In every harness checked, ACP is a distinct launch mode (`gemini --acp`, `copilot --acp`, `kiro-cli acp`, `goose acp`, `opencode acp`) that replaces the terminal UI; the user's interactive TUI session is not an ACP session an outsider can join. ACP therefore helps CrossTalk only where the harness's own TUI is itself a client of a long-lived server we can also talk to.
- **App-server / server mode**: a harness process that exposes an HTTP, WebSocket or local-socket API (OpenCode `opencode serve`, Qwen `qwen serve`, Crush `crush serve`, Goose `goose serve`, Cline hub) through which clients, including the harness's own TUI, create sessions and send prompts. This is the strongest delivery path because a message can be injected into an existing session by id while a human is using it.
- **Headless mode**: non-interactive one-shot execution (`-p`, `exec`, `run`) for scripts and CI. Irrelevant for delivery into a running interactive session; listed only because vendors advertise it as "programmatic access" and it is easy to confuse with server mode.
- **Hook mailbox**: a delivery pattern available where a harness runs shell hooks on user-prompt submission (Claude-style `UserPromptSubmit`, Gemini `BeforeAgent`) and lets the hook return `additionalContext`. CrossTalk can write a message to a per-session mailbox file and a hook reads it into the next turn. This is *deferred* delivery: it lands only when the user next submits a prompt, not while the agent is idle or mid-turn. It satisfies requirement (b) weakly.
- **Session identity**: how our MCP server, spawned as a child, learns which session called it. Options seen: an env var set by the harness, a session id passed in the MCP request `_meta`, a session id in hook stdin JSON that a SessionStart hook can record against the harness pid, or parent-pid inference alone.

## Why one "ACP harness package" does not cover several harnesses

- In every harness checked, ACP mode is entered by launching the binary with an ACP flag and the launching client owns the session. A user's interactive TUI session is not reachable over ACP.
- The exceptions are harnesses whose TUI is itself a thin client of a server (OpenCode, Crush serve, Qwen serve, Cline hub, arguably Kiro "uses ACP internally"). Those are reachable through the *server's* API, which is vendor-specific, not through ACP.
- A generic ACP package would only make sense if CrossTalk changed shape to launch and own harness sessions itself. That is a different product; note it as a possible later lane and move on.

## Ranking

Criteria: user overlap with Claude Code and Codex users; viability of live delivery into a running session; MCP support; openness of the source so we can read and pin the injection path.

1. **OpenCode**: high overlap (the most-installed open-source harness), the only one with a documented HTTP API that can inject a prompt into an existing interactive session (`/session/:id/prompt_async`, `/tui/append-prompt` + `/tui/submit-prompt`), MCP with the session id in `_meta`, MIT. Open question is discovering the TUI's random port; a `lsof`/`/proc` lookup of the parent pid's listening socket is the likely answer, with `serve` + `attach` as the documented fallback. Probably also covers Kilo CLI.
2. **Gemini CLI**: highest overlap among vendor-native CLIs and the operator's stated preference, Apache-2.0 TypeScript, stdio MCP, hooks with `GEMINI_SESSION_ID`. Delivery is deferred (BeforeAgent hook mailbox), which should be stated in the harness's docs as "delivered on your next prompt". Qwen Code is a fork with the same hook schema plus `UserPromptSubmit`, so a shared Gemini-family package is realistic and gives Qwen Code nearly free.
3. **Pi**: the best injection API of any harness (`sendUserMessage` with steer/followUp, `sendMessage` with `triggerTurn`), extension can host a Unix socket, session id and file available to the extension, MIT. User base is smaller, but it is the harness the operator asked about and the implementation is the cleanest, so it is a good third.

Recommended early-release set: **OpenCode, Gemini CLI (with Qwen Code sharing the package), Pi.**

Next tier, worth a source read before committing: **Crush** (Go, `crush serve` workspaces, Claude-compatible hooks), **Cline** (hub daemon with message sending), **Copilot CLI** (very high overlap, hook mailbox with `sessionId`, but proprietary and deferred-only), **Kiro CLI** and **Grok Build** (hook mailbox, lower overlap).

Blocked, with reason: **Aider** (no native MCP), **Meta Muse Code** (closed, MCP conflicting, no IPC), **Zhipu ZCode** (proprietary desktop app, nothing documented), **DeepSeek dsh** (no interactive TUI, preview), **Amp**, **Cursor CLI**, **Factory Droid**, **Auggie** (all closed source with no documented path into a running interactive session; ACP modes are separate launches), **Goose** and **Mistral Vibe** (open source and MCP-capable but no documented way to reach the interactive CLI session; re-check when `goose serve` consolidation and `vibe run-server` mature). **Kimi Code CLI** is undetermined pending a read of its hooks.

## Open items to verify before implementation

- OpenCode: confirm `prompt_async` on a session the TUI is displaying renders in the TUI; confirm port discovery via parent pid; confirm `_meta.sessionID` is present on v1.x as well as v2.x.
- Gemini CLI: confirm whether MCP child processes inherit `GEMINI_SESSION_ID` (hooks do); if not, record pid→session from a SessionStart hook.
- Pi: confirm `pi mcp add` exists in 1.5.0 and that an extension can safely open a listening socket in `session_start`.
- Kilo CLI: confirm the OpenCode `/session` and `/tui` routes survive in the fork.
- Copilot CLI: confirm `userPromptSubmit` hook exists and whether it accepts context output.
