## Defects found (fixed the same night unless noted)

1. Claude's session socket writes nothing back after the two-line frame and keeps the connection open, so the adapter's 10 s ack wait ended `unknown` on every delivered message, and the sender's 2 s settle poll returned `unknown/pending`. Probe: `{"type":"auth","token":"wrong"}` was also accepted and rendered, so Claude 2.1.317 performs no token check and offers no wire evidence. Fix: a clean write with the peer still open after a 300 ms grace is `accepted` (slice s7).
2. The injected envelope carried no message id, so the receiving Claude model called `reply(message_id="")` and got `no_such_message`. Fix: `message-id="…"` attribute (slice s7).
3. Claude's native `SendMessage` to a `uds:` path sends ONE line and no auth frame: `{"msgV":1,"msg_id":"…","type":"user","message":{"role":"user","content":"<cross-session-message from=\"uds:/tmp/cc-socks/<pid>.sock\" hop-chain=\"…\" from-name=\"…\" from-mode=\"prompting\">…</cross-session-message>"},"priority":"next","from":"uds:/tmp/cc-socks/<pid>.sock"}`. Our ingress required an auth line and closed it, so native replies were lost while Claude reported success. Fix: accept an unauthenticated first `user` line only from a peer pid that maps to one registered agent (slice s8).
4. `claude --bg -n <name> "<prompt>"` did not consume the positional prompt; the sessions started idle and were briefed over cross-session messages instead. Not a CrossTalk defect.
5. Codex: the first `reply` failed with `user rejected MCP tool call` because the test driver's elicitation handler auto-declined; a corrected driver passed. Not a CrossTalk defect, but shows MCP tool approval prompts gate `reply` in Codex.
