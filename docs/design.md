# CrossTalk design, draft 1.12 (2026-11-04)

Status: draft under operator review (greenfield gate step 4). Decisions are recorded in `docs/decisions/` (ADR 0001–0011, all provisional and edited in place as the design moves; ADR 0005 is superseded by ADR 0006). Evidence for every "verified" claim is indexed in `docs/spikes/README.md` (spikes 1–4, cross-harness round trip; captured frames to be committed before `go mod init`).

Terms: harness = the agent CLI (Claude Code, Codex). Session = one running harness conversation (a Claude Code session or a Codex thread). Agent = the registered identity of a session. session_ref = the Claude session id or the Codex thread id. Shim = the `crosstalk mcp` process described in §2. herdr = the operator's terminal pane manager and session restorer. cc-socks = Claude Code's per-session socket directory (`/tmp/cc-socks/<pid>.sock`), which Claude scans for peers. A2A = Agent-to-Agent protocol. MCP = Model Context Protocol. uds = unix domain socket. pid = process id. F1–F18 = Codex design-review findings, summarized in the Changelog (1.1 and 1.3 entries). V1–V29, C1–C10, CQ1–CQ4 = council verdict items, listed in the 1.4 entry. R2 = the question whether Claude sessions accept a shim-published `~/.claude/sessions` record as a native peer (§3, §12). Spike n = a pre-build experiment indexed in `docs/spikes/README.md`.

## 1. Goal and non-goals

Goal: any agent on this machine can send a message to any other by name and the receiver gets it inside its running session, without a human and without screen scraping, across harnesses. From v0.2.0 the same holds between a user's own paired machines: `name@alias` reaches a session on a paired host with `inform`, `ask` and `reply` only (§9, ADR 0021, ADR 0022).

Non-goals for v1: spawning or wrapping agent processes (ADR 0006; spawning stays with herdr and a separate delegate tool), messaging between machines that are not paired by the same user, relay through a third host, `command`, `claim` and `release` across hosts, kind=control (stop/shutdown), isolation against hostile same-user processes.

## 2. Components

| Component | Count | Owns |
|---|---|---|
| Shim | one per harness MCP connection | the `crosstalk mcp` process the harness starts for its MCP connection; serves one or more agents. Per agent: MCP tools to its model, A2A server+client, cc-socks-compatible uds ingress, injector into its harness, registration, journal (§5) |
| Directory | none as a process | discovery = every harness session from the harness's own registry, merged with the shims' descriptor directory (ADR 0003) |
| Gateway (v0.2.0) | at most one per host, opt-in | the `crosstalk remote serve` listener for messaging between a user's own machines: pinned mTLS, paired peers, forwards to the loopback A2A servers (docs/plans/release-0.2.0.md, ADR 0021, ADR 0022). Built (slices R1 to R11): the host identity and config, `crosstalk remote config` (§9), the listener with pinning and limits, `crosstalk remote serve` (§5 "Gateway ingress"), pairing, `crosstalk remote pair` and `crosstalk remote join` (§5 "Gateway ingress"), and forwarding of `SendMessage` and `GetTask` to a local agent's loopback A2A server (§5 "Gateway forwarding"); slice R4 added the receiving side's remote sender identity (§5 Authentication, §7) |
| herdr | optional | panes and restore only; no v1 code uses it (§10) |

The shim is a Go binary (ADR 0002). Every harness-specific behaviour (bind from request context, discover sessions, inject, status, render the inbound for the model, native reply address, optional native ingress) lives behind the `harness.Harness` interface in its own package (ADR 0008); `internal/shim`, `internal/mcpserver` and `internal/a2a` import no harness package, and adding a harness such as Gemini is one package plus one line in `cmd/crosstalk` within the extension points supported today (see the ADR 0008 narrowing note in §12). CrossTalk spawns and wraps nothing (ADR 0006): `crosstalk mcp` is installed once per harness as an ordinary MCP server entry (§9). `harness.Harness` embeds `adapter.Adapter` (`Register`, `Inject`, `Status`) and adds `Name`, `Identify` (per call, from the request context), `Bind` (at registration), `Discover`, `Render` and `NativeReplyAddress`; a harness that implements the optional `harness.NativeIngress` serves every agent's `uds_path` (today Claude, whose protocol server is `udsingress.NewIngress`), and a harness that can prove a session ended while its MCP connection lives on implements the optional `harness.Supersession` (today Claude; §3). `cmd/crosstalk` lists the harnesses in trust order: Codex (`_meta.threadId`) before Claude (parent pid). `adapter.Fake` (scriptable `status()` and `inject()` outcomes: success, errors, state races, disconnects, blocking) is a v1 deliverable; the receiver chain and the injector failure branches are tested against it in `go test`.

## 3. Registration and discovery

Identity is bound per request, never per process (ADR 0006). For every `tools/call` the shim resolves the calling session:
- Claude: the shim's parent pid is the Claude session pid; `~/.claude/sessions/<ppid>.json` gives `pid`, `name`, `cwd`, `status`, `messagingSocketPath`.
- Codex: `params._meta.threadId`, which Codex attaches to every `tools/call` (required; `session_ref` is the thread id). `params._meta.sessionId` is present on model-issued calls and absent on app-server `mcpServer/tool/call` frames (spike 9); it is optional supplementary metadata and never a fallback identity. Evidence (rust-v0.166.0 `codex-rs/core/src/mcp_tool_call.rs`; spike 9). MCP `initialize` carries no identity, the environment carries none, and cwd is not discriminating.
- Neither → `unbound`: only `list_agents` is served.

One process may serve several Codex threads (connection pooling, MCP protocol 2026-07-28). The shim keeps one agent record per (harness, session_ref) and binds nothing to the first caller; every call is routed by its own evidence.

Agent identity (CQ9): `agent_id` = first 16 hex of sha256(`<harness>:<session_ref>`), stable for the session's lifetime and independent of any display name. Storage, sockets, locks, journals, task stores, claims and reply-routing records key on `agent_id`; the agent name is a lookup alias. On the first bound call for an agent the shim writes `~/.local/state/crosstalk/agents/<agent_id>.json`:

```
{ "agent_id": "<16 hex>", "name": "<agent name>", "harness": "claude|codex", "role": "primary|subagent", "owner": "<name>|null",
  "pid": <shim pid>, "harness_pid": <Claude session pid (= shim ppid) | null for Codex>, "harness_started_at": "...|null",
  "cwd": "...", "session_ref": "<claude session id | codex thread id>",
  "a2a_url": "http://127.0.0.1:<port>", "uds_path": "~/.local/state/crosstalk/sock/<agent_id>.sock",
  "instance_id": "<uuidv7, new per agent registration>", "harness_endpoint": "<codex app-server endpoint | claude socket path | null>",
  "harness_version": "<Codex app-server version from initialize | null>",
  "credential_ref": "<path to 0600 file holding this agent's A2A bearer token>",
  "installed": true, "started_at": "...", "protocol": 1 }
```

`started_at` and `harness_started_at` are the kernel process start times of the shim and of the Claude session process. `role` defaults to `primary`; `role` and `owner` change only through `claim`/`release` (§7).

Name (CQ8, CQ9): the harness session name (Claude `name`; Codex thread `name`) if free, else `<harness>-<cwd basename>-<first 8 hex of agent_id>`; if that is also taken, extend the suffix two hex at a time until free (agent_id is a hash of the whole session_ref, so identifiers that share a long common prefix, as the four spike-9 threads `01a1a3…` do, still get distinct suffixes). A name is held under its own `flock` for the registration's lifetime. A harness rename does not change `agent_id`, sockets, journals, claims or routing records; it updates the alias only, unless the session has set a name with `rename` (§8), which pins the alias: the new name is taken under its lock, the descriptor's `name` is rewritten, the old alias is released. `send_message(to)` resolves aliases at send time; a message to a released alias is `unknown` with reason `no_such_agent`. Owner references in claims are by `agent_id`.

Binding (F2): `harness_endpoint` + `session_ref` bind an agent to exactly one conversation on exactly one server. A shim never selects a conversation by name, cwd, activity or "most recent". Codex endpoint (CQ10): the shim queries each known endpoint (the managed control socket `~/.codex/app-server-control/app-server-control.sock` plus any `harness_endpoint` recorded in a descriptor); an endpoint counts as hosting the thread only if `thread/loaded/list` includes it (`thread/read` alone may return stored history from a server that does not host the live conversation). Exactly one host → bind it as `harness_endpoint`. More than one → binding stays unresolved, inbound is `unreachable` with reason `ambiguous_endpoint`, journaled; never the first response. None → sending works, inbound is `unreachable`, except an `ask`, which is `rejected/no_endpoint` (§8). Re-resolve (#116): when a delivery finds the bound endpoint empty, or cannot connect to it before anything is sent, the Codex adapter runs the same lookup again, at most once per thread per 10 s; exactly one host → this and later deliveries go there, so a session that bound while the daemon was down or still loading its thread recovers without a restart. The agent's binding, the journal key and the descriptor keep the bind-time value. `canAcceptDirectInput` is a separate per-delivery condition, not a binding input.

Credentials (F5): the bearer token lives only in the file `credential_ref` points to (0600). Descriptors and `list_agents` output never contain it; logs redact it.

Publish order and ownership (F8, C7): there are two locks: the agent record lock `~/.local/state/crosstalk/agents/<agent_id>.lock` (one live registration per session) and the alias lock `~/.local/state/crosstalk/names/<name>.lock` (one live holder per name), both taken first and held for the registration's lifetime; descriptor check, publication, replacement and cleanup happen only under it. A held lock means a running owner: the newcomer registers under its fallback name (§3 Name rule) and its model is told so in the tool result, as "live" only when the holder is not superseded (see Superseded sessions below); a later call takes the name once it is free. Order, on the first bound call: take the lock, replay the journal and drain the pre-bind store (§5), bind uds + A2A listener, confirm the harness binding, then write the descriptor atomically (temp + rename). On exit the shim removes each descriptor only under its lock and only if the file's `instance_id` is its own. Readers treat a descriptor as stale when the pid is dead or the pid is alive but the process start time does not match `started_at` (pid reuse). Known gap: a claim or rename that stalls in the journal past the retirement budget can still republish the retired descriptor when it resumes, since `Publish` checks only the agent lock (`internal/registry/registry.go`); it needs a journal stall over 5 s during a session switch, and the fix is to make name release terminal for `Publish` and `Rename`.

`uds_path` is agent_id-stable (CQ7, CQ9): it survives a shim restart, so a reply address embedded in an envelope before the restart still reaches the agent after it.

Discovery: `list_agents` enumerates every Claude session from `~/.claude/sessions/*.json` and every loaded thread from `thread/loaded/list` + `thread/read` on each known app-server, merged with the descriptor directory (dead or reused pids pruned). Each row: `name`, `harness`, `cwd`, `status`, `crosstalk: bool` (a shim has bound this session), `reachable: bool` (Claude: its socket exists; Codex: status loaded and `canAcceptDirectInput`), `backend` (Codex rows on the `openai` provider with ChatGPT auth only: `reachable` or `unreachable` from the hosting app-server's `account/rateLimits/read`, which tests the ChatGPT backend and not the model itself, so a usage-only or Responses-only outage can mislead it; `unknown` when that cannot be told, for example an API-key account, another provider, a timeout or an endpoint that cannot be dialed; omitted for Claude rows and rows with no loaded thread; cached 30 s per endpoint; ADR 0025), plus `role` and `owner` for bound agents. A session without CrossTalk is listed and messageable (inform only, injected natively by the sender's shim) but has no A2A card and cannot send. herdr is not consulted. Paired hosts (v0.2.0 slice R6): `list_agents` also asks every host in `peers.json` for `GET /v1/agents` (pinned mTLS, `remote.Client`), in parallel with the local listing and each other, under one shared 1.5 s deadline; a host that has not answered then shows `reachable: false, error: timeout` and contributes no rows. A remote row has `name` as `<name>@<alias>`, `host`, `harness`, `agent_id`, `crosstalk`, `messageable`, `reachable`, `status`, `role` (CrossTalk rows only) and, on a native session, `note`; it never has cwd, path, pid, session_ref, endpoint or owner, because the gateway builds each row from an allowlist struct. A peer's listing is untrusted: rows are validated with `a2a.ValidateAttested`, status is control-stripped and capped at 32 bytes, a body over 1 MiB or more than 1000 rows is refused, and a malformed row is dropped (`invalid_listing` only when no row is usable). Remote rows are never written to the descriptor directory.

Claude-visible registration (R2) is out of v1 (1.6): a reply address travels in the envelope (`from="uds:<uds_path>"`), so Claude needs no `~/.claude/sessions` record for a shim to receive native replies, and a pooled Codex shim has no single pid to publish under. Claude sessions see other agents through `list_agents`.

Superseded sessions: Claude Code's `/clear` keeps the process and its shim and starts a new session id, so the old session's record outlives its session. A harness that can prove this implements the optional `harness.Supersession`; Claude reports a session superseded when `~/.claude/sessions/<harness_pid>.json` parses and names another session, and a missing or unreadable file is no evidence. Codex does not implement it: one process serves several live threads, and "same shim, different session" is not evidence. Three rules follow, all in the shared path:
- Readers: `Registry.List`, and so every lookup by name or agent_id, `list_agents`, and the uds sender check, skip a superseded descriptor. Its name stops resolving at once, and the replacement shows as one row: a native row (`crosstalk: false`) until its first bound call, then the bound row.
- Holder: the shim retires a superseded agent before it registers any new agent, and every 2 s without a call. Retiring is the per-agent §9 Exit: new tool calls for the agent are refused, listeners stop, every in-flight journal writer finishes so its final record lands (tool calls, obligation retries, ask-deadline notices, claims applied to the agent; A2A handlers, workers and task-deadline timers, and uds handlers, through their own drains; a writer refused by the drain does nothing and leaves durable state for replay), descriptor and both locks go, the journal stays. All of that waiting shares one close wait (`HandlerCloseWait`, 5 s). If any writer does not stop within it, the descriptor and alias lock still go, the journal stays open, and the agent lock stays until process exit, so a resume of that session is `rejected/agent_held` until the shim process exits.
- Name: a same-process replacement therefore takes the name on its first call. Across processes a held lock cannot be taken from its holder: a newcomer that finds a superseded holder registers under its fallback name, is told the holder has ended (never "live"), and takes the name on a later call. Every bound call retries while the agent's name differs from its harness name, so any agent under a fallback name gets the harness name once it is free; the model is told in `notice`.

A superseded session is not listed, and its agent_id and name are `no_such_agent`. A resume (`claude --resume`, `/resume`) is an ordinary registration of the old `session_ref`: same `agent_id`, same journal replayed (open asks, obligations, routes, deadlines), harness name if free, else fallback name with the "live" notice. A message sent to the session while retired fails at the sender; nothing is queued for it.

Harness-native registries the shim reads, never writes: `~/.claude/sessions/<pid>.json` (Claude: self-binding through the parent pid, discovery and status; never sender identity on the uds ingress), app-server `thread/loaded/list` + `thread/read` (Codex).

## 4. Message

Internal normalized record (F12). This is what the receiver chain and the mailbox hold; it is not a wire format. On the A2A ingress it is decoded from the pinned SDK's `Message` (standard `messageId`, `role`, `parts`, `contextId`, `taskId`); CrossTalk fields travel in `metadata` under the `crosstalk.*` namespace and are all optional. A plain text `SendMessage` with no metadata is valid and normalizes to `kind: inform`, `delivery: immediate`.

```
{ "message_id": "<uuidv7>", "in_reply_to": "<message_id>|null", "context_id": "<conversation>", "task_id": "<id>|null",
  "from": "<agent name>", "to": "<agent name>", "kind": "inform|command|ask", "delivery": "immediate|next_turn",
  "deadline_seconds": <int, ask only, 0 = none>,
  "hop_chain": ["<24-hex>", ...], "sent_at": "...", "parts": [{"type":"text","text":"..."}] }
```

`ask` is reply-required inform: it has `inform`'s permissions (§7) except that an unverified sender may inform but not ask and opens a reply obligation keyed by its `message_id`. `kind` is typed only as `metadata.crosstalk.kind` on an authenticated A2A request; absent = `inform`. The uds ingress has no kind encoding (§5). `delivery` drives the Codex adapter and travels as A2A metadata; it is a no-op on the Claude adapter, where the socket decides mid-turn vs next turn.

`from` is the sender's name as the receiving session sees it, rebuilt by the receiver from the verified identity: `<name>` for a local agent, `<name>@<alias>` for an agent on a paired host (v0.2.0 slice R4; the alias is the receiver's own name for that host, taken from the gateway-set `X-CrossTalk-GW-Alias` header, never from the sender). The dedupe, receipt, route and reply-obligation key of a remote sender is `remote:<fingerprint>/<agent_id>`, never an agent_id, so a message_id sent by two hosts, or by a host and a local agent, is two messages.

hop_chain uses Claude's convention (24-hex sha256 prefixes, max 32) so a chain an A2A client supplies is compatible with Claude's. The hop guard applies to A2A forwarding only: a native frame is never forwarded (ADR 0009) and carries no forwardable chain, so the receiver does not check a chain on a native frame. No code forwards a message today, so no code appends a hop; a reply gets a new message_id and sets in_reply_to.

Messaging limits and the nudge (wave 2, operator ruling 2026-11-04, ADR 0014). There is no limit on how many messages a session sends, and nothing bounds spend: a loop between two sessions is stopped by ending a session. Every send from the MCP send path starts a fresh one-element hop chain; nothing infers a forward from an earlier inbound message. `hopCheck` still guards the one case it can: an A2A client that supplies its own chain (a repeat of the receiver, or more than 32 entries, is rejected). Size, pending-work, open-ask limits and dedupe stay. The send result carries a **nudge**, not a guard: the shim counts the sends each agent makes to each peer (the peer's agent_id, or `harness:session_ref` for a native session), counting every send except one that came back `rejected` or `unreachable` (and except an inform to a name that matches no session, which comes back `unknown` with reason `no_such_agent`; it reached no peer), and `send_message`, `ask` and `reply` all count (a retried reply is not recounted, and a model that keeps retrying an unreachable peer is never stopped, since those sends do not count). When a count reaches 30, 60, 120, 240 and so on, doubling (`NudgeFirst`), the result's `hint` asks the model to check whether the exchange is making progress and says it may stop, or tell its user, if not; the send is still delivered, and the text appends to any hint already there. The count is in memory, per agent and per peer, and resets on restart. Each firing writes one `nudge` journal record (peer, count, time). The numbers are guesses, and whether models heed the hint is unmeasured. It misses fan-out (one message to many peers, each below the threshold), restarts (the count resets), failed sends (not counted), `crosstalk send` and any client that goes around the shim, native bounces, and Claude's own SendMessage.

## 5. Ingress contracts (both feed one receiver)

A2A ingress (required for v1; operator requirement 2026-11-03). Each session is a first-class A2A agent served by its shim.

- Pinned target (F11, V22, C1): **A2A protocol 1.0, JSON-RPC binding**, implemented with the official Go SDK module `github.com/a2aproject/a2a-go/v2` at one tagged release in `go.mod`; the tag and the matching `examples/helloworld/client` revision used as conformance client are recorded here at pin time (candidate: v2.7.0, reported by review, unverified). Method names are the 1.x ones: `SendMessage`, `GetTask`, `CancelTask`, `ListTasks`. Streaming (`SendStreamingMessage`), push notifications and the extended card are not implemented and not advertised; each such method returns the error the pinned spec mandates for a disabled capability, fixed per method in the test 17 matrix.
- Agent Card (F13, C1, V29, CQ2): served at `/.well-known/agent-card.json`, built with the SDK's card type and validated by its resolver. Fields: `name` (agent name), `description` ("<harness> session, role <role>. Task completion is delivery evidence, not model-read or work-done."), `version` (crosstalk build version), `supportedInterfaces` (one entry: the JSON-RPC URL, JSON-RPC protocol binding, protocol version 1.0), `defaultInputModes`/`defaultOutputModes` = `["text/plain"]`, `capabilities` all false, `securitySchemes` = one HTTP bearer scheme and `securityRequirements` requiring it, `skills` = `inform`, `command`, `ask` each with id, name, description, tags and an example. Role and harness go under `metadata.crosstalk` only; the card carries no cwd (ADR 0011).
- Wire handling (F12, C1): the SDK decodes the request; the receiver chain works on the normalized record; the response is the SDK's `SendMessageResponse` (`result.task` or `result.message`) inside the JSON-RPC success envelope, or a protocol error (`InvalidParams`, `TaskNotFound`, `TaskNotCancelable`, `UnsupportedOperation`), never the internal `{message_id, state}` pair. The A2A encoder and the Codex app-server encoder are separate code: Codex omits the JSON-RPC version header on the wire, A2A includes it.
- Task mapping (F14, V6, C8, CQ2): every accepted `SendMessage` creates a server-owned task, `submitted` on acceptance and `working` once dispatch is claimed (`dispatching` in the journal: an attempt is claimed, not delivered). `inform`/`command`: `completed` only on evidenced harness acceptance: Claude = the session-socket connection stays open past the short grace period after the frames are written (Claude sends no acknowledgement, spike 10); Codex = a success response to `turn/start` with the named tool output, or to `thread/inject_items` for queued delivery. Both are delivery evidence to the harness, not evidence the model read the message. `failed` on `unreachable` or `rejected`. A bare write whose connection closes or resets within the grace period, or any ambiguous failure, is `unknown` and leaves the task `working` until reconciled (journal, below). `ask`: `completed` only when the receiving session's `reply` for it is correlated (§8); the reply text is the task's final `Message`; `failed` with `metadata.crosstalk.reason: "deadline"` when `deadline_seconds` elapses first. Every task carries `metadata.crosstalk.completion: "delivered"`: completion is delivery evidence, never model-read or work-done.
- Waiting (C1, CQ1): default `SendMessage` (`configuration.returnImmediately` false or absent) returns only when the task reaches a terminal or interrupted state. There is no server-timeout return of a non-terminal task; a timeout or dropped connection never manufactures completion. `returnImmediately: true` returns the `submitted` task at once; CrossTalk's own `send_message` and `ask` always set it.
- Continuation (C3, C1): a `SendMessage` with `taskId` is allowed only from the principal that created the task. The appended message runs the full receiver chain as a new message with the same `context_id`, policy included; it never inherits the original's kind or authorization. Unknown or another principal's `taskId` → `TaskNotFound`; terminal `taskId` → `UnsupportedOperation`.
- Cancellation (F15, C5, CQ4): the dispatch claim and `CancelTask` are serialized by one per-agent lock, and the claim is durably journaled under that lock before any harness write. `CancelTask` succeeds only while the task is `submitted` with no claim: the message is removed from the mailbox and the task is `canceled`, so a successful cancel means no harness write happened. Claimed (`dispatching`, `working`) or terminal → `TaskNotCancelable`; the shim never interrupts a harness turn. A `codex queue` handoff is an external side effect and is past the claim. `GetTask`, `CancelTask`, `ListTasks` (own tasks only) and continuation are allowed only to the principal that created the task.
- Authentication (F16, V14): bearer tokens are private files, never in descriptors. Each shim holds its own token (0600, path in `credential_ref`) and a per-user shared **peer token** at `~/.local/state/crosstalk/peer.token` (0600, created on first start). Any client presenting the peer token is the principal `local-user`; a shim presenting its own token is the principal of its registered agent. Own-token verification: receiver B resolves the claimed sender's descriptor by `name`, reads the file at its `credential_ref`, and compares in constant time. This proves the sender can read a 0600 file of this user, the same strength as the peer token, accepted under the §1 non-goal; the registered-agent principal gives attribution and policy, not isolation. All holders of the peer token are one principal, `local-user`: "own tasks" means every task that principal created, with no isolation between individual non-shim clients. The token is owner-readable only and never appears in descriptors, `list_agents` output, Agent Cards or logs. A principal without agent registration may send `inform` and `ask` and read, list or cancel its own tasks; `command` requires a registered agent whose role/owner satisfies §7. The conformance test configures the sample client with the peer token. The peer token has one creator, the A2A server's `Listen` (an exclusive create, idempotent across shims); each agent's own token is created by the shim's A2A wiring at `~/.local/state/crosstalk/tokens/<agent_id>.token` before `Listen`, and a receiver accepts a sender's own token only when its descriptor's `credential_ref` is exactly that path for its agent_id. Remote sender (v0.2.0 slice R4): a bearer equal to the gateway credential (`~/.local/state/crosstalk/gateway.token`, 0600, read and mode-checked on each request, constant-time compare) marks a request the gateway forwarded after it stripped every inbound `X-CrossTalk-*` header; the sender is then built from six gateway-set headers, `X-CrossTalk-GW-Host` (the pinned fingerprint, 64 lowercase hex), `-Alias` (the receiver's own alias for that host), `-Agent-ID` (16 lowercase hex), `-Name` (base64url of 1 to 256 bytes of UTF-8 with no control character), `-Harness` (`claude` or `codex`) and `-Role` (`primary` or `subagent`), each exactly once. These names are distinct from the `X-CrossTalk-Remote-*` names a sending host puts on the wire, which the gateway reads, validates and discards (§5 "Gateway forwarding"). A missing, repeated or malformed value is refused with a JSON-RPC rejection (state `rejected`, reason `invalid_remote_sender`), not an HTTP 400, so the sending side reads it as rejected, not unknown, and nothing reaches the receiver chain. Without the gateway credential the six headers mean nothing: the peer token and a local agent's own token keep their meaning whatever else the request carries. The remote `Sender` has `Host`, `HostAlias`, `AgentID`, `Name` as `<name>@<alias>`, `Role`, `Harness`, and principal `remote:<fingerprint>`; it is never `registered` (it is not an agent of this host), its key and its SDK task principal are `remote:<fingerprint>/<agent_id>`, and the agent, name and role fields are attested by the paired host, not proven (the same strength as a local sender). `command`, `claim` and `release` from it are refused (§7). The dispatch claim of a remote sender's message is scoped by that key (journal `dispatch`, `outcome` and `cancel` records carry it as `sender`; a local sender's records are unchanged), so claims of different senders never collide. Because `reply` names a message only by its message_id, the receiver also refuses a message whose message_id another sender already holds (journal dedupe record under a different key): rejected, reason `message_id_in_use`, nothing recorded or injected; the A2A ingress asks before it publishes a task, so no task exists for the contested id. A remote host therefore cannot copy a local message's id to capture its reply, and the reverse; a true duplicate from the same sender is deduped as before.

uds ingress (V1, V2, V4, V18, C3): Claude's two-line protocol on `uds_path`: `{"type":"auth","token":T}` then `{"type":"user","message":{"role":"user","content":C}}`. T is the content of the CrossTalk-issued key at `<uds_path minus .sock>.key` (mode 0600, created on first start, refused if it is not a regular 0600 file); a connection is accepted in one of two shapes: (a) the auth line with a valid T, then the user line; or (b) a single `type:"user"` first line with no auth line, accepted only when the peer pid maps to exactly one registered descriptor with a matching start time (a verified sender), else closed with no state (a session without CrossTalk cannot send, test 26). Claude 2.1.317's own SendMessage to a `uds:` address writes exactly one line such as `{"msgV":1,"msg_id":"…","type":"user","message":{"role":"user","content":"<cross-session-message from=… hop-chain=… from-name=… from-mode=…>…</cross-session-message>"},"priority":"next","from":"uds:…"}` and sends no auth line, and Claude's own session socket performs no token check; unknown top-level fields are ignored, `msg_id` and `from` are kept as display-only. C may be a `<cross-session-message ...>` envelope. Sender identity: at `accept()` the shim reads the peer pid with `getsockopt(SOL_LOCAL, LOCAL_PEERPID)` (macOS, `golang.org/x/sys/unix`; `SO_PEERCRED` on Linux), reads that pid's process start time, and maps it to a descriptor whose `pid` (start time = `started_at`) or `harness_pid` (start time = `harness_started_at`) matches. `~/.claude/sessions/<pid>.json` is never consulted for sender identity. Unmapped pid, start-time mismatch, or a pid matching more than one descriptor (a pooled shim) → unverified. A pooled pid is never resolved by picking the first matching descriptor or by trusting `from-name`; it stays unverified. The native shape (b) gets no ack and no bytes back, only EOF once the receiver returns, on success and on every rejection: Claude's sender treats any reply bytes as an error and only EOF as success (live, 2.1.317). The per-agent receiving socket identifies the recipient, never the sender. The uds ingress exists for native Claude senders; shim-to-shim traffic uses A2A, where identity is the per-agent bearer token and pooling is irrelevant. Since T is readable only by this user, an unverified sender is a same-user process not matched to a registered agent, consistent with the §1 non-goal. The uds ingress has no kind encoding beyond `inform`: a frame is `inform`; a frame that requests any other kind (`ask` or `command`, by a `kind` envelope attribute or a `crosstalk.kind` field) is `rejected` without injection, whatever its sender.

`crosstalk send <name|agent_id> <text|->` is a client of shape (a) for plain scripts: it resolves one registered descriptor by name or agent_id (several of one name → error), reads the agent's key file, writes the auth line and one `user` line with the text as content, and prints the ack (`message_id`, `state`, `reason`); exit 0 for `accepted` or `queued`. The script is not a registered agent, so the receiver sees an unverified sender and the message is an `inform` labelled unverified; it enters the one receiver chain through the uds ingress and is never injected by the CLI. It does not create a key (a missing key is an error) and does not reach native sessions that have no CrossTalk binding.

Two identities per inbound message (F4): the **transport peer** (the process on the socket: a Claude session pid, another shim, or unknown) and the **original sender** (the registered agent the message is from). On the A2A ingress both are the sending shim's agent. On the uds ingress the transport peer is verified from the socket; the original sender equals it when the peer is a registered agent, and is otherwise unverified. A relay never upgrades the original sender's identity beyond what the transport proves.

Native replies through a shim (F4, C8, ADR 0009): when shim B injects a message from A into Claude session B, the envelope's `from` is B's own uds socket and `from-name` is A, and it carries `message-id` so the `reply` tool can name the inbound message. A native `SendMessage` from session B to that address therefore reaches shim B as a frame with no correlation id. Shim B never forwards it: it journals the frame as `bounced` and injects a message from `crosstalk` back into session B saying the native message was not delivered, quoting its first line, and listing the open inbound messages (message_id, sender name, kind) it may answer with `reply`, or `send_message` otherwise. A bounce opens no route and is never itself bounced. Only the `reply` tool, naming the inbound message id, completes an ask and closes its route; an ask nobody answers ends at its deadline. (Live round 4 on 7bf18d1 showed the earlier sole-open-route guess completing an overlapping ask with an inform's text.)

Native-message normalization (F6): a frame arriving over uds without our metadata is assigned a fresh message_id by the receiving shim, `in_reply_to` stays null unless the correlation above is unambiguous, and it is exempt from the message_id dedupe (identical repeated text is legal). Identified messages: authenticate first, then look up (sender, message_id); acceptance is recorded atomically with the journal write so two concurrent duplicates cannot both inject; a retry returns the prior state.

Journal (V8, C6, CQ4): one append-only JSONL file per agent at `~/.local/state/crosstalk/journal/<agent_id>.jsonl`, written and fsynced before an ingress or tool acknowledges. Records: dedupe keys (verified sender, message_id, state); tasks (task_id, message_id, context_id, creating principal, kind, task state, delivery state, reason, ask reply text, deadline, and the A2A message the change appended to history; one record per task change); dispatch claims (message_id, `dispatching`); dispatch outcomes; reply-routing records (session, delivered message_id, original sender); reply-delivery obligations (§8 `reply`; state `pending`, `completed`, `released`, `delivered`, or for a reply to a paired host's agent the ends `rejected` and `unreachable`, with the reason); claims on this agent (owner, claimed/released, §7); the name set with `rename` (§8, kept while set; an older shim that rewrites the journal drops it, and the session falls back to its harness name). Every record carries the binding it was accepted under (`instance_id`, `harness_endpoint`, `session_ref`). Replay on agent registration, under the name lock: acknowledged acceptance is always recoverable; a partial trailing line is discarded; an unresolved `dispatching` record is never re-injected but reconciled (Codex: `thread/turns/list` on the recorded endpoint and thread, for message-specific evidence; Claude: no evidence is available, so it stays `unknown`); unresolved records surface through `receive_message`. Records bound to a different (`harness_endpoint`, `session_ref`) than the agent's current binding are never injected or routed into the new conversation; they become `unreachable` and surface through `receive_message`. Records older than 24h are truncated, except unresolved ones (`submitted`, `dispatching`, `unknown`, `recovered`, open asks, undelivered replies), which are kept until resolved. A2A tasks are journal-backed (S12, 2026-11-03): the A2A server rebuilds its tasks from these records on start, drops terminal tasks older than the retention window, keeps open ones and re-arms their ask deadlines; a delivery outcome learned after the receive returned reaches the task through `Server.Resolve(message_id, state, reason)` (accepted/queued complete an inform or command, rejected/unreachable fail it, unknown leaves it working), which the wire layer applies at start from journaled dispatch outcomes and a later reconciler must call. Pre-bind store (ADR 0026, ADR 0023): a second source of dedupe and route records on registration. `internal/prebind` holds `~/.local/state/crosstalk/prebind/<target agent_id>.jsonl` (directory 0700, files 0600 opened without following links, one advisory lock `prebind/.lock`), one entry per inform a sender's shim injected into a session with no binding, signed with HMAC-SHA256 under the sender's own token (`tokens/<sender agent_id>.token`). In `Shim.Bind`, after `Receiver.Recover` and before the descriptor is published, the shim drains it: a drain claims the file by renaming it to `<agent_id>.claimed` (first finishing a claimed file left by an earlier drain), verifies each entry (MAC, the target's agent_id, harness and session_ref, a sender with a local token file, not a `remote:` key or `local-user`, delivered within `InformRouteTTL`), drops every entry whose message id is used by more than one sender, and hands the rest to `Receiver.ImportDelivered`. That writes the dedupe record (marked `imported`; idempotent per sender and message id; a message id already held by another sender is dropped and, if that holder was itself imported, its route is journaled closed) and an open inform route stamped `min(delivered_at, now)`, which `Recover` restores, so the route expires `InformRouteTTL` after delivery. An import never injects and never reopens a route that has a closed record. Caps: 64 entries and 4 MiB per target; 256 data and claimed files and 16 MiB for the directory; files older than `InformRouteTTL` are swept on every write and drain.

Admission (C9): limits, checked in the policy step before acceptance: message size (default 64 KiB of text parts), pending tasks per agent (default 256; this bounds unresolved A2A task ids, not every unresolved inbound message: continuations of an open task and native ingress occupy no new task, see §13 WA2), open asks per agent (default 32), concurrent default-wait `SendMessage` calls (default 64). Exceeding a limit returns `rejected` (A2A: a JSON-RPC error, no task created) and never evicts accepted work or its dedupe record.

Gateway ingress (v0.2.0 slice R2; plan §3.2; a third listener beside A2A and uds, planned and opt-in; it forwards `/v1/a2a/{agent}` as described in "Gateway forwarding" below): `crosstalk remote serve` runs one gateway per host, held by an exclusive non-blocking `flock` on `~/.local/state/crosstalk/gateway.lock` (0600; it holds the holder's pid, so a second gateway exits 1 naming it). It listens on the one configured `bind:port` over TLS 1.3 only, with `RequireAnyClientCert`, session tickets off and `InsecureSkipVerify` set so that the pin check in `VerifyConnection` is the only check; that runs on every handshake. The client's fingerprint (SHA-256 of its certificate's SubjectPublicKeyInfo) must be in `peers.json`, read through `remote.Peers` (the one cache), or a pairing must be pending in `~/.local/state/crosstalk/remote/pending.json` (read through the one reader that `POST /v1/pair` also uses; then the connection is unenrolled); anything else fails the handshake before any HTTP byte is read. Every request on a pinned connection re-looks-up the fingerprint, so `unpair` is refused at the next request on an open connection (403, connection closed). Before parsing: a handshake gets 5 s, the header read 5 s, the whole request 10 s, the response 30 s, an idle connection 60 s; the body is capped at 80 KiB (413); at most 16 connections may be mid-handshake (a further one is closed at accept), 64 pinned connections, 4 unenrolled connections each closed 15 s after its handshake and when no pairing is pending, and per peer host 8 concurrent requests and 120 requests per minute (429). Unenrolled connections get 403 on every path except `POST /v1/pair` (slice R3); a pinned peer may also call `POST /v1/pair` (after the same per-host concurrency, rate and body checks as any pinned request), so pairing again repairs a half-made pairing or updates an address; every other pinned request goes to the handler (`remote serve` sets the forwarder, "Gateway forwarding" below; a gateway built without a handler answers 404). `POST /v1/pair` takes `{id, alias, address, mac}` (4 KiB cap); the gateway takes the client's fingerprint from the handshake, never the body, and checks `mac` (HMAC-SHA256 keyed by the one-time secret over `crosstalk-pair-v1`, the client fingerprint and this host's fingerprint) in constant time. It counts one attempt per second for the whole gateway before it reads any file (429), then, holding `pending.lock` from the read of `pending.json` to the end of the `peers.json` write, finds the entry by id (404 unknown, 410 expired, judged by a clock read after the lock is held), verifies the proof (403), then under `peers.lock` checks the alias (held by another fingerprint: 409 and the entry stays), removes the entry and writes the peer with the entry's id appended to the peer's `pairing_ids` (the last 8 are kept, so a `remote pair` process that is stopped through more than 8 later pairings of the same host reports failure although it enrolled; accepted limitation; re-pairing a known fingerprint updates its alias, address and `paired_at`). A refused attempt never changes either file. Success answers `{"alias"}` and closes the connection. `remote pair` writes the entry (`id`, `secret`, `expires_at` 10 minutes ahead, optional `alias`; 0600) and waits until it leaves `pending.json` with a peer whose `pairing_ids` lists its entry's id, until it expires, or until interrupt (it then removes the entry); it needs the gateway running, tested by a non-blocking `flock` on `gateway.lock`. `remote join` reads the token from stdin only and checks the server's fingerprint against the token's before it sends anything. If the bind address is missing the gateway retries every 10 s (state `service running, port not bound`); a port held by another program for 60 s ends it with exit 1. `~/.local/state/crosstalk/gateway.token` (0600) is created once with an exclusive create and kept across restarts; the A2A server reads it as the remote-sender credential (slice R4, §5 Authentication).

Gateway forwarding (v0.2.0 slice R5; plan §3.2, §8): `crosstalk remote serve` sets `remote.Forwarder` as the gateway handler. A pinned peer posts `POST /v1/a2a/{agent_id}` with a JSON-RPC A2A request body and its sending agent's attested fields in four request headers, `X-CrossTalk-Remote-Agent-ID`, `-Name` (base64url), `-Harness` and `-Role`, each exactly once; the sender never sends the host fingerprint or the alias. Order of checks, each a refusal before the next: (1) the path must be `/v1/a2a/` plus an agent_id of 16 lowercase hex (any other path under it, with `..`, an encoded separator, a URL or an upper-case id, is `rejected/no_such_agent`; a path outside `/v1/a2a/` is 404; a method other than POST is 405); (2) the four fields are validated by `a2a.ValidateAttested`, the same function `authenticate` applies to the `X-CrossTalk-GW-*` headers, and a missing, repeated or malformed value is a JSON-RPC rejection `rejected/invalid_remote_sender` with HTTP 200, never a 400, so the sending client reads it as rejected and not unknown; (3) the body must be one JSON object with exactly one top-level key that folds to `method` and at most one that folds to `params`, and the method must be exactly `SendMessage` or `GetTask`; anything else (`CancelTask`, `ListTasks`, `SendStreamingMessage`, `SubscribeToTask`, a case or whitespace variant, a duplicate method key, a JSON-RPC batch) is the SDK's `UnsupportedOperation` (batches and non-objects are `InvalidRequest`); a `SendMessage` whose `message.metadata.crosstalk` has a `claim` key, with any value, is `rejected/remote_kind`; (4) the agent_id is looked up in this host's registry (`registry.List`, registered agents with an `a2a_url` only, so a native session is `rejected/no_such_agent`) and only an `http` URL on a loopback address is dialled; nothing in the request body, query or headers chooses the target. The gateway then builds the loopback request itself: the JSON-RPC body byte for byte, `Content-Type: application/json`, the sender's `A2A-Version` header, `Authorization: Bearer <gateway.token>` and the six `X-CrossTalk-GW-*` headers (`Host` is the fingerprint of the pinned connection, `Alias` is the alias in this host's own `peers.json`, the rest come from the validated fields); no other inbound header is copied, so every inbound `X-CrossTalk-*` header and the sender's `Authorization` are dropped whatever their case or count. The gateway's JSON-RPC refusals are produced by the SDK's own encoder, so they read exactly like the loopback server's. A loopback server that refuses the connection answers `rejected/no_such_agent` (the agent exited after registering); any other loopback failure is HTTP 502, which the sender reads as unknown. The loopback response status, `Content-Type` and body are passed back; a reply over 1 MiB is never cut off but replaced by a JSON-RPC error with state `unknown`, reason `response_too_large`. The 80 KiB body cap, the per-peer limits and the pin recheck of "Gateway ingress" apply before the forwarder runs.

Receiver, both ingresses, in order: authenticate → dedupe on (verified sender, message_id) for identified messages → hop_chain check (repeat or >32 → reject) → policy (§7, including admission) → inject (§6). Returns the internal `{message_id, state}`; each ingress encodes that into its own wire response (A2A: Task/error; uds: see the wire behaviour in §5).

## 6. Injector per harness

Each adapter below is wrapped by its package's `NewHarness` (`claude.NewHarness`, `codex.NewHarness`, ADR 0008). The Claude harness's `NativeReplyAddress` is the injecting agent's `uds_path`, passed to `Inject` as `Delivery.ReplyAddress` and sent as the envelope `from`; Codex has none.

Claude adapter: `inject` = connect to the session's `/tmp/cc-socks/<pid>.sock`, auth with the token from `~/.claude/sessions/<pid>.*.key`, send one `user` line whose content is the reconstructed envelope `<cross-session-message from="uds:<shim uds_path>" from-name="<from>">\n<escaped body>\n</cross-session-message>`. Claude sends no acknowledgement of an injected line (spike 10): the connection staying open past the short grace period after both frames are written is `accepted`; EOF, reset or any other reply is `unknown` (CQ2); a failed first write is `unreachable`. Mid-turn delivery between tool calls is verified (spike 1). Next-turn delivery into an idle session is unverified and gated by spike 6 and test 19. `delivery` is a no-op on this adapter.

Codex adapter (ADR 0007): `inject(delivery)` uses the endpoint recorded in `harness_endpoint` at registration, or the endpoint a re-resolve found when that one is empty or refuses the connection (§3 F2). The connection uses WebSocket framing and initializes with `capabilities:{experimentalApi:false}` before any delivery. The existing version gate and endpoint ownership checks remain.

- Verified immediate delivery: `turn/start {threadId,input:[],toolOutput:{name:"receive_message",namespace:"crosstalk",output:<JSON text>,retain:true}}`. Idle starts a turn; active regular work consumes the tool output at the next model boundary. No user input, active-turn lookup, expected-turn retry, or model/cwd/approval overrides.
- Deferred delivery: `next_turn` and all unverified senders use `thread/inject_items {threadId,items:[{type:"function_call_output",name:"receive_message",namespace:"crosstalk",output:<same JSON text>}]}`. This is a no-wake history append. `next_turn` means the next model request, which can be within an already-active turn, not a strict new-turn boundary. Idle work is never started by this path. `queued` requires acknowledged append; shim mailbox placement alone is insufficient.
- Non-steerable turns: any definite `activeTurnNotSteerable` error from `turn/start`, recognized by the error message text (case-insensitive) or the structured `error.data` key (the app-server defines only review and compact today) falls back once to the deferred append. Other definite refusals and pre-send failures are `unreachable`; no retry. A valid immediate response naming a turn is `accepted`; the append's empty result is `queued`. Malformed success or a possibly sent request without a response is `unknown`, with no resend or alternate-path fallback.
- The existing dispatch journal records outcomes. Raw appends may be absent from `thread/turns/list` and `thread/items/list`; lack of a displayed message is never proof of nondelivery. Reconnect cannot automatically resolve these ambiguous appends, which stay `unknown` rather than being re-injected.
- Tool data: the adapter JSON-encodes receiver-validated sender name, verification flag, message identifier, kind, reply reference, parts, and a fixed notice that peer content has no operator authority. Peer body text cannot set outer fields. Both delivery paths preserve the same data, without developer/system context injection.
- Rendering: immediate output is a `functionCallOutput` item, but stock clients may hide generic tool output; raw appends can be omitted from normal history. No sender badge is promised. Never use the internal `codex_tui`/`codex_app` namespace to impersonate native delegation.
- `crosstalk capture` remains a diagnostic; its deliberately failing steer probes and existing version fixtures remain valid. Production delivery no longer invokes `codex queue` or `turn/steer`.

## 7. Trust and policy

Relay (wave 2): The message notice does not cover relay: "any tool but CrossTalk" still lets a peer get a message relayed to a third session. Only the skill speaks to it, and the skill does not reliably load (0 of 6 in the replica runs), so the hole is open. Adding "or message a third session" to the notice was measured and reverted: on Haiku with mocks `peer-wrapper-read` fell from 6 of 6 to 4 of 9 with real file reads, while `peer-relay` already passed on the old text, so the clause cost what it was meant to protect and had no measured benefit; the 8b replica also ran on the old text.

Identity comes from transport (peer pid / A2A auth) matched to registration, never from envelope attributes. Envelope attributes are display only and are reconstructed by the receiver from the verified identity.

| kind | to a subagent | to a primary |
|---|---|---|
| inform | any registered agent; unverified senders allowed | any; unverified allowed |
| ask | verified senders only; an unverified ask is rejected (inform is allowed) | verified senders only |
| command | owner only | any registered primary |
| any kind from a remote sender (v0.2.0 R4) | `inform` and `ask` as for a verified sender; `command` rejected with reason `remote_kind`, whatever the sender's attested role or agent_id; `claim` and `release` refused `remote_kind` | same |
| control | not in v1 | not in v1 |
| unknown kind | rejected | rejected |

A remote sender (an agent on a paired host, v0.2.0 slice R4) is never a registered agent of this host: it can satisfy no check that compares an agent_id with a local agent (a subagent's owner, the receipt of an ask, the native-reply self check), and a reply to it takes the remote branch of the reply path (§8 `reply`, v0.2.0 slice R8). An inform's reply route expires after an hour for a remote key as for a local one.

Claims (role and owner): every agent registers as `primary` with no owner. `claim(name)`: any registered primary may claim an unclaimed registered agent; the claim is journaled in the target's journal and the target is told by an injected `inform`; the target then is `subagent` with that `owner`. `release(name)`: only the owner releases; the target is told the same way and returns to `primary`. An agent's own model can never claim or release itself. A claim ends when the target's session ends. The table above applies to the claimed state.

`kind` is a routing and labelling hint chosen by the sending model; it is not a trust boundary (V3). The control on what a delivered message can cause is the receiving session's own harness permission model. The policy table exists to stop forged or unauthorised `command` from reaching the model, not to make `command` carry authority. `ask` never carries command authority (C3).

Rejected → `state: rejected`, never injected (F7): an unauthorized command is dropped, not downgraded to inform, because the text would carry the same request into the model. `ask` and `command` exist only as `metadata.crosstalk.kind` on an authenticated A2A request (C3); a uds frame is inform, and a uds frame that requests any other kind is rejected without injection (§5). Envelope attributes can cause rejection but never grant command. Continuations re-run this policy (§5). `command` authorizes work only within the receiving session's existing operator permissions; it never changes approvals or settings. Envelope text nested inside a body is body text and never parsed as a second envelope. Peer text is escaped and labelled; it never enters developer/system instructions. Unverified senders never cause `turn/start` (§6; a scheduling rule, CQ3). The same-user credential model is accepted as not being isolation.

## 8. Tool surface (identical in both harnesses, served by `crosstalk mcp`)

The tools are `list_agents`, `send_message`, `reply`, `ask`, `receive_message`, `claim`, `release`, `rename`, `attach`, `detach` and `grant`. An `unbound` call (§3) is served `list_agents` only; every other tool returns `unbound`.

- `list_agents()` → every discovered session with `crosstalk`, `reachable`, `backend` (Codex rows only), status, cwd, harness, name (§3). With paired hosts the output also has the remote rows (no `cwd`, a `host` field, `messageable`) and `hosts`, one entry per paired host: `{host, reachable, agents, error?, warning?}`, `error` one of `gateway_not_running`, `timeout`, `tls_pin_mismatch`, `unpaired_by_peer`, `unreachable`, `invalid_listing`; `warning` says this host's own gateway is not running, so it cannot receive. With no paired host the output is unchanged.
- `send_message(to, text, kind="inform", delivery="immediate")` → `{message_id, state}`; sent over A2A with `returnImmediately: true`. Since the far side answers `submitted` at once, the sending shim polls `GetTask` for up to 2 s for a delivery state past `submitted`/`dispatching` and returns it; if none arrives it returns `unknown` with reason `pending` and keeps the far task id on the journal's outbound record.
- `reply(message_id, text)` → `{message_id, state}`. `message_id` is the inbound message being answered, an ask or an inform; the destination comes from the stored original, not the model. One final reply per ask (continuation messages share their ask's reply), or per standalone inform: it closes the ask, so interim notes go by `send_message`. In order: journals the reply-delivery obligation (CQ4); completes the ask's A2A task, if any, with the reply text as its final `Message`; when the asker is a shim-served agent, sends the reply to the asker's shim as a new inform with `in_reply_to` = `message_id`, which injects it into the asker's bound session; then acknowledges the caller. The reply has its own message_id, so a retry, a repeated `GetTask` or a sender reconnect is deduped and never injected twice (C4). An undelivered obligation is retried from the journal after a restart. When the asker's key is `remote:<fingerprint>/<agent_id>` (v0.2.0 slice R8), the reply is posted as an `inform` with `in_reply_to` through the same remote send as `send_message` to the peer found by fingerprint in `peers.json` (never by alias, label or name), at the asker's agent_id, with the same reply message_id on every attempt: `accepted`/`queued` journal the obligation `delivered`; `rejected` (a gone asker is `no_such_agent`, an unpairing is `unpaired_by_peer`) ends it `rejected` with that reason and no retry; `unknown` and `unreachable` leave it pending, and `reply` returns that state with reason `remote_reply_pending`. A pending remote reply is retried by a timer while the agent lives (first after 60 s, doubling to 10 min) and at registration, until delivered, rejected, or the replier's own clock passes its receipt time of the ask plus the ask's `deadline_seconds` (24 h when the ask had none); then it ends `unreachable` with reason `reply_expired`, journaled. The asker's receiver dedupes on the reply's message_id, and a retried reply is not counted by the nudge. A reply whose asker's fingerprint is no longer in `peers.json` (the host was unpaired) is not rejected: it stays pending and ends `unreachable/reply_expired` at its limit, so pairing the same host again lets it through. The limit is checked when an attempt runs, so an obligation can end up to one retry interval (10 min) after its limit.
- `ask(to, text, deadline_seconds=0)` → `{message_id, state}` at once, where `message_id` is the ask's id; no blocking; the answer arrives through `reply` above. `deadline_seconds` (V15): when it elapses with no `reply`, the task becomes `failed` with `metadata.crosstalk.reason: "deadline"` and the asker's session receives an inbound `inform` with `in_reply_to` set saying the ask expired; already-injected work is not stopped. 0 = no deadline. The deadline is journaled on the outbound ask record (`sent_at` + `deadline_seconds`); replay on registration re-arms the timer of every unanswered ask of the current conversation and expires at once any already past.
- `to` in `send_message` and `ask`, and the target of `claim` and `release`, is an agent name or an agent_id. Resolution: agent_id-shaped values try registered then native agent_id; other values try registered then native name; an empty value matches nothing. The shape of the value picks the lookup: an agent_id-shaped value (16 lowercase hex) matches agent_ids only and never a name, so an agent whose name is 16 lowercase hex is addressable only by its agent_id; any other value matches a registered name without discovery, then a native name; one native match whose session is registered under another name resolves to that registration. Claim of a native id is `rejected/no_such_agent`. Paired hosts (v0.2.0 slice R7): `to` may also be `<name>@<alias>` or `<agent_id>@<alias>`, where `alias` is in this host's `peers.json`. Order: a local match of the whole value first, as above; else, if the text after the last `@` is a paired alias, the remote target; if a local session and a session on that host both match the same value, `rejected/ambiguous_name` with a hint naming the local agent_id and `<agent_id>@<alias>` (the one case where a send with a local match also asks the peer, `GET /v1/agents`, under the 1.5 s bound; no message is sent either way); a value that matches nothing locally and ends in an `@` text that is no paired alias is `rejected/unknown_alias`, with no network call. A bare name never leaves the host: when it matches nothing locally the `no_such_agent` hint lists the `name@alias` rows of the paired hosts that carry it. A remote send lists the peer (`GET /v1/agents`, validated row by row), picks exactly one registered agent (`agent_id` shape: that agent_id; else the exact name; two: `rejected/ambiguous_name`; only a native session: `rejected/remote_native_unsupported`; none: `rejected/no_such_agent`), journals the outbound record with `to` = `remote:<peer fingerprint>/<agent_id>` before the POST, then posts `SendMessage` (`returnImmediately`) to `/v1/a2a/<agent_id>` (the path carries the agent_id only, never a name or peer text) and polls `GetTask` at that same path for the remote settle bound (5 s, `wire.RemoteSettle`; local targets keep 2 s). States: `accepted` or `queued` as the receiver reports; `unknown` with reason `pending` when the connection fails after the request was written; `rejected` with the gateway's reason (`no_such_agent` when the agent left; `unpaired_by_peer` when the peer's handshake refuses this host); `unreachable` with `gateway_not_running`, `tls_pin_mismatch`, `timeout` or `unreachable` when the request never left. A gateway acceptance alone is never `accepted`. `command`, `claim` and `release` to a remote target are `rejected/remote_kind` before any network call. An ask's deadline runs on this host's clock, and its expiry notice reads as for a local ask. The nudge counts per host-scoped key, so two agents on one peer count separately.
- A `send_message` or `ask` result may carry `hint`, plain text naming the model's next step; `reason` stays the stable code. `ask` or a command to a session with no CrossTalk binding is `rejected/native_inform_only` with a hint: when `reachable`, send_message reaches it and its first CrossTalk call binds it, then ask works; when not reachable, nothing reaches it now. A name that matches several native sessions is `rejected/ambiguous_name` for every kind, with a hint to address one by agent_id. An `ask` to a registered session whose harness has no endpoint to deliver to (a Codex thread with no reachable app-server: `--no-daemon`, `-c`, `codex exec`) is `rejected/no_endpoint`: the receiver chain turns the adapter's `adapter.ErrNoEndpoint` into the refusal after the dispatch claim, so the ask leaves no mailbox entry, arms no deadline and is not queued; the sender resends if the target gains an endpoint. The result carries the same hint as an `unreachable` send to that session. `inform` and `command` to it stay `unreachable` and pullable with `receive_message`. A send to a Codex session whose `backend` is `unreachable` keeps its state and carries a hint, never a refusal: for `accepted` or `queued`, that the message is in the thread but the session may not act on it until its app-server reaches its backend again, and that the user may restart the app-server (`codex app-server daemon restart`, which interrupts running Codex work); for `unknown`, that delivery is unconfirmed and the backend is down as well, so the sender checks `receive_message` rather than resending blind (ADR 0025).
- `receive_message(after?, limit?)` → mailbox pull (V23, C9). Every accepted message is journaled. The cursor `after` is a message_id located over the full journal ordering, but the default state filter always applies, with or without `after`: the tool never returns `accepted` or `queued` messages. By default it returns only entries in state `unreachable`, `unknown`, `recovered` or `bounced` (not `accepted` or `queued`, both of which the harness itself delivers), so a model never receives a delivered message twice; it also returns the agent's own outbound messages whose latest state is `unknown` (for example a send whose far-side task was still pending when the settle poll timed out), marked `"direction":"outbound"` with `to`, `task_id` and `reason`, while inbound entries carry `"direction":"inbound"`; `after` only moves the starting point in that ordering. Each entry carries direction, message_id, task_id, from, state, shim instance_id and bound session_ref; credentials redacted. An inbound entry that carries text also carries `notice`, the receiving harness's own peer-text notice (`harness.Noticer`: `claude.Notice` or `codex.Preamble`), so a pulled message is framed like a delivered one.
- `claim(name)` → `{name, owner}`: the caller, a registered primary, becomes the owner of the unclaimed registered agent `name` (§7). Across shims the claim is an A2A `SendMessage` carrying `metadata.crosstalk.claim: {owner, claimed}` with the owner's own token; it creates no task, never reaches the receiver chain, and is refused unless `owner` is the authenticated sender.
- `release(name)` → `{name}`: the owner ends its claim on `name` (§7).
- `attach(inbox)` → `{inbox, owner, members, created}` (ADR 0024): the calling primary joins the role inbox `inbox`, creating it with itself as owner when it does not exist (`created: true`); an inbox with a live owner needs a grant from that owner (`rejected/not_granted`), and an ownerless one needs a grant or a `claim` (`rejected/ownerless`). `owner` and each member's `agent_id` are agent_ids; `members` is responder first, each `{agent_id, name, attached_at}`; the owner's result also carries `grants`. Attaching again changes nothing. Inbox names compare without case and may not be empty or contain `@`, `/`, a control character or an `inbox:` prefix (`rejected/invalid_inbox`).
- `detach(inbox)` → `{inbox, owner, members}`: the caller leaves the inbox; an owner that detaches leaves it ownerless and keeps its grant. Detaching when not a member changes nothing.
- `grant(inbox, to, owner=false)` → `{inbox, owner, grants}`: only the live owner may grant (`rejected/not_owner`); `to` is resolved as `claim` resolves its target and must be a registered session on this host. With `owner=true` ownership passes to `to`, which must already be a member (`rejected/not_member`), and the old owner stays granted. An unknown inbox is `rejected/no_such_inbox`.
- `claim("inbox:<name>")` → `{inbox, owner}`: the caller becomes owner and a member of an ownerless inbox, keeping its grants; a live owner makes it `rejected/inbox_owned`. The `inbox:` prefix is read in any case before the value is resolved, so it never names a session. `release("inbox:<name>")` is `rejected/invalid_inbox`: an inbox has no release form, `detach` leaves it. `attach`, `detach`, `grant` and the inbox form of `claim` are primary-only (`rejected/caller_not_primary`) and act only on the calling session, identified from the request.
- `rename(name)` → `{name, previous}` (ADR 0027): sets the calling session's own alias, from request identity, so a session renames only itself; a primary or a subagent may call it. `name` is 1 to 64 bytes with no control character or `@`, not 16 lowercase hex, and not starting with `inbox:` in any case, else `rejected/invalid_name`; spaces are allowed inside a name but not at either end (HTTP trims the A2A sender header). The alias lock is the uniqueness rule: a name held by another live registration is `rejected/name_held` and the session keeps its alias. The new alias lock is taken and the descriptor rewritten first, then a name record is journaled (a failed append rolls the alias back); the name is a pin: while set, a harness rename (Claude `-n` or `/rename`, a Codex thread title) is recorded but never moves the alias, and a pinned session whose alias differs from its pin (a restart found the name held) retries the pin on every call. The pin is replayed at registration, before the first descriptor publish. `rename` to the current alias still pins it. The way to give a Codex session a name is a brief that tells it to call `rename` first.

States (V16): `accepted` = injected immediately with harness evidence (Claude socket connection open past the grace period, Codex named `turn/start.toolOutput` success with a turn identifier); `queued` = verified no-wake handoff to Codex model history (`thread/inject_items` success; next model request, not necessarily a new turn); `rejected` = policy, auth, admission, hop or kind failure, or an ask to a session with no harness endpoint (`no_endpoint`), never injected; `unreachable` = definite harness refusal, pre-send failure, binding not loaded, systemError, or a journal record bound to another conversation; `unknown` = ambiguous failure after a dispatch claim, no resend; `recovered` = a uds message that passed the re-run checks on replay after a crash before its dispatch claim, never injected and not resent. None implies read or completed. `recovered` is a mailbox-entry state only, never a `send_message` return. `bounced` is a mailbox-entry state only (a native frame the shim bounced back to its own session), never a `send_message` return; `dispatching` is a journal/task-internal state only.

## 9. Lifecycle

Install (ADR 0006, ADR 0013, ADR 0016), once per harness, no wrapper and no per-session configuration: `crosstalk install` copies the binary to `~/.local/bin`, installs the plugin from `plugins/crosstalk/` (the skill only) and registers the server at the binary's absolute path (`docs/setup.md`); the manual forms are:
- Claude: `claude mcp add --scope user crosstalk -- <abs path>/crosstalk mcp`
- Codex: in `~/.codex/config.toml`, `[mcp_servers.crosstalk]` with `command = "<abs path>/crosstalk"`, `args = ["mcp"]` and `default_tools_approval_mode = "approve"` (stops Codex prompting on every CrossTalk tool call)

Start: the harness connects the MCP server; that `crosstalk mcp` process is the shim. Protocol initialization creates no agent. Per-agent state (descriptor, agent_id-stable uds `~/.local/state/crosstalk/sock/<agent_id>.sock`, journal, A2A listener on its own loopback port) is created lazily on the first bound call for that agent, in the §3 order. `not_ready` applies only between a tool call and completion of its agent's binding, which should be immediate. A call whose name lock is held by a live owner is not served under that name.

Exit: when stdio closes the shim removes its own-instance descriptors, sockets and uds keys under their locks (a new key is created on the next start); journals and lock files are kept, since unlinking a lock file would let a later opener lock a different inode (§3). A session whose shim has exited is still listed and reachable natively for inbound (§3), but native replies to its name-stable `uds_path` fail to connect until the harness reconnects the MCP server and the next bound call re-registers the agent, which resumes its journal. Compaction and tool reconnection therefore re-register under the same name and `session_ref`; `/clear` is a new `session_ref` that takes over the name, and the old session's agent is retired as above without the shim exiting (§3 Superseded sessions); a fork is a new `session_ref` and never inherits the parent's binding. Records bound to an old `session_ref` are `unreachable` (§5).

Remote host identity (v0.2.0 slice R1; the listener, pairing and forwarding are slices R2 to R5, §5): `crosstalk remote config` prints this host's alias, bind address, port and fingerprint, and `crosstalk remote config --bind IP [--port N] [--alias NAME] [--force] [--yes]` writes `~/.config/crosstalk/remote.json` (0600) and, if missing, the host key `host.key` (ECDSA P-256, 0600) and self-signed `host.crt` (0644, 20 years). The fingerprint is the SHA-256 of the certificate's SubjectPublicKeyInfo, so it follows the key, not the certificate. `peers.json` (0600, `{"version": 1, "peers": [...]}`) is written atomically (temp file and rename) under `peers.lock`, keyed by fingerprint, and re-read when its mtime, size or inode changes (always, within 2 s of its last write); a file that does not parse is refused with its path and never overwritten. Every file and the directory (0700) is refused if it is not the regular file or directory with the expected mode, like the uds key (§5). Exit codes: 0, 1 unreadable config, 2 usage error, a bind address that is a wildcard or not on an interface of this host (`--force` allows the latter), or no terminal to confirm on without `--yes`. Package `internal/remote`; plan §4.1 and §6.

Remote login unit (v0.2.0 slice R11, plan §4.2 and §4.3): `crosstalk remote enable [--bind ADDR] [--port N] [--alias NAME] [--yes]` writes the config when flags are given, then the unit (macOS `~/Library/LaunchAgents/dev.getcrosstalk.remote.plist`, Linux `~/.config/systemd/user/crosstalk-remote.service`) naming the binary `install` registers, checked executable and answering `crosstalk version`, and starts it (`launchctl bootstrap gui/<uid>`; `systemctl --user daemon-reload` then `enable --now`). The unit's sha256 is stored in `remote.json` as `unit_sha256`: an identical file is a no-op, any other file is refused with nothing written, and `crosstalk remote disable` (stop, remove) and `uninstall` touch only a file whose hash matches. On Linux with `Linger=no` it prints `run: loginctl enable-linger <user>`; nothing runs it. `install --remote --bind ADDR` and `reinstall --remote` run the same steps after the PATH step and end with the `next:` line; on a terminal without `--yes` install asks once (default no) and offers tailnet then private LAN addresses; `--yes` without `--remote` writes nothing remote, and `--remote --yes` without `--bind` exits 2. `uninstall` removes the owned unit when `installKeep` finds no remaining user, including when Homebrew keeps the binary file, and keeps it while the binary is kept; `uninstall --purge` removes `~/.config/crosstalk/` with the state directory, prints `unpair this host on: <aliases>`, and refuses while `gateway.lock` is held unless the holder is CrossTalk's own unit about to be stopped. `remote status` reads `running` only when the listener on `bind:port` presents this host's certificate; otherwise a held lock reads `service running, port not bound`.

The C7 name lock (§3), the journal rules and the admission limits (§5) apply per agent record. `crosstalk capture` (§6) is a diagnostic subcommand. Harness SessionStart hooks are v1.1 (§12).

Per-agent state in a shared process: each agent's A2A listener binds `127.0.0.1:0` and is tied to exactly one agent record; the actual URL is published in the descriptor and not persisted across reconnects (a reconnect may pick another port and updates the descriptor). Task stores, journals, credentials and ownership locks are per agent and never merge because two agents share a process. Creation is lazy and atomic: concurrent first calls for one session reuse one listener, journal and lock. Closing one agent leaves sibling listeners intact; `release` changes role only. `list_agents` distinguishes a live shim process from an agent it currently serves (`crosstalk: true` means served now).

## 11. Tests that gate "done"

1. Claude→Claude via shim: send, native SendMessage reply is journaled `bounced` at the receiving shim with a bounce injected into the replying session; the `reply` tool then routes to the sender with in_reply_to resolved.
2. Claude→Codex verified immediate while Codex is mid-turn: named tool output is consumed at the next model boundary; no peer `userMessage` item is created.
3. Claude→Codex while idle, verified immediate sender: new turn starts with tool output. Deferred or unverified input: no-wake append succeeds (`queued`), idle remains idle, and a later independently started turn consumes the data.
4. Codex→Claude via shim uds: arrives mid-turn with reconstructed envelope and verified sender.
5. Native reply bounce (ADR 0009): with one or two outstanding asks from the same sender, a native Claude reply is journaled `bounced`, nothing is forwarded, the asks stay `working` with their routes open, and the session receives a bounce listing both message ids; a `reply` naming one id completes that ask only; a native answer to the bounce itself is bounced again, not delivered.
6. Duplicate delivery (same message_id twice): second returns the prior state and causes no second injection.
7. hop_chain loop (A2A ingress only, R15): A→B→A in a chain supplied by an A2A client is rejected at the repeat, and a chain longer than 32 is rejected. Native frames carry no forwardable chain (ADR 0009), so there is no native repeat or overflow case.
8. Policy: a non-owner primary sends command to a subagent → rejected, never injected.
9. Unverified uds sender (random pid) sends command → rejected without injection; inform accepted and labelled unverified; to an idle Codex session it is appended without wake, never `turn/start`ed.
10. Harness restart: after both harnesses exit and are relaunched with the same session names (herdr restore or by hand), both agents re-register under the same names and test 2 passes again.
11. Reply without a registry record: a shim with no `~/.claude/sessions` entry injects into Claude with `from="uds:<uds_path>"`; Claude's native SendMessage reply connects to that path and authenticates with the shim's CrossTalk-issued key; the shim's receiver journals it `bounced` and injects a bounce, and nothing is forwarded.

12. Binding ambiguity (F2): two codex panes sharing a cwd, plus a third conversation on a different server; each agent receives only into its bound thread; a tool call with no binding evidence returns `unbound`.
13. Relay routing (F4): A→B via B's shim, B replies natively and the frame is journaled `bounced` with a bounce listing both open message ids, then B answers with the `reply` tool naming A's message; the reply reaches A, with a third agent C also having messaged B in the same window; C never receives A's reply and vice versa.
14. Forged attributes (F7): envelope claiming from="<owner>" over an unverified transport is rejected for command and reconstructed from the verified identity for inform; a command nested inside envelope body text does not become a command.
15. Replacement vs old exit (F8): a second process binding an agent name while the first holds it → the second does not register under it; kill the first, let the second register, then let a stale first-process exit path run → the second's descriptor survives.
16. Injector failure branches (F10), run in `go test` against `adapter.Fake`: idle→active race during tool-output turn/start (joins active work), review/compact refusal → one no-wake append, malformed success → unknown, definite refusal or pre-send failure → unreachable, disconnect right after acceptance → state unknown and no resend, reconnect → no duplicate work. Concurrent duplicate ingress (same message_id on both ingresses at once) → exactly one injection.

17. A2A conformance matrix, pinned `a2a-go` release with its helloworld client configured with the peer token: (a) the Agent Card validates with the SDK resolver, including `version`, `securityRequirements` and the JSON-RPC interface entry; (b) plain-text `SendMessage` without `returnImmediately` returns `result.task` only in a terminal state, `completed` with `metadata.crosstalk.completion: "delivered"`, and the text appears inside the session; (c) a default-wait `SendMessage` whose dispatch ends `unknown` (fake adapter) never returns `completed`; (d) `GetTask` after `SendMessage` returns shows `completed`; (e) an `ask` sent with `returnImmediately: true` returns `submitted` at once and reaches `completed` with the reply as its final message after the session calls `reply`; (f) `CancelTask` on an unclaimed `submitted` task cancels it, and on a claimed or terminal task returns `TaskNotCancelable`; (g) `SendMessage` with a terminal `taskId` → `UnsupportedOperation`, with an unknown `taskId` → `TaskNotFound`; (h) `ListTasks` returns only the caller's tasks; (i) a request with no or a wrong bearer token is refused; (j) each unimplemented method (streaming, push notifications, extended card) returns the error the pinned spec mandates. Status: the official SDK sample-client run has not been executed; this gate is open and untested.
18. Codex endpoint pinning: a thread on a non-default app-server (`codex --remote <other>`) receives both immediate (tool output) and next_turn (raw history append) delivery from the same shim, and nothing reaches the default daemon.
19. Idle Claude: a shim injects `inform` into an idle Claude session (no active turn, no pending tool call); Claude starts a turn and the model sees the envelope within 30 s. Repeated with an unverified sender, recording whether it wakes the session (CQ3).
20. Restart dedupe: restart shim B; the sender retries the same message_id → returns the prior state, zero injections. A journal with a partial trailing line replays without it; an unresolved `dispatching` record is reconciled only with positive evidence, otherwise stays `unknown` (including raw Codex appends absent from client history), and is never re-injected.
21. Restart reply routing (CQ7, real process restart, not an in-process reload): kill shim B between injection into Claude B and Claude B's native reply, with Claude B still running; a native reply fails to connect until Claude B reconnects the MCP server; after the reconnect and B's next bound call, a native reply to the pre-crash `uds_path` is journaled `bounced` and a bounce is injected (it is not routed), and the `reply` tool for the pre-crash message routes to A. Kill and restart both shim B and Claude B → the pending reply is `unreachable`, never injected into the new conversation. Restart shim B between `reply` completing the task and forwarding to A → the reply reaches A exactly once. Restart under the same name bound to a different conversation → no pending work or reply is injected into the new conversation; those records are `unreachable` in `receive_message`.
22. Cancel race (C5): with `adapter.Fake` blocking between dequeue and the harness write, `CancelTask` issued in that window either succeeds with zero fake writes or returns `TaskNotCancelable` with exactly one write; never canceled and written.
23. Continuation and authority (C3, V3): registered principal X sends `SendMessage(taskId=T)` for a task created by Y → `TaskNotFound`, nothing injected; Y's continuation of T is policy-checked again (a `command` continuation to a subagent Y does not own → rejected, not injected); an `ask` from a non-owner to a subagent is accepted with inform permissions and gains no command authority; a `command` from a registered primary to another primary gains no approval or setting the receiving session did not already have (a gated action still prompts).
24. Concurrent startup (C7): two processes binding one name at once → exactly one registers; a stale cleanup by the loser racing the winner's publication never removes the winner's descriptor.
25. Admission (C9): stall a receiver (fake adapter blocking) and exceed each limit → deterministic `rejected` before acceptance; every previously accepted message is still accounted for in the journal and `receive_message`.
26. Installation: plain `claude` and plain `codex` with the one MCP entry (§9); `list_agents` lists both plus a third session with no CrossTalk; a message to the third lands; the third cannot send.
27. Codex pooling: a pooled Codex MCP connection serving two threads routes each `tools/call` by `_meta.threadId` and never cross-binds; a call with no `_meta.threadId` is served `list_agents` only.
28. Claim/release: a primary claims an unclaimed agent and the target receives an injected `inform` and lists as `subagent` of the owner; a non-owner `release` is rejected; an agent claiming or releasing itself is rejected; claiming an already-claimed agent is rejected; the claim ends when the target's session ends.

29. Naming (CQ8): four Codex threads whose ids all begin `01a1a3` in one cwd, no harness names → four distinct fallback names; a fifth agent whose chosen name is held → suffix extended, never the same conflicting fallback.
30. Rename (CQ9): rename a harness session while it has an outstanding ask delivered to it and an owner claim on it; a native reply to the pre-rename envelope address still reaches the shim and is journaled `bounced`, and the `reply` tool for the pre-rename message still routes; the claim still binds; after a disconnect and reconnect the same `agent_id` resumes the same journal; a message to the old alias is `unknown`/`no_such_agent`.
31. Endpoint ownership (CQ10): stored history on endpoint A and live thread on endpoint B → bind B; the same thread loaded on two endpoints → `ambiguous_endpoint`, no binding.
32. `/clear` (§3 Superseded sessions): a new Claude session on the same process and shim keeps the name with no notice; `list_agents` shows it once and not the old session; delivery by name reaches it; before its first call it is a native row and its name routes natively. A dead holder in another process never gets a "live" notice and yields the name within the sweep. A live holder still forces the suffix. Pooled Codex threads never evict each other. `/resume` of the old session takes the free name and its old ask is still answerable; resume in another process with the name held live gets the suffix, the "live" notice and its journal.
33. Native rejection hints (§8): `native_inform_only` carries a hint that is true for reachable and unreachable targets; an ambiguous name is `ambiguous_name` with an agent_id hint.

34. Pinning and unpair on open connections (v0.2.0, ADR 0021): an unpinned client is refused before any HTTP, TLS 1.2 and session resumption are refused, and a request on a connection that was open when its peer was removed gets 403 and reaches no handler. Pinned by `TestUnpinnedClientRefusedBeforeHTTP`, `TestTLS12Refused`, `TestNoSessionResumption`, `TestUnpairRefusesOpenConnection` and `TestAgentsEndpointRequiresPinnedPeer`.
35. Pairing is single use: a token redeems once, also under concurrent redeems and across processes; a wrong secret, an expired token or a pairing attempt beyond the rate limit writes nothing, and the pairing binds the joining host's key. Pinned by `TestPairSingleUse`, `TestPairConcurrentRedeem`, `TestPairConcurrentRedeemAcrossProcesses`, `TestPairWrongSecret`, `TestPairExpired`, `TestPairRateLimited` and `TestPairBindsClientKey`.
36. Host-scoped sender identity (ADR 0022): a remote sender's key is `remote:<fingerprint>/<agent_id>`, so the same agent_id from two hosts never shares a route, receipt or journal record. Pinned by `TestRemoteSenderKeyIsHostScoped`, `TestRemoteSenderIdentityShape`, `TestRemoteRouteRecordsHostScopedKey` and `TestRemoteReceiptUsesHostScopedKey`.
37. Two-host inform: a message sent to `name@alias` through two real gateways is injected once in the target session. Pinned by `TestTwoHostInform`; the same path over Docker containers in CI is spike 17 (`docs/spikes/17-ci-two-host.md`). Not run on two real machines.
38. Remote discovery and its bound: `list_agents` shows a paired host's agents live, a native session there as `messageable: false`, an unpaired host not at all, a down gateway as no rows with the local rows unchanged, and a slow host costs at most 1.5 s. Pinned by `TestListAgentsShowsPairedHostAgents`, `TestRemoteNativeListedUnmessageable`, `TestUnpairedHostNotListed`, `TestListAgentsGatewayDown` and `TestListAgentsTimeoutBound`.

Cross-host reply across a disconnect: a `reply` returns `remote_reply_pending` while the asker's gateway is down, is retried with backoff and after a restart, resends the same message so it is never shown twice, and ends `unreachable` after the ask's deadline. Pinned by `TestTwoHostReplyAcrossDisconnect`, `TestRemoteReplyPendingWhileGatewayDown`, `TestRemoteReplyResumesAfterRestart`, `TestRemoteReplyRetryBackoff`, `TestRemoteReplyRetryEndsUnreachable` and `TestRemoteReplyResponseDroppedDedupes`.

The login unit (ADR 0021): `remote enable` twice writes an identical file once, refuses a foreign or edited unit with nothing written, `disable` and `uninstall` remove only a unit whose hash matches `unit_sha256`, the Linger hint is printed and never run, and K8 reports a changed unit. ## 12. Open questions

- Codex `_meta.threadId` / `_meta.sessionId` on `tools/call` is release-source evidence (rust-v0.166.0 `codex-rs/core/src/mcp_tool_call.rs`), not a documented API: captured live by spike 9 before the Codex adapter, verified live on 0.166.0 (docs/spikes/09-codex-binding/): a model-issued tools/call carried `_meta.threadId` and `_meta.sessionId`; `mcpServer/tool/call {threadId}` reached the per-thread instance before first use and during an active turn, without `experimentalApi`. Re-verify per Codex release.
- R2 (Claude-visible shim record): closed, out of v1 (§3).
- Claude acknowledgement (resolved by spike 10, R18): Claude 2.1.317 sends no acknowledgement of an injected line. The Claude adapter treats the connection staying open past the short grace period as `accepted`; an ack line decides the state if one is ever sent; EOF, reset or any other reply is `unknown`. This is a weaker operational definition than a Claude acknowledgement and is delivery evidence only. Our own uds ingress replies `{"type":"ack","message_id","state","reason"}` on the authenticated shape (a).
- uds ingress key location (S1): `<uds_path minus .sock>.key`, 0600, created on first start. Resolved (spike 10, ADR 0009): a native Claude `SendMessage` to a `uds:` address writes the verified single-line native frame without the key; the shim journals it `bounced` and injects a bounce (test 11), so Claude never needs the key, which authenticates only CrossTalk's own shape (a) clients.
- Agent Card exposure (S4): decided by ADR 0011. The card has no cwd, every `Access-Control-*` header and `Vary` is stripped, OPTIONS answers 204, a non-loopback Host gets 421; residual name, role and harness exposure to same-machine browsers is accepted.
- Native targets (S5): a session without CrossTalk accepts `inform` only; `ask` or `command` to it is `rejected/native_inform_only`; to a target that resolves to nothing it is `rejected/no_such_agent` (no deadline timer, no expiry notice, no mailbox entry). A message injected into such a session carries the sender's agent_id (`from-agent-id` in the Claude envelope, `from_agent_id` in the Codex rendering) so its model can `send_message` that exact agent_id (ADR 0023). After an inform returns `accepted` or `queued`, the sender's shim also appends a signed entry to the pre-bind store (`~/.local/state/crosstalk/prebind/<target agent_id>.jsonl`, §5 Journal), and the one-way hint says the recipient can answer with `reply` once it has used CrossTalk; if that write fails or hits a cap the result keeps the old hint and adds one saying a `reply` may not find the message (ADR 0026). The recipient's shim replays the store when it binds, so `reply` on the delivered message id succeeds once, until `InformRouteTTL` (1 h) after the sender's delivery time; `reply` drains the store again on a miss, and again when the message was imported but its route was never opened. A message that was not kept, was dropped, or is older than an hour still returns `no_such_message` with the pre-bind hint.
- Reply-route lifetime (S1): decided by ADR 0010. Ask routes close with their task; inform routes expire after `InformRouteTTL` (1 h) on the journal clock and are swept on admission; the bounce lists every open ask then the ten newest informs with a count.
- Packaging (2026-11-04): decided by ADR 0013. The product stays a pure MCP server; one plugin tree for Claude Code and Codex carries a skill and the server entry, never a second code path. Hooks remain v1.1 (below). Live clean-account runs are not done (`docs/plans/agent-plugins-clean-run.md`).
- ADR 0008 narrowing note (R16): today the core selects one `NativeIngress` implementation for all agents. A second native ingress protocol, a deferred-delivery (mailbox) capability and installation hooks are outside the current `harness.Harness` interface, so "one package plus one line" holds only within the supported extension points. `Render` is exposed on the interface, but each injector builds its own payload; it is not the canonical path of the shared dispatch. Revisit when a second native protocol is chosen.
- Next harnesses (spike 11): OpenCode, Gemini CLI with Qwen Code sharing a package, Pi; ACP is a launch mode, not an attach surface, so no generic ACP harness.
- A2A auth beyond the same-user bearer/peer-token scheme. Cross-host auth is built for v0.2.0 (pinned mTLS plus host-scoped sender keys, §5, ADR 0021 and 0022); anything beyond that is open.
- v1.1, harness SessionStart hooks (F9): Codex `SessionStart` fires on startup, resume, clear, compact and fork, not once per process. A hook must inform the existing shim, never start one; it must be idempotent per (thread id, agent instance): a fork gets its own binding and never inherits the parent's, and the hook's `session_id` → app-server thread id mapping is verified first. SessionStart may fire before the model-tool connection is ready; SessionEnd may lag pane closure.
- v1.1, turn-boundary task completion (V6, C8): once harness idle-status observation is verified and bound to the turn that consumed the injection.
