# CrossTalk design, draft 1.7 (2026-11-03)

Status: draft under operator review (greenfield gate step 4). Decisions are recorded in `docs/decisions/` (ADR 0001–0006; ADR 0005 is superseded by ADR 0006). Evidence for every "verified" claim is indexed in `docs/spikes/README.md` (spikes 1–4, cross-harness round trip; captured frames to be committed before `go mod init`).

Terms: harness = the agent CLI (Claude Code, Codex). Session = one running harness conversation (a Claude Code session or a Codex thread). Agent = the registered identity of a session. session_ref = the Claude session id or the Codex thread id. Shim = the `crosstalk mcp` process described in §2. herdr = the operator's terminal pane manager and session restorer. cc-socks = Claude Code's per-session socket directory (`/tmp/cc-socks/<pid>.sock`), which Claude scans for peers. A2A = Agent-to-Agent protocol. MCP = Model Context Protocol. uds = unix domain socket. pid = process id. F1–F18 = Codex design-review findings, summarized in the Changelog (1.1 and 1.3 entries). V1–V29, C1–C10, CQ1–CQ4 = council verdict items, listed in the 1.4 entry. R2 = the question whether Claude sessions accept a shim-published `~/.claude/sessions` record as a native peer (§3, §12). Spike n = a pre-build experiment indexed in `docs/spikes/README.md`.

## 1. Goal and non-goals

Goal: any agent on this machine can send a message to any other by name and the receiver gets it inside its running session, without a human and without screen scraping, across harnesses.

Non-goals for v1: spawning or wrapping agent processes (ADR 0006; spawning stays with herdr and a separate delegate tool), cross-machine messaging, kind=control (stop/shutdown), isolation against hostile same-user processes.

## 2. Components

| Component | Count | Owns |
|---|---|---|
| Shim | one per harness MCP connection | the `crosstalk mcp` process the harness starts for its MCP connection; serves one or more agents. Per agent: MCP tools to its model, A2A server+client, cc-socks-compatible uds ingress, injector into its harness, registration, journal (§5) |
| Directory | none as a process | discovery = every harness session from the harness's own registry, merged with the shims' descriptor directory (ADR 0003) |
| herdr | optional | panes and restore only; no v1 code uses it (§10) |

The shim is a Go binary (ADR 0002), one package with a harness adapter inside it. CrossTalk spawns and wraps nothing (ADR 0006): `crosstalk mcp` is installed once per harness as an ordinary MCP server entry (§9). Adding a harness = one adapter: `register()`, `inject(message, delivery)`, `status()`. `adapter.Fake` (scriptable `status()` and `inject()` outcomes: success, errors, state races, disconnects, blocking) is a v1 deliverable; the receiver chain and the injector failure branches are tested against it in `go test`.

## 3. Registration and discovery

Identity is bound per request, never per process (ADR 0006). For every `tools/call` the shim resolves the calling session:
- Claude: the shim's parent pid is the Claude session pid; `~/.claude/sessions/<ppid>.json` gives `pid`, `name`, `cwd`, `status`, `messagingSocketPath`.
- Codex: `params._meta.threadId`, which Codex attaches to every `tools/call` (required; `session_ref` is the thread id). `params._meta.sessionId` is present on model-issued calls and absent on app-server `mcpServer/tool/call` frames (spike 9); it is optional supplementary metadata and never a fallback identity. Evidence (rust-v0.166.0 `codex-rs/core/src/mcp_tool_call.rs`; spike 9). MCP `initialize` carries no identity, the environment carries none, and cwd is not discriminating.
- Neither → `unbound`: only `list_agents` is served.

One process may serve several Codex threads (connection pooling, MCP protocol 2026-07-28). The shim keeps one agent record per (harness, session_ref) and binds nothing to the first caller; every call is routed by its own evidence.

Agent identity (CQ9): `agent_id` = first 16 hex of sha256(`<harness>:<session_ref>`), stable for the session's lifetime and independent of any display name. Storage, sockets, locks, journals, task stores, claims and reply-routing records key on `agent_id`; the agent name is a lookup alias. On the first bound call for an agent the shim writes `~/.local/state/crosstalk/agents/<agent_id>.json`:

```
{ "agent_id": "<16 hex>", "name": "<agent name>", "harness": "claude|codex", "role": "primary|subagent", "owner": "<name>|null",
  "pid": <shim pid>, "harness_pid": <Claude session pid (= shim ppid) | null for Codex>, "harness_started_at": "...|null",
  "cwd": "...", "session_ref": "<claude session id | codex thread id>",
  "a2a_url": "http://127.0.0.1:<port>", "uds_path": "~/.local/state/crosstalk/sock/<agent_id>.sock",
  "instance_id": "<uuidv7, new per agent registration>", "harness_endpoint": "<codex app-server endpoint | claude socket path | null>",
  "harness_version": "<Codex app-server version from initialize | null>",
  "credential_ref": "<path to 0600 file holding this agent's A2A bearer token>",
  "installed": true, "started_at": "...", "protocol": 1 }
```

`started_at` and `harness_started_at` are the kernel process start times of the shim and of the Claude session process. `role` defaults to `primary`; `role` and `owner` change only through `claim`/`release` (§7).

Name (CQ8, CQ9): the harness session name (Claude `name`; Codex thread `name`) if free, else `<harness>-<cwd basename>-<first 8 hex of agent_id>`; if that is also taken, extend the suffix two hex at a time until free (agent_id is a hash of the whole session_ref, so identifiers that share a long common prefix, as the four spike-9 threads `01a1a3…` do, still get distinct suffixes). A name is held under its own `flock` for the registration's lifetime. A harness rename does not change `agent_id`, sockets, journals, claims or routing records; it updates the alias only: the new name is taken under its lock, the descriptor's `name` is rewritten, the old alias is released. `send_message(to)` resolves aliases at send time; a message to a released alias is `unknown` with reason `no_such_agent`. Owner references in claims are by `agent_id`.

Binding (F2): `harness_endpoint` + `session_ref` bind an agent to exactly one conversation on exactly one server. A shim never selects a conversation by name, cwd, activity or "most recent". Codex endpoint (CQ10): the shim queries each known endpoint (the managed control socket `~/.codex/app-server-control/app-server-control.sock` plus any `harness_endpoint` recorded in a descriptor); an endpoint counts as hosting the thread only if `thread/loaded/list` includes it (`thread/read` alone may return stored history from a server that does not host the live conversation). Exactly one host → bind it as `harness_endpoint`. More than one → binding stays unresolved, inbound is `unreachable` with reason `ambiguous_endpoint`, journaled; never the first response. None → sending works, inbound is `unreachable`. `canAcceptDirectInput` is a separate per-delivery condition, not a binding input.

Credentials (F5): the bearer token lives only in the file `credential_ref` points to (0600). Descriptors and `list_agents` output never contain it; logs redact it.

Publish order and ownership (F8, C7): there are two locks: the agent record lock `~/.local/state/crosstalk/agents/<agent_id>.lock` (one live registration per session) and the alias lock `~/.local/state/crosstalk/names/<name>.lock` (one live holder per name), both taken first and held for the registration's lifetime; descriptor check, publication, replacement and cleanup happen only under it. A held lock means a live owner: the newcomer registers under its fallback name (§3 Name rule) and its model is told so in the tool result; a later harness rename to a free name re-registers. Order, on the first bound call: take the lock, replay the journal (§5), bind uds + A2A listener, confirm the harness binding, then write the descriptor atomically (temp + rename). On exit the shim removes each descriptor only under its lock and only if the file's `instance_id` is its own. Readers treat a descriptor as stale when the pid is dead or the pid is alive but the process start time does not match `started_at` (pid reuse).

`uds_path` is agent_id-stable (CQ7, CQ9): it survives a shim restart, so a reply address embedded in an envelope before the restart still reaches the agent after it.

Discovery: `list_agents` enumerates every Claude session from `~/.claude/sessions/*.json` and every loaded thread from `thread/loaded/list` + `thread/read` on each known app-server, merged with the descriptor directory (dead or reused pids pruned). Each row: `name`, `harness`, `cwd`, `status`, `crosstalk: bool` (a shim has bound this session), `reachable: bool` (Claude: its socket exists; Codex: status loaded and `canAcceptDirectInput`), plus `role` and `owner` for bound agents. A session without CrossTalk is listed and messageable (inform only, injected natively by the sender's shim) but has no A2A card and cannot send. herdr is not consulted.

Claude-visible registration (R2) is out of v1 (1.6): a reply address travels in the envelope (`from="uds:<uds_path>"`), so Claude needs no `~/.claude/sessions` record for a shim to receive native replies, and a pooled Codex shim has no single pid to publish under. Claude sessions see other agents through `list_agents`.

Harness-native registries the shim reads, never writes: `~/.claude/sessions/<pid>.json` (Claude: self-binding through the parent pid, discovery and status; never sender identity on the uds ingress), app-server `thread/loaded/list` + `thread/read` (Codex).

## 4. Message

Internal normalized record (F12). This is what the receiver chain and the mailbox hold; it is not a wire format. On the A2A ingress it is decoded from the pinned SDK's `Message` (standard `messageId`, `role`, `parts`, `contextId`, `taskId`); CrossTalk fields travel in `metadata` under the `crosstalk.*` namespace and are all optional. A plain text `SendMessage` with no metadata is valid and normalizes to `kind: inform`, `delivery: immediate`.

```
{ "message_id": "<uuidv7>", "in_reply_to": "<message_id>|null", "context_id": "<conversation>", "task_id": "<id>|null",
  "from": "<agent name>", "to": "<agent name>", "kind": "inform|command|ask", "delivery": "immediate|next_turn",
  "deadline_seconds": <int, ask only, 0 = none>,
  "hop_chain": ["<24-hex>", ...], "sent_at": "...", "parts": [{"type":"text","text":"..."}] }
```

`ask` is reply-required inform: it has `inform`'s permissions (§7) and opens a reply obligation keyed by its `message_id`. `kind` is typed only as `metadata.crosstalk.kind` on an authenticated A2A request; absent = `inform`. The uds ingress has no kind encoding (§5). `delivery` drives the Codex adapter and travels as A2A metadata; it is a no-op on the Claude adapter, where the socket decides mid-turn vs next turn.

hop_chain uses Claude's convention (24-hex sha256 prefixes, max 32) so loop guard survives a Claude hop. Forwarding keeps message_id and appends a hop; a reply gets a new message_id and sets in_reply_to.

## 5. Ingress contracts (both feed one receiver)

A2A ingress (required for v1; operator requirement 2026-11-03). Each session is a first-class A2A agent served by its shim.

- Pinned target (F11, V22, C1): **A2A protocol 1.0, JSON-RPC binding**, implemented with the official Go SDK module `github.com/a2aproject/a2a-go/v2` at one tagged release in `go.mod`; the tag and the matching `examples/helloworld/client` revision used as conformance client are recorded here at pin time (candidate: v2.7.0, reported by review, unverified). Method names are the 1.x ones: `SendMessage`, `GetTask`, `CancelTask`, `ListTasks`. Streaming (`SendStreamingMessage`), push notifications and the extended card are not implemented and not advertised; each such method returns the error the pinned spec mandates for a disabled capability, fixed per method in the test 17 matrix.
- Agent Card (F13, C1, V29, CQ2): served at `/.well-known/agent-card.json`, built with the SDK's card type and validated by its resolver. Fields: `name` (agent name), `description` ("<harness> session, role <role>. Task completion is delivery evidence, not model-read or work-done."), `version` (crosstalk build version), `supportedInterfaces` (one entry: the JSON-RPC URL, JSON-RPC protocol binding, protocol version 1.0), `defaultInputModes`/`defaultOutputModes` = `["text/plain"]`, `capabilities` all false, `securitySchemes` = one HTTP bearer scheme and `securityRequirements` requiring it, `skills` = `inform`, `command`, `ask` each with id, name, description, tags and an example. Role, harness and cwd go under `metadata.crosstalk` only.
- Wire handling (F12, C1): the SDK decodes the request; the receiver chain works on the normalized record; the response is the SDK's `SendMessageResponse` (`result.task` or `result.message`) inside the JSON-RPC success envelope, or a protocol error (`InvalidParams`, `TaskNotFound`, `TaskNotCancelable`, `UnsupportedOperation`), never the internal `{message_id, state}` pair. The A2A encoder and the Codex app-server encoder are separate code: Codex omits the JSON-RPC version header on the wire, A2A includes it.
- Task mapping (F14, V6, C8, CQ2): every accepted `SendMessage` creates a server-owned task, `submitted` on acceptance and `working` once dispatch is claimed (`dispatching` in the journal: an attempt is claimed, not delivered). `inform`/`command`: `completed` only on evidenced harness acceptance: Claude = the harness acknowledges the socket write; Codex = a success response to `turn/steer` or `turn/start`, or `codex queue` success for queued delivery. `failed` on `unreachable` or `rejected`. A bare write with no harness acknowledgement, or any ambiguous failure, is `unknown` and leaves the task `working` until reconciled (journal, below). `ask`: `completed` only when the receiving session's `reply` for it is correlated (§8); the reply text is the task's final `Message`; `failed` with `metadata.crosstalk.reason: "deadline"` when `deadline_seconds` elapses first. Every task carries `metadata.crosstalk.completion: "delivered"`: completion is delivery evidence, never model-read or work-done.
- Waiting (C1, CQ1): default `SendMessage` (`configuration.returnImmediately` false or absent) returns only when the task reaches a terminal or interrupted state. There is no server-timeout return of a non-terminal task; a timeout or dropped connection never manufactures completion. `returnImmediately: true` returns the `submitted` task at once; CrossTalk's own `send_message` and `ask` always set it.
- Continuation (C3, C1): a `SendMessage` with `taskId` is allowed only from the principal that created the task. The appended message runs the full receiver chain as a new message with the same `context_id`, policy included; it never inherits the original's kind or authorization. Unknown or another principal's `taskId` → `TaskNotFound`; terminal `taskId` → `UnsupportedOperation`.
- Cancellation (F15, C5, CQ4): the dispatch claim and `CancelTask` are serialized by one per-agent lock, and the claim is durably journaled under that lock before any harness write. `CancelTask` succeeds only while the task is `submitted` with no claim: the message is removed from the mailbox and the task is `canceled`, so a successful cancel means no harness write happened. Claimed (`dispatching`, `working`) or terminal → `TaskNotCancelable`; the shim never interrupts a harness turn. A `codex queue` handoff is an external side effect and is past the claim. `GetTask`, `CancelTask`, `ListTasks` (own tasks only) and continuation are allowed only to the principal that created the task.
- Authentication (F16, V14): bearer tokens are private files, never in descriptors. Each shim holds its own token (0600, path in `credential_ref`) and a per-user shared **peer token** at `~/.local/state/crosstalk/peer.token` (0600, created on first start). Any client presenting the peer token is the principal `local-user`; a shim presenting its own token is the principal of its registered agent. Own-token verification: receiver B resolves the claimed sender's descriptor by `name`, reads the file at its `credential_ref`, and compares in constant time. This proves the sender can read a 0600 file of this user, the same strength as the peer token, accepted under the §1 non-goal; the registered-agent principal gives attribution and policy, not isolation. All holders of the peer token are one principal, `local-user`: "own tasks" means every task that principal created, with no isolation between individual non-shim clients. The token is owner-readable only and never appears in descriptors, `list_agents` output, Agent Cards or logs. A principal without agent registration may send `inform` and `ask` and read, list or cancel its own tasks; `command` requires a registered agent whose role/owner satisfies §7. The conformance test configures the sample client with the peer token. The peer token has one creator, the A2A server's `Listen` (an exclusive create, idempotent across shims); each agent's own token is created by the shim's A2A wiring at `~/.local/state/crosstalk/tokens/<agent_id>.token` before `Listen`, and a receiver accepts a sender's own token only when its descriptor's `credential_ref` is exactly that path for its agent_id.

uds ingress (V1, V2, V4, V18, C3): Claude's two-line protocol on `uds_path`: `{"type":"auth","token":T}` then `{"type":"user","message":{"role":"user","content":C}}`. T is the content of the shim's own `~/.claude/sessions/<shim pid>.<sha256>.key` when the Claude-visible record is published (§3), else a CrossTalk-issued 0600 key; a connection is accepted in one of two shapes: (a) the auth line with a valid T, then the user line; or (b) a single `type:"user"` first line with no auth line, accepted only when the peer pid maps to exactly one registered descriptor with a matching start time (a verified sender), else closed with no state (a session without CrossTalk cannot send, test 26). Claude 2.1.317's own SendMessage to a `uds:` address writes exactly one line such as `{"msgV":1,"msg_id":"…","type":"user","message":{"role":"user","content":"<cross-session-message from=… hop-chain=… from-name=… from-mode=…>…</cross-session-message>"},"priority":"next","from":"uds:…"}` and sends no auth line, and Claude's own session socket performs no token check; unknown top-level fields are ignored, `msg_id` and `from` are kept as display-only. C may be a `<cross-session-message ...>` envelope. Sender identity: at `accept()` the shim reads the peer pid with `getsockopt(SOL_LOCAL, LOCAL_PEERPID)` (macOS, `golang.org/x/sys/unix`; `SO_PEERCRED` on Linux), reads that pid's process start time, and maps it to a descriptor whose `pid` (start time = `started_at`) or `harness_pid` (start time = `harness_started_at`) matches. `~/.claude/sessions/<pid>.json` is never consulted for sender identity. Unmapped pid, start-time mismatch, or a pid matching more than one descriptor (a pooled shim) → unverified. A pooled pid is never resolved by picking the first matching descriptor or by trusting `from-name`; it stays unverified. The native shape (b) gets no ack and no bytes back, only EOF once the receiver returns, on success and on every rejection: Claude's sender treats any reply bytes as an error and only EOF as success (live, 2.1.317). The per-agent receiving socket identifies the recipient, never the sender. The uds ingress exists for native Claude senders; shim-to-shim traffic uses A2A, where identity is the per-agent bearer token and pooling is irrelevant. Since T is readable only by this user, an unverified sender is a same-user process not matched to a registered agent, consistent with the §1 non-goal. The uds ingress has no command encoding: a frame is `inform`; a frame that requests `command` (a `kind` envelope attribute or a `crosstalk.kind` field) is `rejected` without injection, whatever its sender.

Two identities per inbound message (F4): the **transport peer** (the process on the socket: a Claude session pid, another shim, or unknown) and the **original sender** (the registered agent the message is from). On the A2A ingress both are the sending shim's agent. On the uds ingress the transport peer is verified from the socket; the original sender equals it when the peer is a registered agent, and is otherwise unverified. A relay never upgrades the original sender's identity beyond what the transport proves.

Native replies through a shim (F4, C8): when shim B injects a message from A into Claude session B, the envelope's `from` is B's own uds socket and `from-name` is A. The envelope also carries `message-id`, so the `reply` tool can name the inbound message. Claude's native SendMessage reply therefore arrives at shim B, which must route it to A. Routing uses only shim B's journaled record of that delivery, keyed by (B's session, the delivered message_id, A); it never derives the destination from the reply text. Outstanding deliveries are counted per message, not per sender: when more than one delivery into the same Claude session is outstanding (two asks from one sender count as two), a native reply with no correlating content is delivered to the shim's mailbox for that session as `in_reply_to: null`, state `uncorrelated`, never guessed (F6). A route is consumed by a native reply or by the `reply` tool naming its message id.

Native-message normalization (F6): a frame arriving over uds without our metadata is assigned a fresh message_id by the receiving shim, `in_reply_to` stays null unless the correlation above is unambiguous, and it is exempt from the message_id dedupe (identical repeated text is legal). Identified messages: authenticate first, then look up (sender, message_id); acceptance is recorded atomically with the journal write so two concurrent duplicates cannot both inject; a retry returns the prior state.

Journal (V8, C6, CQ4): one append-only JSONL file per agent at `~/.local/state/crosstalk/journal/<agent_id>.jsonl`, written and fsynced before an ingress or tool acknowledges. Records: dedupe keys (verified sender, message_id, state); tasks (task_id, creating principal, kind, state); dispatch claims (message_id, `dispatching`); dispatch outcomes; reply-routing records (session, delivered message_id, original sender); reply-delivery obligations (§8 `reply`); claims on this agent (owner, claimed/released, §7). Every record carries the binding it was accepted under (`instance_id`, `harness_endpoint`, `session_ref`). Replay on agent registration, under the name lock: acknowledged acceptance is always recoverable; a partial trailing line is discarded; an unresolved `dispatching` record is never re-injected but reconciled (Codex: `thread/turns/list` on the recorded endpoint and thread, for message-specific evidence; Claude: no evidence is available, so it stays `unknown`); unresolved records surface through `receive_message`. Records bound to a different (`harness_endpoint`, `session_ref`) than the agent's current binding are never injected or routed into the new conversation; they become `unreachable` and surface through `receive_message`. Records older than 24h are truncated, except unresolved ones (`submitted`, `dispatching`, `unknown`, open asks, undelivered replies), which are kept until resolved.

Admission (C9): limits, checked in the policy step before acceptance: message size (default 64 KiB of text parts), pending tasks per agent (default 256), open asks per agent (default 32), concurrent default-wait `SendMessage` calls (default 64). Exceeding a limit returns `rejected` (A2A: a JSON-RPC error, no task created) and never evicts accepted work or its dedupe record.

Receiver, both ingresses, in order: authenticate → dedupe on (verified sender, message_id) for identified messages → hop_chain check (repeat or >32 → reject) → policy (§7, including admission) → inject (§6). Returns the internal `{message_id, state}`; each ingress encodes that into its own wire response (A2A: Task/error; uds: Claude's native ack).

## 6. Injector per harness

Claude adapter: `inject` = connect to the session's `/tmp/cc-socks/<pid>.sock`, auth with the token from `~/.claude/sessions/<pid>.*.key`, send one `user` line whose content is the reconstructed envelope `<cross-session-message from="uds:<shim uds_path>" from-name="<from>">\n<escaped body>\n</cross-session-message>`. State `accepted` only when the harness acknowledges the write; no acknowledgement → `unknown` (CQ2). Mid-turn delivery between tool calls is verified (spike 1). Next-turn delivery into an idle session is unverified and gated by spike 6 and test 19. `delivery` is a no-op on this adapter.

Codex adapter: `inject(delivery)` over the endpoint recorded in `harness_endpoint` at registration (default: the daemon uds `~/.codex/app-server-control/app-server-control.sock`; websocket framing, JSON-RPC 2.0 without the version header, `initialize` first):
- handshake: `initialize {clientInfo, capabilities:{experimentalApi:false}}`, await the result, then send the `initialized` notification, before any other call (F3). At `register()` the shim records the result's server version as `harness_version`, refuses to bind a Codex agent on a version outside the tested set (today: 0.166) and logs a warning on an untested minor (V11).
- immediate: `thread/turns/list` → the turn with status `inProgress` (the `Turn` type has no kind field, so steerability cannot be read from the list) → `turn/steer {threadId, expectedTurnId, input:[{type:"text", text}]}`. Error handling (F1): `activeTurnNotSteerable {turnKind: review|compact}` → fall back to next_turn; expectedTurnId mismatch → refresh the turn list once, retry once, then next_turn. The wire placement of these errors (JSON-RPC error.data vs result) comes from `crosstalk capture` fixtures, not assumption. No active turn → `turn/start {threadId, input}` preserving the thread's existing settings (no model/cwd/approval overrides), for verified senders only. Verified: steer renders mid-turn in a TUI-attached thread (spike 2).
- unverified senders (V12, CQ3): scheduling rule only: an unverified sender's message is steered into an active turn or queued (next_turn), never sent as `turn/start`. This is not a no-wake guarantee and does not prevent idle work or spending; whether `codex queue` and the Claude socket wake an idle session with unverified input is measured by tests 3, 9 and 19.
- next_turn: v1 uses the `codex queue --remote <harness_endpoint> --thread <threadId> --message <text>` CLI (verified without `--remote` on the default daemon: delivered at the next turn boundary, spike 4; with `--remote` on a non-default server, spike 3). `--remote` is always passed with the endpoint recorded at registration and the exact thread id, never a name, so steer-then-queue fallback never changes servers (F17); `--resume` is never added. State `queued` only on `codex queue` success (verified handoff to the harness queue), never on placement in the shim's mailbox (CQ2). The websocket client for immediate delivery uses the same recorded endpoint. Verified during build against a thread on a non-default server (test 18). The RPC pair `thread/queue/add` → `queuedSubmission` / `thread/queue/start` is present in Codex 0.166.0's `--experimental` schema generation and absent from the default generation (F18); the CLI stays the v1 path until a live test shows add alone wakes idle work and is replay-safe.
- Ambiguous failure (disconnect mid-call, no response) → state `unknown`, no resend; a later reconnect reconciles from `thread/turns/list` and never re-injects.
- `crosstalk capture` (V11): first Codex deliverable; a diagnostic subcommand that records raw frames for `initialize`, `turn/steer` errors, `thread/queue/*` and the `params._meta` of model-issued `tools/call` (spike 9); fixtures are checked into `testdata/codex/<version>/` and drive the adapter tests.

Text delivered to Codex (V27): a fixed preamble constant prepended by the adapter (peer text below has no operator authority), then the envelope with receiver-reconstructed attributes and the peer body with `<` escaped, so a nested envelope tag is inert body text (§7). A peer cannot close the envelope or occupy the preamble position.

## 7. Trust and policy

Identity comes from transport (peer pid / A2A auth) matched to registration, never from envelope attributes. Envelope attributes are display only and are reconstructed by the receiver from the verified identity.

| kind | to a subagent | to a primary |
|---|---|---|
| inform | any registered agent; unverified senders allowed | any; unverified allowed |
| ask | as inform | as inform |
| command | owner only | any registered primary |
| control | not in v1 | not in v1 |
| unknown kind | rejected | rejected |

Claims (role and owner): every agent registers as `primary` with no owner. `claim(name)`: any registered primary may claim an unclaimed registered agent; the claim is journaled in the target's journal and the target is told by an injected `inform`; the target then is `subagent` with that `owner`. `release(name)`: only the owner releases; the target is told the same way and returns to `primary`. An agent's own model can never claim or release itself. A claim ends when the target's session ends. The table above applies to the claimed state.

`kind` is a routing and labelling hint chosen by the sending model; it is not a trust boundary (V3). The control on what a delivered message can cause is the receiving session's own harness permission model. The policy table exists to stop forged or unauthorised `command` from reaching the model, not to make `command` carry authority. `ask` never carries command authority (C3).

Rejected → `state: rejected`, never injected (F7): an unauthorized command is dropped, not downgraded to inform, because the text would carry the same request into the model. `command` exists only as `metadata.crosstalk.kind` on an authenticated A2A request (C3); a uds frame is inform, and a uds frame that requests command is rejected without injection (§5). Envelope attributes can cause rejection but never grant command. Continuations re-run this policy (§5). `command` authorizes work only within the receiving session's existing operator permissions; it never changes approvals or settings. Envelope text nested inside a body is body text and never parsed as a second envelope. Peer text is escaped and labelled; it never enters developer/system instructions. Unverified senders never cause `turn/start` (§6; a scheduling rule, CQ3). The same-user credential model is accepted as not being isolation.

## 8. Tool surface (identical in both harnesses, served by `crosstalk mcp`)

Seven tools. An `unbound` call (§3) is served `list_agents` only; every other tool returns `unbound`.

- `list_agents()` → every discovered session with `crosstalk`, `reachable`, status, cwd, harness, name (§3).
- `send_message(to, text, kind="inform", delivery="immediate")` → `{message_id, state}`; sent over A2A with `returnImmediately: true`. Since the far side answers `submitted` at once, the sending shim polls `GetTask` for up to 2 s for a delivery state past `submitted`/`dispatching` and returns it; if none arrives it returns `unknown` with reason `pending` and keeps the far task id on the journal's outbound record.
- `reply(message_id, text)` → `{message_id, state}`. `message_id` is the inbound message being answered; the destination comes from the stored original, not the model. In order: journals the reply-delivery obligation (CQ4); completes the ask's A2A task, if any, with the reply text as its final `Message`; when the asker is a shim-served agent, sends the reply to the asker's shim as a new inform with `in_reply_to` = `message_id`, which injects it into the asker's bound session; then acknowledges the caller. The reply has its own message_id, so a retry, a repeated `GetTask` or a sender reconnect is deduped and never injected twice (C4). An undelivered obligation is retried from the journal after a restart.
- `ask(to, text, deadline_seconds=0)` → `{message_id, state}` at once, where `message_id` is the ask's id; no blocking; the answer arrives through `reply` above. `deadline_seconds` (V15): when it elapses with no `reply`, the task becomes `failed` with `metadata.crosstalk.reason: "deadline"` and the asker's session receives an inbound `inform` with `in_reply_to` set saying the ask expired; already-injected work is not stopped. 0 = no deadline.
- `receive_message(after?, limit?)` → mailbox pull (V23, C9). Every accepted message is journaled. By default it returns only entries in state `unreachable`, `unknown` or `uncorrelated` (not `accepted` or `queued`, both of which the harness itself delivers), so a model never receives a delivered message twice; `after` paginates the full journal. Each entry carries message_id, task_id, from, state, shim instance_id and bound session_ref; credentials redacted.
- `claim(name)` → `{name, owner}`: the caller, a registered primary, becomes the owner of the unclaimed registered agent `name` (§7). Across shims the claim is an A2A `SendMessage` carrying `metadata.crosstalk.claim: {owner, claimed}` with the owner's own token; it creates no task, never reaches the receiver chain, and is refused unless `owner` is the authenticated sender.
- `release(name)` → `{name}`: the owner ends its claim on `name` (§7).

States (V16): `accepted` = injected immediately with harness evidence (Claude socket write acknowledged, Codex `turn/steer` or `turn/start` success); `queued` = verified handoff to the harness's next-turn queue (`codex queue` success); `rejected` = policy, auth, admission, hop or kind failure, never injected; `unreachable` = harness binding not loaded, systemError, or a journal record bound to another conversation; `unknown` = ambiguous failure after a dispatch claim, no resend. None implies read or completed. `uncorrelated` is a mailbox-entry state only, never a `send_message` return; `dispatching` is a journal/task-internal state only.

## 9. Lifecycle

Install (ADR 0006), once per harness, no wrapper and no per-session configuration:
- Claude: `claude mcp add --scope user crosstalk -- crosstalk mcp`
- Codex: in `~/.codex/config.toml`, `[mcp_servers.crosstalk]` with `command = "crosstalk"` and `args = ["mcp"]`

Start: the harness connects the MCP server; that `crosstalk mcp` process is the shim. Protocol initialization creates no agent. Per-agent state (descriptor, agent_id-stable uds `~/.local/state/crosstalk/sock/<agent_id>.sock`, journal, A2A listener on its own loopback port) is created lazily on the first bound call for that agent, in the §3 order. `not_ready` applies only between a tool call and completion of its agent's binding, which should be immediate. A call whose name lock is held by a live owner is not served under that name.

Exit: when stdio closes the shim removes its own-instance descriptors and sockets under their locks; journals are kept. A session whose shim has exited is still listed and reachable natively for inbound (§3), but native replies to its name-stable `uds_path` fail to connect until the harness reconnects the MCP server and the next bound call re-registers the agent, which resumes its journal. Compaction and tool reconnection therefore re-register under the same name and `session_ref`; a fork is a new `session_ref` and never inherits the parent's binding. Records bound to an old `session_ref` are `unreachable` (§5).

The C7 name lock (§3), the journal rules and the admission limits (§5) apply per agent record. `crosstalk capture` (§6) is a diagnostic subcommand. Harness SessionStart hooks are v1.1 (§12).

Per-agent state in a shared process: each agent's A2A listener binds `127.0.0.1:0` and is tied to exactly one agent record; the actual URL is published in the descriptor and not persisted across reconnects (a reconnect may pick another port and updates the descriptor). Task stores, journals, credentials and ownership locks are per agent and never merge because two agents share a process. Creation is lazy and atomic: concurrent first calls for one session reuse one listener, journal and lock. Closing one agent leaves sibling listeners intact; `release` changes role only. `list_agents` distinguishes a live shim process from an agent it currently serves (`crosstalk: true` means served now).

## 11. Tests that gate "done"

1. Claude→Claude via shim: send, native SendMessage reply, in_reply_to resolved. 
2. Claude→Codex immediate while Codex is mid-turn: rendered before the turn ends.
3. Claude→Codex while idle, verified sender: new turn starts. Unverified sender to the same idle session: `codex queue` handoff succeeds (`queued`), and whether the queued input wakes the idle session is recorded (CQ3).
4. Codex→Claude via shim uds: arrives mid-turn with reconstructed envelope and verified sender.
5. Two outstanding asks between the same pair: replies made with the `reply` tool both correlate by message_id; a native Claude reply with two outstanding originals lands `uncorrelated` in the mailbox, and the sender of each ask can retrieve it with `receive_message`.
6. Duplicate delivery (same message_id twice): second returns the prior state and causes no second injection.
7. hop_chain loop: A→B→A with forwarding is rejected at the repeat.
8. Policy: a non-owner primary sends command to a subagent → rejected, never injected.
9. Unverified uds sender (random pid) sends command → rejected without injection; inform accepted and labelled unverified; to an idle Codex session it is queued, never `turn/start`ed, and whether it wakes the session is recorded (CQ3).
10. Harness restart: after both harnesses exit and are relaunched with the same session names (herdr restore or by hand), both agents re-register under the same names and test 2 passes again.
11. Reply without a registry record: a shim with no `~/.claude/sessions` entry injects into Claude with `from="uds:<uds_path>"`; Claude's native SendMessage reply connects to that path and authenticates with the shim's CrossTalk-issued key; the reply reaches the shim's receiver.

12. Binding ambiguity (F2): two codex panes sharing a cwd, plus a third conversation on a different server; each agent receives only into its bound thread; a tool call with no binding evidence returns `unbound`.
13. Relay routing (F4): A→B via B's shim, B replies natively, reply reaches A, with a third agent C also having messaged B in the same window; C never receives A's reply and vice versa.
14. Forged attributes (F7): envelope claiming from="<owner>" over an unverified transport is rejected for command and reconstructed from the verified identity for inform; a command nested inside envelope body text does not become a command.
15. Replacement vs old exit (F8): a second process binding an agent name while the first holds it → the second does not register under it; kill the first, let the second register, then let a stale first-process exit path run → the second's descriptor survives.
16. Injector failure branches (F10), run in `go test` against `adapter.Fake`: active→idle race during steer (state mismatch → refresh once → queue), idle→active race during turn/start (joins the new turn, acceptable for immediate only), review/compact turn → activeTurnNotSteerable → queue, disconnect right after acceptance → state unknown and no resend, reconnect → no duplicate work. Concurrent duplicate ingress (same message_id on both ingresses at once) → exactly one injection.

17. A2A conformance matrix, pinned `a2a-go` release with its helloworld client configured with the peer token: (a) the Agent Card validates with the SDK resolver, including `version`, `securityRequirements` and the JSON-RPC interface entry; (b) plain-text `SendMessage` without `returnImmediately` returns `result.task` only in a terminal state, `completed` with `metadata.crosstalk.completion: "delivered"`, and the text appears inside the session; (c) a default-wait `SendMessage` whose dispatch ends `unknown` (fake adapter) never returns `completed`; (d) `GetTask` after `SendMessage` returns shows `completed`; (e) an `ask` sent with `returnImmediately: true` returns `submitted` at once and reaches `completed` with the reply as its final message after the session calls `reply`; (f) `CancelTask` on an unclaimed `submitted` task cancels it, and on a claimed or terminal task returns `TaskNotCancelable`; (g) `SendMessage` with a terminal `taskId` → `UnsupportedOperation`, with an unknown `taskId` → `TaskNotFound`; (h) `ListTasks` returns only the caller's tasks; (i) a request with no or a wrong bearer token is refused; (j) each unimplemented method (streaming, push notifications, extended card) returns the error the pinned spec mandates.
18. Codex endpoint pinning: a thread on a non-default app-server (`codex --remote <other>`) receives both immediate (steer) and next_turn (queue) delivery from the same shim, and nothing reaches the default daemon.
19. Idle Claude: a shim injects `inform` into an idle Claude session (no active turn, no pending tool call); Claude starts a turn and the model sees the envelope within 30 s. Repeated with an unverified sender, recording whether it wakes the session (CQ3).
20. Restart dedupe: restart shim B; the sender retries the same message_id → returns the prior state, zero injections. A journal with a partial trailing line replays without it; an unresolved `dispatching` record is reconciled (Codex) or stays `unknown` (Claude) and is never re-injected.
21. Restart reply routing (CQ7, real process restart, not an in-process reload): kill shim B between injection into Claude B and Claude B's native reply, with Claude B still running; the native reply fails to connect until Claude B reconnects the MCP server; after the reconnect and B's next bound call, a native reply to the pre-crash `uds_path` routes to A. Kill and restart both shim B and Claude B → the pending reply is `unreachable`, never injected into the new conversation. Restart shim B between `reply` completing the task and forwarding to A → the reply reaches A exactly once. Restart under the same name bound to a different conversation → no pending work or reply is injected into the new conversation; those records are `unreachable` in `receive_message`.
22. Cancel race (C5): with `adapter.Fake` blocking between dequeue and the harness write, `CancelTask` issued in that window either succeeds with zero fake writes or returns `TaskNotCancelable` with exactly one write; never canceled and written.
23. Continuation and authority (C3, V3): registered principal X sends `SendMessage(taskId=T)` for a task created by Y → `TaskNotFound`, nothing injected; Y's continuation of T is policy-checked again (a `command` continuation to a subagent Y does not own → rejected, not injected); an `ask` from a non-owner to a subagent is accepted with inform permissions and gains no command authority; a `command` from a registered primary to another primary gains no approval or setting the receiving session did not already have (a gated action still prompts).
24. Concurrent startup (C7): two processes binding one name at once → exactly one registers; a stale cleanup by the loser racing the winner's publication never removes the winner's descriptor.
25. Admission (C9): stall a receiver (fake adapter blocking) and exceed each limit → deterministic `rejected` before acceptance; every previously accepted message is still accounted for in the journal and `receive_message`.
26. Installation: plain `claude` and plain `codex` with the one MCP entry (§9); `list_agents` lists both plus a third session with no CrossTalk; a message to the third lands; the third cannot send.
27. Codex pooling: a pooled Codex MCP connection serving two threads routes each `tools/call` by `_meta.threadId` and never cross-binds; a call with no `_meta.threadId` is served `list_agents` only.
28. Claim/release: a primary claims an unclaimed agent and the target receives an injected `inform` and lists as `subagent` of the owner; a non-owner `release` is rejected; an agent claiming or releasing itself is rejected; claiming an already-claimed agent is rejected; the claim ends when the target's session ends.

29. Naming (CQ8): four Codex threads whose ids all begin `01a1a3` in one cwd, no harness names → four distinct fallback names; a fifth agent whose chosen name is held → suffix extended, never the same conflicting fallback.
30. Rename (CQ9): rename a harness session while it has an outstanding ask delivered to it and an owner claim on it; the native reply to the pre-rename envelope address still routes; the claim still binds; after a disconnect and reconnect the same `agent_id` resumes the same journal; a message to the old alias is `unknown`/`no_such_agent`.
31. Endpoint ownership (CQ10): stored history on endpoint A and live thread on endpoint B → bind B; the same thread loaded on two endpoints → `ambiguous_endpoint`, no binding.

## 12. Open questions

- Codex `_meta.threadId` / `_meta.sessionId` on `tools/call` is release-source evidence (rust-v0.166.0 `codex-rs/core/src/mcp_tool_call.rs`), not a documented API: captured live by spike 9 before the Codex adapter, verified live on 0.166.0 (docs/spikes/09-codex-binding/): a model-issued tools/call carried `_meta.threadId` and `_meta.sessionId`; `mcpServer/tool/call {threadId}` reached the per-thread instance before first use and during an active turn, without `experimentalApi`. Re-verify per Codex release.
- R2 (Claude-visible shim record): closed, out of v1 (§3).
- Claude native ack format (S1, 2026-11-03): the Claude adapter returns `accepted` only on an `{"type":"ack"}` reply line from the session socket; any other reply, close or timeout is `unknown`. What Claude 2.1.317 actually writes back is unverified until test 4 or 19 runs live. Our own uds ingress replies `{"type":"ack","message_id","state","reason"}`.
- uds ingress key location (S1): `<uds_path minus .sock>.key`, 0600, created on first start. How a native Claude `SendMessage` to a `uds:` address finds this key is open (test 11).
- A2A task persistence (S4, 2026-11-03): tasks live in memory only; a shim restart loses `GetTask` for earlier tasks (the receiver's journal dedupe still returns the prior state), and an `unknown` task has no reconcile hook yet. Add journal-backed tasks or a `Resolve(messageID, state)` before v1.
- Agent Card exposure (S4): the SDK card handler sends `Access-Control-Allow-Origin: *`, so any page in a browser on this machine can read name, role, harness and cwd from a listening shim. Decide whether to strip CORS or trim the card before v1.
- Ask deadlines across restart (S5): deadline timers are in memory and do not survive a shim restart; the asker never gets the expiry notice. Replay should re-arm them.
- Native targets (S5): a session without CrossTalk accepts `inform` only; `ask` or `command` to it is `rejected/native_inform_only`.
- Reply-route lifetime (S1): every delivery from a registered sender opens a reply route, including plain informs that may never be answered, so later native replies into that session land `uncorrelated`. Ruling needed: open routes only for `ask`, or expire inform routes.
- A2A auth beyond the same-user bearer/peer-token scheme (needed for cross-machine, out of v1).
- v1.1, harness SessionStart hooks (F9): Codex `SessionStart` fires on startup, resume, clear, compact and fork, not once per process. A hook must inform the existing shim, never start one; it must be idempotent per (thread id, agent instance): a fork gets its own binding and never inherits the parent's, and the hook's `session_id` → app-server thread id mapping is verified first. SessionStart may fire before the model-tool connection is ready; SessionEnd may lag pane closure.
- v1.1, turn-boundary task completion (V6, C8): once harness idle-status observation is verified and bound to the turn that consumed the injection.
