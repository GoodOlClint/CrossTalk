# ADR 0016 — `crosstalk install` registers the MCP server at the installed binary's absolute path; the plugin carries only the skill

- **Status:** Provisional (operator 2026-11-05)
- **Date:** 2026-11-05
- **Deciders:** operator (rulings 2026-11-05) + Claude (Opus 5.5)
- **Context source:** `docs/plans/release-0.1.3.md` section (a); ADR 0013 (rejected `crosstalk install`, plugin-supplied server); `docs/setup.md` ENOENT row; the 2026-11-04 clean-account run and a Linux test VM run

## Context

ADR 0013 ships the MCP server inside the plugin with the bare command `crosstalk`, so the binary must be on the PATH the harness sees. A harness started outside a shell does not see shell-profile PATH entries, which fails as `ENOENT` on Claude (ADR 0013 "Not yet run live", PATH row; setup.md troubleshooting table). Setup is eight manual steps, two of them easy to get wrong: removing a manual MCP entry (two shims, `agent_held`) and removing a Codex `[mcp_servers.crosstalk]` table without its `tools.*` sub-tables (Codex refuses the whole config with `invalid transport`). The operator reversed ADR 0013's rejection of `crosstalk install` for 0.1.3 and ruled that MCP registration uses the absolute installed path.

Terms: shim = the `crosstalk mcp` process a harness starts. Allow rule = an entry in Claude Code's `permissions.allow` list in `~/.claude/settings.json`. Bin dir = the directory install copies the binary into.

## Decision

- `crosstalk install [claude|codex]`, `crosstalk uninstall [claude|codex]` and `crosstalk reinstall [claude|codex]` exist. With no harness name, the command finds each of `claude` and `codex` on the PATH and acts on each one found; with a name, it acts on that one.
- Install copies the running binary (`os.Executable`, symlinks resolved) to a stable bin dir, default `~/.local/bin` (no admin rights), by writing a temporary file in that directory and renaming it over the target, so a running shim keeps its old file and is never killed or blocked. When the running binary already is the target, the copy is skipped. A binary from `go install` installs the same way. A linked Homebrew keg binary is not copied: install uses `<prefix>/bin/crosstalk` ([ADR 0018](0018-homebrew-tap-formula-and-crosstalk-install-registers-the-homebrew-path.md)).
- The MCP server is registered by install, not by the plugin, with the command set to the absolute path of the installed binary: Claude through `claude mcp add --scope user crosstalk -- <path> mcp`; Codex as a `[mcp_servers.crosstalk]` table in `~/.codex/config.toml` with `default_tools_approval_mode = "approve"`. An existing entry keeps its approval mode, environment and tool sub-tables; its command becomes the installed path and its args `["mcp"]`. The server key stays `crosstalk` (the Codex delivery namespace in `internal/harness/codex/appserver/methods.go:203` depends on it).
- Install runs each harness's own plugin commands (`claude plugin install`, `codex plugin marketplace add` and `codex plugin add`), so the skill arrives in the same run. The plugin manifests carry the skill only: no `mcpServers` key, no `claude.mcp.json` or `codex.mcp.json`.
- Install adds the Claude allow rule `mcp__crosstalk__*` and ports every rule naming the old `mcp__plugin_crosstalk_crosstalk__` prefix, in every permission source it can find (user, project and local settings of projects listed in `~/.claude.json`, managed settings), so no restriction is lost: user and local files are rewritten; a checked-in project or managed file with an old-prefix deny or ask stops the install before any registration, naming the file, until the user ports it.
- Adding the bin dir to the PATH is optional and only serves a person typing `crosstalk send`; the harnesses no longer need it.
- Each step is shown and confirmed on a terminal; `--yes` runs every required step without asking (the PATH step needs `--path` too); without a terminal and without `--yes`, install changes nothing and exits non-zero. Every changed config file is written atomically after a backup copy next to it.
- Install ends with checks, each reported pass or fail: the plugin is installed at the binary's version and ships no server; exactly one `crosstalk` MCP server is registered per harness; `codex mcp list` succeeds (Codex's own parser) and no `[mcp_servers.crosstalk.tools.*]` table is left without its parent; the allow rule is present and no deny rule names the prefix; the registered command is the installed path and is executable; a live MCP handshake with the registered command lists the seven tools and reports the binary's version. Install prints that running sessions keep their old server until restarted.
- Uninstall reverses each step, including deleting the binary (the earlier "uninstall leaves the binary" default is void) once no harness registration still names it, and never a recognized Homebrew keg binary (`<prefix>/bin/crosstalk` resolving into `<prefix>/Cellar/crosstalk/<version>/bin/`; it points to `brew uninstall crosstalk`). A plain copy placed in the prefix with `--bin-dir` is deleted like any other. It keeps the plugin marketplaces and leaves `~/.local/state/crosstalk` (journals, tokens) in place; `--purge` deletes the state dir (operator ruling Q5) only when no harness reports CrossTalk setup (`SetUp`; an unreadable config counts as set up) and no running shim holds an agent, which stops the purge with an error. A harness that is an uninstall target is rechecked only for config its own uninstall leaves (`harness.Leftover`). Claude's `SetUp` counts the user-scope entry, every project's local-scope entry in `~/.claude.json`, the `.mcp.json` of each project listed there, and the installed-plugin registry; `Registered` needs one of those entries to run the installed binary (the command is looked up on PATH if it is a bare name, then symlink-resolved (dot components in filesystem order) before the compare; exact string compare if either side will not resolve; a relative command with a path separator counts as running the binary, because Claude's launch directory is not recorded), and so does the binary step's `harness.Leftover` recheck of an uninstall target; the state step's recheck counts an entry naming any binary, and the kept message names the scope and the command. Because `SetUp` counts local- and project-scope entries, `install --check` with no names runs Claude's checks when only such an entry exists. A project key that is not an absolute path (`""`) is not scanned for `.mcp.json`. A project that `~/.claude.json` does not list is not scanned (known gap).
- Both marketplace files pin the plugin to a release tag (`git-subdir` source on this repo, `path` `plugins/crosstalk`, `ref` `vX.Y.Z`), so a plugin install or update gets the tagged plugin, not `main` (operator ruling Q11; both CLIs confirmed live). The `ref` moves in its own commit after the release tag exists, never to an rc tag.
- Reinstall re-applies every step with no uninstall first (Q3). Claude registration is user scope by default (Q9).
- Harness-specific install code lives in the harness package behind an optional `harness.Installer` interface (`Found`, `InstallSteps`, `UninstallSteps`, `Checks`, plus `SetUp`, which guards `--purge` (0.1.4), and `Registered`, which the plan did not list: it reads a harness's config files without its CLI, so uninstall keeps the shared binary and state while any other harness's config still runs the binary or cannot be read; as `NativeIngress` and `Supersession` are optional), per ADR 0008; the binary copy, PATH step, prompts and check runner live in `cmd/crosstalk`. `harness.InstallEnv` carries, besides `Bin`, `Version`, `Home` and `Run` (the plan's shape), three fields the plan did not list: `Handshake` (the K6 MCP client lives in `cmd/crosstalk`, while each adapter knows its registered command, args and env), `SkipRulePort` (a Claude-only flag the Claude step needs) and `Marketplace` (what `plugin marketplace add` receives, `GoodOlClint/CrossTalk` unless `CROSSTALK_MARKETPLACE` names another source, so an rc rehearsal can point at a scratch marketplace whose `ref` is the rc tag). `harness.ReplaceFile` is the one backup-then-atomic-write used by both adapters and the PATH step; it backs a file up once per run, so the backup is the file before this run.
- As built, install and reinstall run the same steps: every step is idempotent, so install re-applies each step too (`marketplace add` on both CLIs accepts a marketplace already present, verified live). Claude registration is `claude mcp add --scope user crosstalk [-e K=V ...] -- <path> mcp`: the name precedes `-e`, since `-e` placed before the name takes the name as an env pair (verified live). K2 on Claude reads the installed plugin's `mcpServers` from `claude plugin list --json` and the local-scope entries in `~/.claude.json`, not `claude mcp list`, which starts every configured server to report its health. Codex `plugin marketplace upgrade` is skipped for a local marketplace, which Codex refuses to upgrade.

## Rejected alternatives

- **Keep the plugin-supplied server with a bare command (ADR 0013).** The PATH failure stays, and setup stays eight manual steps.
- **`${HOME}/.local/bin/crosstalk` in the static plugin manifests.** Claude expands environment variables in plugin MCP config; Codex support is unknown, and any bin dir other than the default breaks.
- **Ship the binary in the plugin repo.** About 16 MB per version in git history.
- **README-first: the plugin README says "install this plugin, then run `crosstalk install`", and install does only settings and MCP.** Leaves the plugin and the MCP registration in two steps the user can do out of order (plugin 0.1.2 still carries a server, so a 0.1.2 plugin plus an install-registered server gives two shims). Kept as the fallback text in the plugin README; the operator ruled for install running the plugin commands (plan Q1).
- **A TOML library for the Codex config.** Round-tripping drops comments and reorders a file Codex itself rewrites; a bounded line edit plus `codex mcp list` as the parser check is enough.

## Consequences

- Reverses two parts of ADR 0013: its rejection of `crosstalk install` and its plugin-supplied server. ADR 0013 is edited in place (AGENTS.md: all ADRs are provisional and edited in place).
- Claude tool names change prefix from `mcp__plugin_crosstalk_crosstalk__` to `mcp__crosstalk__`. Allow rules, eval graders under `plugins/crosstalk/evals/` and any other repo or settings file naming the old prefix need the new one.
- Moving the binary needs `crosstalk reinstall`.
- `docs/setup.md` shrinks to: download, verify, `./crosstalk install`.
- With the plugin pinned to a tag, plugin changes on `main` reach no user until the `ref` moves. The server removal, the installer and the version bump still merge in one PR. A 0.1.2 user who updates the plugin after the `ref` moves to `v0.1.3` has no server until they run the 0.1.3 binary's `crosstalk install` (release notes and plugin README say so). An old plugin next to an install-registered server gives two shims; the install's "exactly one server" check catches it.
