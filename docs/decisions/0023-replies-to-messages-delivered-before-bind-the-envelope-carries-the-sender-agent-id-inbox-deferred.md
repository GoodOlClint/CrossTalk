# ADR 0023 — Replies to messages delivered before bind: the envelope carries the sender's agent_id, the pre-bind inbox is deferred

- **Status:** Provisional (operator 2026-11-07)
- **Date:** 2026-11-07
- **Deciders:** operator + Claude (Opus 5.5) + Codex review
- **Context source:** issue #41 (dogfood); PR #57 (pre-bind hint); triage of #41 part (b); operator ruling 2026-11-07 on the first draft of this ADR (PR #58): take the middle path, defer the inbox

## Context

A session with no CrossTalk binding can still receive an `inform`: when the target resolves to a native session and to no descriptor, the sender's shim injects the message through its own harness adapter (`internal/shim/send.go`, the `tgt.Native` branch of `deliver`; design §12 S5). `ask` and `command` to such a target are `rejected/native_inform_only`, so only informs take this path. The receiver's shim does not exist yet, or has not registered the agent, so the receiver's journal never gets the dedupe record or the reply route for that message. The message still shows in the receiver's conversation with a `message-id`. When the receiver binds and calls `reply` with that id, `inbound` finds no dedupe record and `reply` returns `no_such_message`; since PR #57 the hint says the message may predate the binding. The model then has to `send_message` the sender by name, or tries Claude's native SendMessage, which ADR 0009 bounces.

The sender already knows everything the receiver's journal would have held: the message, its own agent_id, the target's binding (harness, session_ref) and therefore the target's future agent_id (`identity.AgentID(harness, session_ref)`, a fixed hash), and the delivery state. What is missing is a way to hand this to the receiver's shim that does not let any process write reply routes into an agent's journal.

The first draft of this ADR (PR #58) designed a pre-bind inbox that would make such a message answerable with `reply`. Two Codex review rounds brought it to a sound contract, but at a size out of proportion to the case: a MAC'd file written by one agent into another's state, a lock, crash recovery of a claimed file, collision rules, per-target and directory caps, and an accepted forgery surface. The operator ruled for a smaller step.

## Decision

1. When the sender's shim injects a message into a session with no CrossTalk binding (the `tgt.Native` branch of `deliver`), the delivered message carries the sender's agent_id next to its name: in the Claude envelope as a `from-agent-id` attribute, in the Codex rendering as a `from_agent_id` field. Messages delivered through a receiver's own ingress are unchanged; they already have a reply route.
2. The pre-bind hint that `reply` returns since PR #57 tells the model to `send_message` to the sender's agent_id shown in that message (`from-agent-id` in Claude, `from_agent_id` in Codex), not to the sender's name; the hint reads the same in both harnesses.
3. Nothing else changes: no inbox, no new journal or route records, no routing change, no change to the MCP tool surface (design §8). `reply` to such a message still returns `no_such_message`.

Accepted loss: the answer reaches the sender as a new inform, not threaded as a reply to its message; the sender's ask machinery is not involved anyway, because only informs reach an unbound session.

## Rejected alternatives

- **Build the pre-bind inbox now.** Deferred, not rejected; see Deferred below.
- **Keep the hint as merged in PR #57 (name only).** `send_message` by name works only while the name still resolves to the same session; names alias live descriptors and a successor or a rename takes the name over (#54). The agent_id is the fixed hash of the binding, so it reaches the session that sent the message or nothing. (Opus review point: the middle path removes the name-drift argument, which was the main case against hint-only.)
- **Bind the receiver on delivery.** The sender's shim cannot create or register the receiver's shim; identity comes from the receiving harness per request (ADR 0006), and a binding made by another process would be the cross-agent identity claim ADR 0004 forbids.

## Consequences

- The agent_id in the envelope is display text, like `from-name`: it is written by the sending shim, and the receiver's shim never reads it as sender identity (ADR 0004). A model that uses it only addresses a `send_message`; the receiving shim authenticates that send from transport as for any other.
- A sender that is gone by the time the answer is sent makes the `send_message` return `no_such_agent`, as for a name; it never reaches a different session.
- Design §5 (native delivery) and §12 S5 gain the attribute and the hint wording in the implementing commit.
- Tests that gate this ADR: a native delivery's Claude envelope and Codex rendering carry the sender's agent_id; a delivery through a receiver's own ingress does not; the pre-bind hint points at the sender's agent_id in the message.
- Implementation commits carry `Provisional-ADR: 0023`.

## Deferred: pre-bind inbox

Kept as written after two Codex review rounds (the second with no findings), so a later session can build it without redoing the design.

- **Why deferred:** heavy for a rare case that has a working fallback (rule 2 of the Decision above), and it adds a forgery surface (a same-user process holding an agent's token can open a reply route in another agent's journal).
- **Revisit when:** dogfood shows messages to unbound sessions are frequent, or the lost threading of their answers hurts.

### Design

1. **Write.** After a native inject of an inform returns `accepted` or `queued`, the sender's shim appends one entry to the pre-bind inbox of the target, keyed by the target's agent_id. Nothing is written for any other state, for a registered target (it gets the message through A2A and journals it itself) or for an inject that failed. An entry is one JSON line: `v`, the target's `agent_id`, `harness` and `session_ref`, the sender's `agent_id`, the full message (as journaled on the sender's outbound record), `delivered_at` (sender clock), the delivery state, and `mac`. A failed inbox write does not change the send result's state; the result adds a hint that a `reply` from that session may not find the message.
2. **Authenticate.** `mac` is HMAC-SHA256 over the entry's other fields in canonical order, keyed with the sender's own agent token (`~/.local/state/crosstalk/tokens/<sender agent_id>.token`, design §5). The receiver verifies it by reading the token at exactly that path for the claimed sender agent_id, as A2A own-token verification does, and compares in constant time. It also requires that the inbox file is a regular file (opened with no-follow), mode 0600, owned by the current uid, inside a 0700 directory, and that the entry's target agent_id, harness and session_ref equal the receiver's current binding. A failed check drops the entry and logs the reason; it is never replayed. The token never leaves its file; the entry carries only the MAC. This gives the entry the same strength as the sender's A2A bearer credential: it proves the writer can read that agent's 0600 token, and no more (ADR 0004 Consequences, design §1 non-goal).
3. **Replay.** When an agent registers, after journal replay and under the same name lock, its shim drains its inbox. A drain takes the inbox lock (rule 6), first finishes a claimed file left by an earlier drain (`<agent_id>.claimed`, one fixed name per target), then renames `<agent_id>.jsonl` to that claimed name and releases the lock; writers only append while they hold the lock, so no writer holds the claimed inode open. It verifies each entry, applies the collision rule (rule 4), and imports each remaining entry by writing to its own journal (fsynced) the two effects of a native delivery: a dedupe record with the message, the sender key = the sender's agent_id and the entry's delivery state, and an inform route record whose open time is `min(delivered_at, now)` on the journal clock. Import is idempotent per (sender, message_id): a retry writes whichever of the two records is missing and nothing else, and never writes an open record for a route that has a closed record, so a crash after the rename, after the dedupe append or after the route append completes on the next drain without reopening an answered or expired route. Only after every entry is imported or dropped does it delete the claimed file. Replay never injects, never re-delivers and never answers: the message already reached the conversation. `openRoute` today stamps the route with the current clock (`internal/receiver/receiver.go`), so the import needs a receiver entry point that journals the supplied open time and keeps it as `OpenedAt`, on first open and on restart replay alike.
4. **Late entries and collisions.** A sender that resolved the target as native just before it bound can write an entry after the receiver's drain. So when `reply` finds no dedupe record for a message id, it drains the inbox once more before it returns `no_such_message`. No timer and no file watch. A message id names one message and `reply` looks it up by id alone, so: entries in one drain that share a message id with different senders are all dropped; and an entry whose message id already has a dedupe record from a different sender is dropped and, if that record was itself imported from the inbox (never one from the receiver's own ingress), its route is journaled closed. Collisions therefore fail closed to the pre-bind hint, but only for routes still open and only when the second entry is drained at all: once a route is answered, a later conflicting entry changes nothing, and `reply` never drains for an id it already finds.
5. **Route lifetime and dedupe (ADR 0010).** A replayed route is an ordinary inform route: it expires `InformRouteTTL` (1 h) after the sender's delivery time, not after the bind, so waiting for a bind never extends it; and it takes one reply, through the existing obligation path, with `already_replied` and the byte-identical retry rules unchanged. An entry older than `InformRouteTTL` at replay is deleted without replay; `reply` to it gives the pre-bind hint as today. There is no ask on this path, so no ask deadline runs while a message waits for the bind. If native targets ever accept `ask`, that needs its own decision on whether the deadline runs on the asker's clock while the target is unbound.
6. **Storage and caps.** `~/.local/state/crosstalk/inbox/<target agent_id>.jsonl`, directory 0700, files 0600 opened with no-follow. One inbox lock, an advisory lock on `inbox/.lock` that is created once and never deleted, serializes every append, claim (rename) and sweep; a writer opens the data file only after it holds the lock and closes it before it releases it. Per target at most 64 entries and 4 MiB; for the whole directory at most 256 data and claimed files and 16 MiB, claimed files included. A write that would pass any cap is skipped (the newest message loses its route, older ones keep theirs) with the send hint from rule 1. Every write and every drain sweeps the directory under the lock: a data file whose last write is older than `InformRouteTTL` holds only useless entries and is deleted; a claimed file is left to its owner's next drain unless it is also older than `InformRouteTTL`. The sweep reads at most the capped file count. Age is enforced only when some shim writes or drains; with no activity the inbox holds at most the directory cap until the next one. The inbox is never read by `list_agents`, `receive_message` or the bounce.
7. **Remote (ADRs 0021, 0022, planned for v0.2.0).** Only a local shim's own native send path writes the inbox. The gateway never writes it, and a remote sender cannot reach a native session (`rejected/remote_native_unsupported`), so no cross-host message takes this path. Replay accepts only an entry whose sender agent_id has a local token file; an entry naming a `remote:` key or `local-user` is dropped. `crosstalk send` and other peer-token clients never reach native sessions, so they write no entries.

### Its rejected alternatives

- **The receiver pulls from the sender's journal on bind.** The receiver does not know which agents sent to it, so every bind would scan every journal for outbound records addressed `<harness>:<session_ref>`. It reads another agent's private journal, couples the receiver to the sender's record format, retention and truncation, and has no answer for a sender whose journal was already trimmed. The inbox carries only what replay needs, keyed by the one id the receiver knows.
- **Trust the inbox file by mode and owner alone (no MAC).** Every same-user process can write a 0600 file in the user's state directory, including a `crosstalk send` script that is no registered agent. Without a MAC such a process could open a route that names any registered agent as the sender, which is sender identity from message content and breaks ADR 0004. The MAC makes the forger hold that agent's token.
- **Bind the receiver on delivery.** The sender's shim cannot create or register the receiver's shim; identity comes from the receiving harness per request (ADR 0006), and a binding made by another process would be exactly the cross-agent identity claim ADR 0004 forbids.
- **Key the inbox by name.** Names are per host, change at a successor (#54) and can be reused by another session; the agent_id is the fixed hash of the binding and is what the receiver's journal is keyed by.

### Its consequences

- What a forged entry can do: a same-user process that can read some agent's token can open an inform route in a receiver's journal naming that agent as sender and any message id. Replay never injects, so its text never reaches the model, but the route is listed in a bounce (ADR 0009) with its message id, so the model may `reply` to an id it never saw delivered, and that reply's text goes to the named sender. To redirect a reply to a real message, the forger must know its id before the receiver binds and get its entry drained first; rule 4 closes the forged route when the genuine entry is drained while the route is still open, but if the model answered first, or `reply` found the forged record and so never drained, the forged route wins. These cases are accepted inside the same-user non-goal (design §1, ADR 0004 Consequences), not prevented: the MAC proves token possession, not that a delivery happened, and the harness's permission model stays the control on what a reply can cause.
- Design §5 (Journal) gains the inbox as a second source of dedupe and route records on registration, and §12 S5 gains the `reply` behaviour for native targets. The pre-bind hint from PR #57 stays for the cases the inbox does not cover (no entry, dropped entry, entry over the cap or older than an hour).
- The Claude and Codex paths are the same: the inbox is keyed by agent_id and written by shared shim code, not by an adapter (ADR 0008).
- Tests that would gate an implementation: a native inform then a bind then `reply` succeeds and closes the route; a second `reply` with other text gets `already_replied`; an entry with a bad MAC, wrong binding, wrong mode, a symlink, or a sender with no token file is dropped; two verified entries with one message id and different senders are both dropped; a forged entry imported first and a genuine one drained later closes the forged route; a crash after the rename, after the dedupe append and after the route append each completes on the next drain without reopening a closed route; a writer paused across a claim and its delete loses no entry; an entry imported 55 minutes after delivery expires five minutes later, also after a restart; the directory caps skip a write and count claimed files; an entry written after replay is picked up by `reply`; an entry older than `InformRouteTTL` is deleted and `reply` gives the pre-bind hint; caps skip the write and the send result carries the hint; a fully imported claimed file left by a crash replays as a no-op.
