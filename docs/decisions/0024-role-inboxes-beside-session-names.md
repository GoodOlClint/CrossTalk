# ADR 0024 — Role inboxes beside session names

- **Status:** Provisional (operator 2026-11-07)
- **Date:** 2026-11-07
- **Deciders:** operator + Claude (Opus 5.5) + Codex review
- **Context source:** issues #43 and #54 (dogfood); triage of both; operator rulings 2026-11-07 on the first draft of this ADR (PR #61): no `rename` tool, keep session names as they are and add role inboxes with a handover overlap; then: an inbox is owned by its creator, who grants access, an ownerless inbox is taken over by a claim, and offline delivery is sketched

## Context

A CrossTalk name is a per-host lookup alias for an `agent_id`, held under its own alias lock for the registration's lifetime (design §3, ADR 0003). The shim takes it from the harness: the Claude session name, or the Codex thread name. If that name is taken, the agent registers under the fallback `<harness>-<cwd basename>-<hex>`, and on every bound call `followRename` (`internal/mcpserver/server.go`) moves the alias back to the harness name once it is free. Storage, sockets, journals, claims and reply routes key on `agent_id`, the fixed hash of (harness, session_ref); the name only resolves `to` at send time (`ResolveTarget`, `internal/mcpserver/target.go`).

**#43, Codex has no launcher-set name.** Claude gets a name from `claude -n`. Codex has no launch-name flag (upstream). Codex `Identify` returns only the thread id from `params._meta.threadId` (`internal/harness/codex/harness.go`), so `Server.resolve` copies the name from Discover, which is the `thread/read` name (`internal/harness/codex/discovery.go`): Codex's auto title for the thread. A launcher that named the session in its prompt cannot find it by that name and must use `agent_id`. Identity is per request and one Codex process may serve several threads, so anything process-scoped cannot name one thread.

A second observation on #43 (dogfood, 2026-11-07): before a Codex session bound, `list_agents` showed a nameless row with one `agent_id`; after it bound, the row showed the auto title with a different `agent_id`. The native row and the bound row compute `agent_id` the same way (`identity.AgentID(harness, session_ref)` in `listAgents`, `internal/mcpserver/discovery.go`, and in `Server.agent`), so the two rows had different session_refs. The triage suggests the pre-bind row was another thread that never ran a turn; that is not confirmed, and this ADR decides nothing about it.

**#54, a saved name breaks at a successor.** A long-lived role (a coordinator) is replaced by a fresh session whose name carries a generation number. Peers that saved the old name get `unknown` / `no_such_agent`; the hint (`internal/mcpserver/hints.go`) sends them to `list_agents`, and nothing points at the successor. This works as designed, but every sender has to work out who replaced whom, and the old and new sessions have no shared address during the handover.

**Already shipped (PR #56, docs only):** briefs use a role name, and a sender runs `list_agents` before its first send.

**First draft of this ADR (PR #61).** It proposed a `rename(name)` tool through which a session pinned its own name and handed a role name to a successor. The operator rejected it: session names should stay as they are, and a role needs an address that more than one session can hold at once, so a handover can overlap. The operator also asked whether a tool named `rename` would clash with the harness rename features (Claude Code's `-n` launch flag and the user-typed `/rename`; neither is model-callable). This draft has no `rename` tool, so that question does not arise: harness renames keep moving the session name through `followRename`, unchanged. A second ruling added ownership: a session may not join a live inbox on its own word.

## Decision

Add role inboxes: a named address, separate from session names, that one or more bound sessions attach to. A message to an inbox reaches every attached session; exactly one of them, the responder, can answer it. Each inbox has one owner, at first the session that created it, and only the owner lets other sessions attach. Session names, the alias lock and `followRename` do not change, and every session stays addressable by its own name and `agent_id`.

1. **Tools.** Three new MCP tools, and one new target form for an existing one:
   - `attach(inbox)` → `{inbox, owner, members}` and `detach(inbox)` → `{inbox, owner, members}`. No target argument: each acts on the calling agent, whose identity comes from the request (Claude parent pid, Codex `_meta.threadId`; ADR 0004, ADR 0006). `attach` to an inbox the caller is already in, and `detach` from one it is not in, succeed without change.
   - `grant(inbox, to, owner=false)` → `{inbox, owner, grants}`: the owner lets the registered local agent `to` (name or `agent_id`, resolved as for `claim`) attach; with `owner=true` it hands ownership to `to`, which must already be a member. Only the owner may grant (`rejected/not_owner`).
   - `claim("inbox:<name>")` → `{inbox, owner}`: takes over an ownerless inbox (rule 4). `claim` of a session is unchanged; the `inbox:` form picks the inbox meaning, as it does in `to`. `release` takes no `inbox:` form (`rejected/invalid_inbox`); an owner gives up ownership by detaching or handing it over.
   - An `unbound` call gets `unbound` for all of them. No message, envelope or peer can attach, detach, grant or claim for a session.
2. **Address form.** An inbox is addressed as `inbox:<name>` in `to`. A value that starts with `inbox:` resolves only to an inbox and never to a session name or `agent_id`, the same way an `agent_id`-shaped value never matches a name (design §8); a session whose own name starts with `inbox:` is then addressable only by its `agent_id`. Inbox names may not be empty or contain `@`, `/` or control characters (`rejected/invalid_inbox`). The inbox name space is separate from session names, so an inbox never takes a session name's alias lock and a session name never blocks an inbox. Sending to an inbox needs no grant, as sending to a session needs none.
3. **Where state lives.** Membership lives in the descriptor: each descriptor gains `inboxes: [{"name": "<inbox>", "attached_at": "<time>"}]`, which an agent writes only in its own descriptor, under its agent lock, through the existing atomic publish (`Registration` in `internal/registry/registry.go`). An inbox's members are the live, non-superseded descriptors that list it (`Registry.List`), so a dead or superseded member drops out the same way its name does. Ownership and grants live in one small file per inbox, `~/.local/state/crosstalk/inboxes/<name>.json` (`{"name", "owner": "<agent_id>", "owner_instance": "<instance_id>", "grants": ["<agent_id>", ...]}`, mode 0600), written atomically. `owner_instance` is the owner's registration `instance_id` (design §3: new for every registration), so a restart or resume of the owner is visible in the file. A shim writes it only for its own calling agent, and only as rule 4 allows.
   - **One serialization boundary.** Every operation that reads ownership or changes membership (`attach`, `detach`, `grant`, inbox `claim`, and the resume replay of rule 11) runs entirely under the inbox lock `inboxes/<name>.lock`: check the file and the owner's descriptor, write the file, append the journal record, publish the descriptor, then release. Senders read membership without the lock; they see a member only once its descriptor is published.
   - **Crash between steps.** Authority is the file plus a live owner descriptor whose `instance_id` equals `owner_instance` and which lists the inbox. A crash after the file write and before the descriptor publish leaves that check false, so the inbox is ownerless and claimable; a crash after the journal append and before the publish is finished by replay under the lock, which re-runs the rule 4 checks first. A displaced owner never regains authority on recovery: replay sees the file name another owner or another `owner_instance` and falls under Resume below.
4. **Ownership.**
   - **Create.** `attach` to an inbox that has no file creates it, with the caller as owner and member and no grants.
   - **Owned.** The inbox is owned while the owner's descriptor is live, not superseded, has `instance_id` = `owner_instance` and lists the inbox. `attach` by any other session then succeeds only if the caller's `agent_id` is in `grants` (`rejected/not_granted` otherwise, with a hint to ask the owner by `send_message`).
   - **Hand over.** `grant(inbox, to, owner=true)` sets `owner` and `owner_instance` to `to`'s, under the lock. The grants are kept: the old owner chose the new one and the members it had let in. The old owner stays a member until it detaches.
   - **Grants end with an ownership incarnation.** Grants are cleared whenever the file is next written after the owner incarnation it names has ended (gone, superseded, detached, or restarted with a new `instance_id`). Any operation under the lock that finds the inbox ownerless clears them before anything else; an `attach` that finds `grants` written for a dead incarnation treats them as empty. A grant therefore never outlives the registration that gave it, even when the owner resumes before anyone else looks.
   - **Ownerless.** An inbox is ownerless when its owner is gone, superseded or has detached (an owner that detaches gives up ownership; the other members stay attached). `attach` to an ownerless inbox is `rejected/ownerless` with a hint to `claim` it. `claim("inbox:<name>")` on an ownerless inbox makes the caller its owner and a member in one locked operation (file, journal, descriptor), with grants cleared; on an owned inbox it is `rejected/inbox_owned`.
   - **Resume.** Replay (rule 11) runs under the inbox lock. A former owner whose `agent_id` the file still names takes the inbox back as a new incarnation: `owner_instance` becomes its new `instance_id` and grants are cleared, because the old incarnation ended. A member re-attaches only if the inbox is owned and it is in the current incarnation's `grants`. In every other case (another owner, ownerless and not named in the file, grant cleared) the membership is dropped, a detach record is journaled, and its model is told in `notice`.
5. **Responder.** The responder is the member with the latest `attached_at` (ties broken by the lower `agent_id`). The newest member answers new messages, so a successor that attaches takes over answering at once, and the predecessor keeps watching until it detaches. Since only granted sessions can attach to an owned inbox, only the owner decides who can become responder.
6. **Delivery.** The sender's shim resolves `inbox:<name>` to its members at send time and sends one message per member, all with the same `message_id`, through each member's own ingress and receiver chain, as for a direct send. The responder gets the message as sent (`inform`, `ask` or `command`). `command` goes to the responder only and is never copied. For `inform` and `ask`, every other member gets a copy: the message with its original `kind` kept, plus `metadata.crosstalk.inbox` = the inbox name and `metadata.crosstalk.inbox_copy` = true. Each member's receiver authorizes the copy against its original `kind`, exactly as a direct message of that kind (an unverified sender's ask copy is rejected at a watcher as it is at the responder); no kind is converted before or instead of that check (ADR 0004: never downgraded). Only after authorization does the receiver deliver it as a copy: journaled for dedupe with the copy marker on the record, opening no reply route. `reply` checks the persisted marker before anything else and returns `rejected/inbox_copy` with a hint that the responder answers. An ask copy's A2A task completes on delivery, like an inform's (`outcome`, `internal/a2a/mapping.go`): it carries no reply obligation, arms no ask deadline and does not count against the open-ask limit (`MaxOpenAsks`, `internal/a2a/server.go`; admitted in `tasks.create`, `internal/a2a/tasks.go`), while the ordinary pending-delivery limit still applies. The copy marker is persisted on the task and journal records, so replay and late delivery reconciliation keep it delivery-only. The copy flag only removes a reply route and never changes the authorization, so a forged flag gains a sender nothing. Every message, copy or not, shows the inbox name to the receiving model.
7. **Result.** `send_message` and `ask` to an inbox return the responder's `{message_id, state}` plus `inbox` and `copies: [{agent_id, state}]`. The per-peer nudge (ADR 0014) counts the inbox as one peer.
8. **Replies and asks.** An ask to an inbox is an ask to the responder: its A2A task, deadline, reply route and the sender's outbound record are keyed exactly as for a direct ask to that `agent_id`. The sender's outbound record (keyed by `message_id`, `internal/journal/journal.go`) holds the responder leg only. Each copy leg is journaled as its own record keyed by (`message_id`, recipient `agent_id`), never under the outbound key, so a copy that settles last cannot overwrite the responder leg's `To`, `Kind`, state or task id; receipt matching (`askedPeer`, `internal/receiver/receiver.go`), deadlines and restart replay read only the outbound record. Journals, dedupe, reply routes, receipts and open asks keep keying on `agent_id`; nothing is re-keyed by inbox. One reply per ask (ADR 0010) holds because only the responder has a route. An ask the responder received stays with it after it detaches or after another member attaches; it answers it or tells the new responder by `send_message`.
9. **Membership notices.** On `attach`, `detach`, an ownership hand-over and a claim, the caller's shim sends an `inform` copy (rule 6, so it opens no route) to every other member, naming the session, the change, the owner and the responder after it. The detach notice is the predecessor's "I am not watching the role inbox anymore": it comes from the detaching session's authenticated identity, not from text it writes.
10. **Zero members.** A send or ask to an inbox with no live member is `rejected/no_such_agent`, with a hint that no session is attached to that inbox. Nothing is queued; see Offline delivery below.
11. **Persistence.** Each attach and detach is journaled in the agent's own journal (a new record type keyed by inbox name). Journal retention keeps the latest record while the agent is attached, as `unresolved` does for an active `TypeClaim` (`internal/journal/journal.go`). Registration replays it under rule 4's Resume check and republishes the inbox in the descriptor with its original `attached_at`, so a shim restart or a resume of the same session_ref restores membership without making the resumed session the responder by accident. An owner that restarts or resumes is owner again as a new incarnation with grants cleared (rule 4, Resume), if the file still names its `agent_id`; while it is down the inbox is ownerless and claimable. Claude `/clear` starts a new session_ref and a new `agent_id` (design §3, Superseded sessions); its membership and ownership do not carry over.
12. **Visibility.** `list_agents` shows each bound row's `inboxes`, with the owner and the responder marked, so membership and ownership are never hidden. Grants are shown to the owner in `attach` and `grant` results.
13. **Remote (ADRs 0021, 0022, planned for v0.2.0).** Inboxes are local to a host. The gateway serves no `attach`, `detach`, `grant` or inbox `claim`, a grant names only a local agent, and a remote sender cannot join a local inbox. `inbox:<name>@<host>` is `rejected/remote_inbox_unsupported` until a later ADR decides cross-host inboxes; a bare `inbox:<name>` never leaves the host. Refusing `@` in inbox names keeps that later form free.

### Offline delivery: sketched, not included

The operator asked for a message to a fully offline session or inbox to wait and be picked up when the session next resumes. It does not fall out of this design: membership lives in live descriptors and an offline session has none, so there is nothing to deliver to without a new store. It is close to the pre-bind inbox ADR 0023 deferred for #41 and can share its storage technique (a MAC under the sender's token, a lock, caps), but not its safety contract: that design never injects, because the message was already delivered, while an offline spool must inject undelivered text. The follow-on has to decide, beyond ADR 0023: delivery of content that never reached the model, partly completed delivery after a crash, offline asks and when their deadlines start, and a forgery exposure that includes text reaching the model. A sketch:
- **Where messages wait:** a spool per target, keyed by the target's `agent_id` (for a session) or inbox name, written by the sender's shim. An entry carries what the receiver's replay needs (message, sender `agent_id`, target binding, a MAC under the sender's token, as in ADR 0023's deferred design), never a reply route opened by the sender.
- **Delivery:** a session's spool is drained into its own journal when it registers (resume); an inbox's spool is delivered to the responder on the first `attach` or `claim` that gives the inbox a member. Drained messages go through the receiver chain like any other.
- **Expiry and size:** entries expire after a fixed time (`InformRouteTTL`, 1 h, is the starting point) and the spool has a per-target and a directory cap; a write over a cap is refused.
- **What the sender sees:** a new state, for example `queued_offline`, distinct from `queued` (which means handed to Codex model history), with a hint that the message waits up to the expiry; an `ask` gets no deadline timer until it is drained.
- **Cost:** a cross-agent write path with a MAC, a lock, crash recovery of a claimed spool file, caps, and a forgery surface larger than ADR 0023's, since a forged entry's text would be injected.

It is the named follow-on **"offline spool"**, to be decided together with ADR 0023's deferred pre-bind inbox, since both write into an agent's future journal. Revisit when either holds: dogfood shows messages lost to a cold handover or a briefly offline session often enough that briefs work around it, or ADR 0023's inbox is reopened for #41.

How it answers each issue:
- **#43.** The launcher names an inbox in its brief, and the Codex session's first CrossTalk call is `attach("<that name>")`, which creates the inbox with the session as owner; peers then send to `inbox:<that name>`. If the launcher created the inbox first, it grants the session after the session's first CrossTalk call shows it in `list_agents`. Each pooled thread attaches only itself, because each call carries its own `threadId`. Still missing: the session's own name stays Codex's auto title, and the inbox has no member until the session's first CrossTalk call, so a send before then is `no_such_agent` (offline spool would cover it). The pre-bind `agent_id` difference is not addressed.
- **#54.** Peers send to `inbox:<role>`, never to a generation-numbered name. Warm handover:
  1. The predecessor P owns `inbox:<role>` and is its responder.
  2. The successor S starts and makes its first CrossTalk call, so it is registered. P calls `grant("<role>", "<S>")`.
  3. S calls `attach("<role>")`. S is now the responder for new messages; both get the membership notice; P keeps receiving copies.
  4. P calls `grant("<role>", "<S>", owner=true)`. S owns the inbox.
  5. P answers the asks it already holds (they are keyed by P's `agent_id`) and hands any other state to S by `send_message`.
  6. P calls `detach("<role>")`. S gets the notice that P is no longer watching the inbox; S is the only member and the owner.
  7. P exits. Peers that sent to `inbox:<role>` throughout reached a member at every step.

  Cold handover: P is gone, its descriptor goes stale, and the inbox is ownerless with no members. S calls `claim("inbox:<role>")` and is owner and responder. Sends in between get `no_such_agent`.

## Rejected alternatives

- **A `rename` tool (the first draft of this ADR).** Rejected by the operator: it moved one name between sessions with no overlap, needed a pin that overrode harness renames, and raised the question of a clash with the harness's own rename features.
- **Open inboxes that any session may attach to.** Rejected by the operator's second ruling: joining a live inbox would silently give a session everything sent to it and the responder role.
- **Carry "who answers" with session `claim`/`release`.** A session claim makes the caller the owner of another agent: the target becomes a subagent, only its owner may `command` it (design §7). Using it to pick the responder would hand command authority to whoever takes over a role. The `inbox:` form of `claim` reuses only the word and the "take what has no owner" rule; it grants no authority over any session.
- **Ownership hand-over by `release` then `claim`.** Between the two, the inbox is ownerless and any session can claim it. `grant(owner=true)` moves ownership in one locked operation to a session the owner chose.
- **The owner picks the responder.** One more tool and state for no case in #43 or #54; granting access already decides who can become responder, and the newest-member rule matches the handover order.
- **Inboxes in the session-name space, under the alias lock.** The alias lock has one holder, which is the opposite of an inbox with several members, and an inbox name would block a session from taking the same harness name (or the reverse). A distinct `inbox:` form keeps both sets of rules unchanged.
- **Ownership and grants in the owner's descriptor.** They must outlive the owner (an ownerless inbox is claimed, a restarted owner is owner again) and be written by a new owner, which may not write another agent's descriptor. Membership stays in descriptors because it must vanish with its session.
- **Deliver to the responder only.** The watching member would learn nothing until it took over, so a successor would start without what arrived during the overlap. The operator asked that a message reach the attached sessions. Cost accepted: a message to an inbox with k members is injected into k sessions and costs model tokens in each of them; outside a handover an inbox usually has one member, so the extra cost is mostly confined to the overlap.
- **The earliest member answers.** A handover would then need a separate step to move the answer role, and a successor would sit as a watcher while its predecessor wound down. With the newest member answering, attaching is the takeover.
- **Members agree who answers by talking to each other.** That puts reply correctness in the models' hands: two members can both answer one ask, or neither. The shim decides by a rule both can see in `list_agents`.
- **Offline delivery in this ADR.** See the sketch above: it needs the store ADR 0023 deferred, at the same cost, and nothing else in this design depends on it.
- **A retired-name-to-successor pointer, or a single-holder role alias.** The writer of a pointer makes an identity claim that does not come from transport (ADR 0004), and a single holder gives no overlap.
- **A launch environment variable for the inbox or name.** It is process-scoped; one Codex process may serve several threads (design §3), and the managed app-server, not the launcher, starts it.
- **Cross-host inboxes in v0.2.0.** Out of scope for #43 and #54; the address form leaves room for them.

## Consequences

- **Trust (ADR 0004).** Every inbox action is taken by the session itself, from transport identity; the owner check compares the caller's `agent_id` with the file. A live inbox can be joined only by a session its owner granted. The exposure that remains, stated plainly: any bound same-user session can claim an ownerless inbox, becoming its owner and responder and receiving everything sent to it from then on, including during a cold handover before the intended successor claims it. Members get a notice of the claim and `list_agents` shows the owner, but an ownerless inbox with no members notifies no one. Any same-user process can also edit the inbox file directly. Both sit inside the same-user non-goal (design §1), like taking a free session name today. The skill and the MCP server instructions say to attach, grant and claim only for an inbox the user or the launch brief names; the peer-text notice already tells the model not to act on a peer's word, which covers a peer asking for a grant.
- **No impersonation through an inbox.** Replies, claims of sessions, open asks and journals stay keyed by `agent_id`. A session that attaches or claims never receives a reply to another member's ask, never inherits a session claim and never answers an ask that went to someone else. A copy opens no route, so a watcher cannot answer for the responder. Owning an inbox gives no authority over its members beyond letting them in.
- **Kinds and policy.** Each member's receiver runs the full chain, so `command` policy (owner only for a subagent) applies per member. A `command` to an inbox reaches only the responder; copies of `inform` and `ask` are authorized against their own kind at each watcher.
- **Remote:** see Decision rule 13. The ADR 0022 planned text is unchanged; cross-host inboxes need their own ADR.
- **Inbox files are not pruned.** An ownerless inbox with no members keeps its small file so it can be claimed later. A sweep of files with no members and no owner is left until the directory grows enough to matter.
- **Design changes when built:** §3 (the descriptor's `inboxes` field; the inbox file; ownership, grants and the responder rule), §4 (the `inbox` and `inbox_copy` metadata), §7 (attach, grant and inbox claim are self-only for the caller and grant no authority over sessions; the exposure above), §8 (ten tools: `attach`, `detach`, `grant`; the `inbox:` form of `to` and `claim`; the result's `inbox` and `copies`; reasons `invalid_inbox`, `not_granted`, `not_owner`, `ownerless`, `inbox_owned`, `inbox_copy`, `remote_inbox_unsupported`), §11 (new tests), the tool count in AGENTS.md, the skill (`plugins/crosstalk/skills/crosstalk/SKILL.md`), the MCP server instructions and `docs/faq.md`.
- **Files an implementation would touch:** `internal/registry/` (descriptor field; a method that republishes the agent's inboxes; the inbox file with its lock and atomic write), `internal/mcpserver/` (`attach`, `detach` and `grant` handlers and the `inbox:` branch of `claim`, beside `claims.go`; `target.go` resolves `inbox:`; `discovery.go` shows inboxes; `hints.go` for the new reasons), `internal/shim/send.go` (fan-out in `deliver`, copies, the result, the nudge peer; `Reply` returns `inbox_copy`), `internal/receiver/receiver.go` (a copy is authorized by its original kind, journals dedupe with the copy marker and opens no route), the sender's journal records (copy legs keyed apart from the outbound record), `internal/journal/journal.go` (the attach record type and its retention), `internal/msg` (the two metadata fields), `internal/a2a/tasks.go` and `mapping.go` (an ask copy is admitted outside the open-ask limit and completes on delivery, persisted for replay).
- **Tests that would pin it:** `TestAttachCreatesInboxOwnedByCaller`; `TestAttachOwnedInboxNeedsGrant`; `TestGrantOnlyByOwner`; `TestGrantOwnerHandsOverInOneWrite`; `TestOwnerDetachLeavesInboxOwnerlessAndClearsGrants`; `TestClaimOwnerlessInbox` (and `inbox_owned` on an owned one); `TestAttachOwnerlessRejectedWithClaimHint`; `TestInboxActionsSelfOnlyAndUnbound`; `TestInboxAddressNeverMatchesSessionName`; `TestInboxFanOutResponderGetsKindOthersGetCopies`; `TestInboxCopyOpensNoRoute` (and `reply` to it is `inbox_copy`); `TestInboxForgedCopyFlagOnlyRemovesRoute`; `TestInboxAskOneReply`; `TestInboxNewestMemberResponds`; `TestInboxMembershipNotices`; `TestInboxZeroMembersNoSuchAgent`; `TestInboxAttachSurvivesRestartAndKeepsOrder` (including a record older than the journal retention window, an owner that resumes and gets a new incarnation with grants cleared, and a member whose grant was cleared); `TestInboxSupersededMemberDropsOut`; `TestInboxHandover` (the seven warm steps of #54, with an ask held by P answered by P after S attached) and `TestInboxColdHandoverClaim`; `TestInboxCommandOnlyToResponder`; `TestInboxCopyAuthorizedAgainstOriginalKind` (an unauthorized watcher rejects an ask copy; a rejected responder does not stop authorized copies); `TestInboxAskCopiesNeverFillOpenAsks` (more ask copies than the open-ask limit, delivered with no deadline, then a watcher restart, then a direct ask is admitted and answered; every copy stays unreplyable); `TestInboxCopyLegNeverOverwritesResponderLeg` (the watcher settles last and the responder's reply is still recognized, also after a sender restart); `TestInboxConcurrentClaimAndResume`; `TestInboxCrashBetweenFileAndDescriptor` (the inbox is ownerless, and a displaced owner does not regain authority on recovery); `TestInboxOwnerResumeClearsOldGrants`; `TestInboxRemoteAddressRejected`; `TestInboxCodexThreadsIndependent`; `TestListAgentsShowsInboxOwnerAndResponder`.

## Open questions

- **Newest member responds, with no watch-only attach.** Recommendation: keep it. A session that wants to watch without taking over has no use in #43 or #54; add an `attach(inbox, respond=false)` form only when a case appears.
- **Reason code for an empty inbox.** Recommendation: reuse `no_such_agent`, which senders and the skill already handle, with an inbox-specific hint, instead of adding `no_such_inbox`.
- **Removing a member or revoking a grant.** Not in this draft: neither issue needs the owner to eject a member. Recommendation: add `revoke(inbox, to)` only when a case appears; until then the owner can hand over or detach.
- **Offline spool.** Recorded as a follow-on above. Recommendation: decide it with ADR 0023's deferred inbox, not here.
