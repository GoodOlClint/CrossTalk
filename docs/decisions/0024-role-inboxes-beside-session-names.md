# ADR 0024 — Role inboxes beside session names

- **Status:** Provisional (operator 2026-11-07)
- **Date:** 2026-11-07
- **Deciders:** operator + Claude (Opus 5.5) + Codex review
- **Context source:** issues #43 and #54 (dogfood); triage of both; operator rulings 2026-11-07 on the first draft of this ADR (PR #61): no `rename` tool, keep session names as they are and add role inboxes with a handover overlap; then: an inbox is owned by its creator, who grants access, an ownerless inbox is taken over by a claim, and offline delivery is sketched; then approved with three fixes: grants belong to the inbox, delivery falls back past an unreachable responder, and only primary sessions act on inboxes

## Context

A CrossTalk name is a per-host lookup alias for an `agent_id`, held under its own alias lock for the registration's lifetime (design §3, ADR 0003). The shim takes it from the harness: the Claude session name, or the Codex thread name. If that name is taken, the agent registers under the fallback `<harness>-<cwd basename>-<hex>`, and on every bound call `followRename` (`internal/mcpserver/server.go`) moves the alias back to the harness name once it is free. Storage, sockets, journals, claims and reply routes key on `agent_id`, the fixed hash of (harness, session_ref); the name only resolves `to` at send time (`ResolveTarget`, `internal/mcpserver/target.go`).

**#43, Codex has no launcher-set name.** Claude gets a name from `claude -n`. Codex has no launch-name flag (upstream). Codex `Identify` returns only the thread id from `params._meta.threadId` (`internal/harness/codex/harness.go`), so `Server.resolve` copies the name from Discover, which is the `thread/read` name (`internal/harness/codex/discovery.go`): Codex's auto title for the thread. A launcher that named the session in its prompt cannot find it by that name and must use `agent_id`. Identity is per request and one Codex process may serve several threads, so anything process-scoped cannot name one thread.

A second observation on #43 (dogfood, 2026-11-07): before a Codex session bound, `list_agents` showed a nameless row with one `agent_id`; after it bound, the row showed the auto title with a different `agent_id`. The native row and the bound row compute `agent_id` the same way (`identity.AgentID(harness, session_ref)` in `listAgents`, `internal/mcpserver/discovery.go`, and in `Server.agent`), so the two rows had different session_refs. The triage suggests the pre-bind row was another thread that never ran a turn; that is not confirmed, and this ADR decides nothing about it.

**#54, a saved name breaks at a successor.** A long-lived role (a coordinator) is replaced by a fresh session whose name carries a generation number. Peers that saved the old name get `unknown` / `no_such_agent`; the hint (`internal/mcpserver/hints.go`) sends them to `list_agents`, and nothing points at the successor. This works as designed, but every sender has to work out who replaced whom, and the old and new sessions have no shared address during the handover.

**Already shipped (PR #56, docs only):** briefs use a role name, and a sender runs `list_agents` before its first send.

**First draft of this ADR (PR #61).** It proposed a `rename(name)` tool through which a session pinned its own name and handed a role name to a successor. The operator rejected it: session names should stay as they are, and a role needs an address that more than one session can hold at once, so a handover can overlap. The operator also asked whether a tool named `rename` would clash with the harness rename features (Claude Code's `-n` launch flag and the user-typed `/rename`; neither is model-callable). This ADR adds no `rename` tool. Later, on 2026-11-09, the operator ruled for #43 that a `rename` tool is built after all; ADR 0027 records it. An inbox names a role and a rename names one session, so the two answer different needs; a session that never calls `rename` keeps harness renames moving its name through `followRename`, unchanged. A second ruling added ownership: a session may not join a live inbox on its own word.

## Decision

Add role inboxes: a named address, separate from session names, that one or more bound sessions attach to. A message to an inbox reaches every attached session; exactly one of them, the responder, can answer it. Each inbox has one owner, at first the session that created it, and only the owner lets other sessions attach. Inboxes do not change session names, the alias lock or `followRename` (a session's own name is ADR 0027's `rename`), and every session stays addressable by its own name and `agent_id`.

1. **Tools.** Three new MCP tools, and one new target form for an existing one:
   - `attach(inbox)` → `{inbox, owner, members, created}` (`created` is true when this call created the inbox) and `detach(inbox)` → `{inbox, owner, members}`; `owner` and member ids are `agent_id`s, members responder first. No target argument: each acts on the calling agent, whose identity comes from the request (Claude parent pid, Codex `_meta.threadId`; ADR 0004, ADR 0006). `attach` to an inbox the caller is already in, and `detach` from one it is not in, succeed without change.
   - `grant(inbox, to, owner=false)` → `{inbox, owner, grants}`: the owner lets the registered local agent `to` (name or `agent_id`, resolved as for `claim`) attach; with `owner=true` it hands ownership to `to`, which must already be a member. Only the owner may grant (`rejected/not_owner`).
   - `claim("inbox:<name>")` → `{inbox, owner}`: takes over an ownerless inbox (rule 4). `claim` of a session is unchanged; the `inbox:` form picks the inbox meaning, as it does in `to`. `release` takes no `inbox:` form (`rejected/invalid_inbox`); an owner gives up ownership by detaching or handing it over.
   - Only a primary session may call `attach`, `detach`, `grant` or inbox `claim`; a subagent gets `rejected/caller_not_primary`, the code session `claim` already returns (`internal/mcpserver/claims.go`). A member that is claimed as a subagent stays attached and cannot change its membership until it is released. An `unbound` call gets `unbound` for all of them. No message, envelope or peer can attach, detach, grant or claim for a session.
2. **Address form.** An inbox is addressed as `inbox:<name>` in `to`. A value that starts with `inbox:` resolves only to an inbox and never to a session name or `agent_id`, the same way an `agent_id`-shaped value never matches a name (design §8); a session whose own name starts with `inbox:` is then addressable only by its `agent_id`. Inbox names compare without case (`Coord` and `coord` are one inbox, stored lowercase). Inbox names may not be empty or contain `@`, `/` or control characters (`rejected/invalid_inbox`). The inbox name space is separate from session names, so an inbox never takes a session name's alias lock and a session name never blocks an inbox. Sending to an inbox needs no grant, as sending to a session needs none.
3. **Where state lives.** Membership lives in the descriptor: each descriptor gains `inboxes: [{"name": "<inbox>", "attached_at": "<time>"}]`, which an agent writes only in its own descriptor, under its agent lock, through the existing atomic publish (`Registration` in `internal/registry/registry.go`). An inbox's members are the live, non-superseded descriptors that list it (`Registry.List`), so a dead or superseded member drops out the same way its name does. Ownership and grants live in one small file per inbox, `~/.local/state/crosstalk/inboxes/<name>.json` (`{"name", "owner": "<agent_id>", "grants": ["<agent_id>", ...]}`, mode 0600), written atomically. A shim writes it only for its own calling agent, and only as rule 4 allows.
   - **One serialization boundary.** Every operation that reads ownership or changes membership (`attach`, `detach`, `grant`, inbox `claim`, and the resume replay of rule 11, which runs in `register()` right after the first descriptor publish) runs entirely under the inbox lock `inboxes/<name>.lock`: check the file and the owner's descriptor, write the file, append the journal record, publish the descriptor, then release. Senders read membership without the lock; they see a member only once its descriptor is published.
   - **Crash between steps.** Authority is the file plus a live, non-superseded owner descriptor that lists the inbox. A crash after the file write and before the descriptor publish leaves that check false, so the inbox is ownerless and claimable; a crash after the journal append and before the publish is finished by replay under the lock, which re-runs the rule 4 checks first. A displaced owner never regains authority on recovery: once another session has claimed the inbox or been handed it, the file names that session, and replay falls under Resume below as a member at most.
4. **Ownership.**
   - **Create.** `attach` to an inbox that has no file creates it, with the caller as owner and member and no grants.
   - **Grants belong to the inbox.** `grants` is the inbox's list of sessions allowed to attach, kept across every change of owner: an owner restart, a hand-over and a claim all leave it as it is, and only `grant` adds to it. A session in `grants` may attach whether the inbox is owned or ownerless, and re-attaches after its own restarts (Resume below). Any other session's `attach` is `rejected/not_granted` with a hint to ask the owner by `send_message` when the inbox is owned, and `rejected/ownerless` with a hint to `claim` it when it is not.
   - **Owned.** The inbox is owned while the owner's descriptor is live, not superseded and lists the inbox.
   - **Hand over.** `grant(inbox, to, owner=true)` sets `owner` to `to` under the lock, and adds the old owner to `grants` so it may re-attach. The old owner stays a member until it detaches.
   - **Ownerless.** An inbox is ownerless when its owner is gone, superseded or has detached (an owner that detaches gives up ownership and is added to `grants`; the other members stay attached). `claim("inbox:<name>")` on an ownerless inbox makes the caller its owner and a member in one locked operation (file, journal, descriptor) and inherits the existing `grants`; on an owned inbox it is `rejected/inbox_owned`.
   - **Resume.** Replay (rule 11) runs under the inbox lock. A session the file names as owner is owner again, with `grants` unchanged. A session in `grants` re-attaches, owned or ownerless. In every other case (the file names another owner and the session is not in `grants`, or the file is gone) the membership is dropped, a detach record is journaled, and its model is told in `notice`.
5. **Responder.** The responder is the member with the latest `attached_at` (ties broken by the lower `agent_id`). The newest member answers new messages, so a successor that attaches takes over answering at once, and the predecessor keeps watching until it detaches. Since only sessions in `grants` (or the owner or a claimer) can attach, only the owner and its predecessors decide who can become responder.
   - **Built (without the walk below).** The responder is the first member, whatever its `list_agents` row says. When its delivery comes back `unreachable`, the send returns that state with the `responder` field, no next member is tried, no copy is sent, and an ask arms no deadline. Any other state ends the same way it does for a direct send to that `agent_id`. The three parts below are the follow-up (I8, ruling A1 of the plan) and are not built.
   - **Fallback (follow-up (I8), not yet built).** For each message the sender's shim picks the responder by walking the members newest first. It skips a member whose `list_agents` row is not `reachable`, and moves on from one whose delivery comes back with a definite non-delivery: `unreachable` (design §8: harness refusal, pre-send failure, binding not loaded, `systemError`), which means nothing was injected. A member that hangs, whose delivery comes back `unknown` with reason `pending` (the settle poll ended without a state past `submitted`/`dispatching`; this covers a task still submitted, one already dispatching, and a poll that failed, so it is no proof of anything), gets a `CancelTask`; only a cancel confirmed to take effect before the far side's dispatch claim lets the walk move on, because only then is it certain nothing was injected. Any other `unknown`, any `accepted` or `queued`, and any `rejected` (a policy decision, ADR 0004) ends the walk at that member. The member the walk ends at is the responder for this message and opens the reply route; every other member gets a copy (rule 6), except the ones the walk passed, which get none.
   - **Durable candidate (follow-up (I8), not yet built).** The sender's outbound record (keyed by `message_id`) always holds the walk's active candidate, written before that candidate's dispatch exactly as a direct send writes it today, so a candidate that accepts and replies before its send or poll returns is matched by `askedPeer` (`internal/receiver/receiver.go`) and its deadline is armed. The walk advances only after the evidence for a definite non-delivery or a confirmed cancel is journaled: it records the passed leg under its own (`message_id`, `agent_id`) key, then rewrites the outbound record to the next candidate. A sender that restarts mid-walk resumes from the outbound record: a candidate whose leg has no journaled non-delivery evidence stays the responder, with `unknown` if its state is ambiguous, and the walk is never restarted from the top.
   - **Durable route closure (shipped with #63, not a change this ADR makes).** A leg counts as `unreachable` for the walk only if the receiver durably closed the reply route it opened before injection. The receiver closes the route first: the closed route record is appended, and only then the `unreachable` dispatch and dedupe outcome. When the close does not land, it records and reports `unknown` (reason `journal`) instead, so neither the immediate return nor a later `GetTask` or retry after a receiver restart can show `unreachable` while the route is still recoverable; the walk stops there and that candidate stays the responder, whose route may survive a restart. This holds for every send, not only inbox legs.
   - **No double reply.** The walk moves past a member only when it is certain that member received nothing and holds no route, so at most one member holds a route for the message. A member whose delivery is ambiguous stays the responder, with `unknown` reported as today; no second member is tried.
   - **Exhausted walk (follow-up (I8), not yet built).** If every member is skipped or passed, the send returns `unreachable` with reason `no_reachable_member`, no `responder`, every member in `passed`, and no copies; an ask arms no deadline and opens no obligation. An inbox with no live member at all is rule 10.
6. **Delivery.** The sender's shim resolves `inbox:<name>` to its members at send time and sends one message per member, all with the same `message_id`, through each member's own ingress and receiver chain, as for a direct send. The responder gets the message as sent (`inform`, `ask` or `command`). `command` goes to the responder only and is never copied. For `inform` and `ask`, every other member gets a copy: the message with its original `kind` kept, plus `metadata.crosstalk.inbox` = the inbox name and `metadata.crosstalk.inbox_copy` = true. Each member's receiver authorizes the copy against its original `kind`, exactly as a direct message of that kind (an unverified sender's ask copy is rejected at a watcher as it is at the responder); no kind is converted before or instead of that check (ADR 0004: never downgraded). Only after authorization does the receiver deliver it as a copy: journaled for dedupe with the copy marker on the record, opening no reply route. `reply` checks the persisted marker before anything else and returns `rejected/inbox_copy` with a hint that the responder answers. An ask copy's A2A task completes on delivery, like an inform's (`outcome`, `internal/a2a/mapping.go`): it carries no reply obligation, arms no ask deadline and does not count against the open-ask limit (`MaxOpenAsks`, `internal/a2a/server.go`; admitted in `tasks.create`, `internal/a2a/tasks.go`), while the ordinary pending-delivery limit still applies. The copy marker is persisted on the task and journal records (`Inbox`, `Copy`), so replay and late delivery reconciliation keep it delivery-only; a copy's task is stored with kind `inform` and the kind it was sent as in `OrigKind`, so a reader that predates the markers resumes an inform, never an ask, and the kind shown to the sender and the receiving model stays the original. The copy flag only removes a reply route and never changes the authorization, so a forged flag gains a sender nothing. Every message, copy or not, shows the inbox name to the receiving model, and a copy also shows the copy marker (Claude envelope attribute `inbox-copy="true"`, Codex field `inbox_copy: true`), set only on a copy, so a watcher knows the message is informational and the responder answers.
7. **Result.** `send_message` and `ask` to an inbox return the responder's `{message_id, state}` plus `inbox`, `responder` (its `agent_id`; omitted when the walk is exhausted), `copies: [{agent_id, state, reason?}]`, and, once the fallback walk exists (follow-up, not built), `passed: [{agent_id, state}]` for the members it moved past. The per-peer nudge (ADR 0014) counts the inbox as one peer.
8. **Replies and asks.** An ask to an inbox is an ask to the responder: its A2A task, deadline, reply route and the sender's outbound record are keyed exactly as for a direct ask to that `agent_id`. The sender's outbound record (keyed by `message_id`, `internal/journal/journal.go`) holds the responder leg only. Each copy leg (and, once the walk exists, each leg it moved past) is journaled as its own `leg` record keyed by (`message_id`, recipient `agent_id`); the outbound key holds only the responder leg, so a copy that settles last cannot overwrite the responder leg's `To`, `Kind`, state or task id; receipt matching (`askedPeer`, `internal/receiver/receiver.go`), deadlines and restart replay read only the outbound record. Journals, dedupe, reply routes, receipts and open asks keep keying on `agent_id`; nothing is re-keyed by inbox. One reply per ask (ADR 0010) holds because only the responder has a route. An ask the responder received stays with it after it detaches or after another member attaches; it answers it or tells the new responder by `send_message`.
9. **Membership notices.** On `attach`, `detach`, an ownership hand-over and a claim, the caller's shim sends an `inform` copy (rule 6, so it opens no route) to every other member, naming the session, the change, the owner and the responder after it. The detach notice is the predecessor's "I am not watching the role inbox anymore": it comes from the detaching session's authenticated identity, not from text it writes.
10. **Zero members.** A send or ask to an inbox with no live member is `rejected/no_such_agent`, with a hint that no session is attached to that inbox. Nothing is queued; see Offline delivery below.
11. **Persistence.** Each attach and detach is journaled in the agent's own journal (a new record type keyed by inbox name). Journal retention keeps the latest record while the agent is attached, as `unresolved` does for an active `TypeClaim` (`internal/journal/journal.go`). Registration replays it right after its first descriptor publish, under rule 4's Resume check, and republishes the inbox in the descriptor with its original `attached_at`, so a shim restart or a resume of the same session_ref restores membership without making the resumed session the responder by accident. An owner that restarts or resumes is owner again with its grants intact (rule 4, Resume), if the file still names its `agent_id`; while it is down the inbox is ownerless and claimable, and a claimer inherits the grants. Claude `/clear` starts a new session_ref and a new `agent_id` (design §3, Superseded sessions); its membership and ownership do not carry over.
12. **Visibility.** `list_agents` shows each bound row's `inboxes`, with the owner and the responder marked, so membership and ownership are never hidden. Grants are shown to the owner in `attach` and `grant` results.
13. **Remote (ADRs 0021, 0022, built in 0.2.0).** Inboxes are local to a host. The gateway serves no `attach`, `detach`, `grant` or inbox `claim`, a grant names only a local agent, and a remote sender cannot join a local inbox. `inbox:<name>@<host>` is `rejected/remote_inbox_unsupported` until a later ADR decides cross-host inboxes; a bare `inbox:<name>` never leaves the host. Refusing `@` in inbox names keeps that later form free.

### Offline delivery: sketched, not included

The operator asked for a message to a fully offline session or inbox to wait and be picked up when the session next resumes. It does not fall out of this design: membership lives in live descriptors and an offline session has none, so there is nothing to deliver to without a new store. It is close to the pre-bind inbox ADR 0023 deferred for #41 and can share its storage technique (a MAC under the sender's token, a lock, caps), but not its safety contract: that design never injects, because the message was already delivered, while an offline spool must inject undelivered text. The pre-bind store itself is built by ADR 0026, which keeps ADR 0023's design (a MAC under the sender's token, a lock, caps) and never injects; the offline spool stays deferred and would reuse that storage technique. The follow-on has to decide, beyond ADR 0023: delivery of content that never reached the model, partly completed delivery after a crash, offline asks and when their deadlines start, and a forgery exposure that includes text reaching the model. A sketch:
- **Where messages wait:** a spool per target, keyed by the target's `agent_id` (for a session) or inbox name, written by the sender's shim. An entry carries what the receiver's replay needs (message, sender `agent_id`, target binding, a MAC under the sender's token, as in ADR 0023's deferred design), never a reply route opened by the sender.
- **Delivery:** a session's spool is drained into its own journal when it registers (resume); an inbox's spool is delivered to the responder on the first `attach` or `claim` that gives the inbox a member. Drained messages go through the receiver chain like any other.
- **Expiry and size:** entries expire after a fixed time (`InformRouteTTL`, 1 h, is the starting point) and the spool has a per-target and a directory cap; a write over a cap is refused.
- **What the sender sees:** a new state, for example `queued_offline`, distinct from `queued` (which means handed to Codex model history), with a hint that the message waits up to the expiry; an `ask` gets no deadline timer until it is drained.
- **Cost:** a cross-agent write path with a MAC, a lock, crash recovery of a claimed spool file, caps, and a forgery surface larger than ADR 0023's, since a forged entry's text would be injected.

It is the named follow-on **"offline spool"**, still deferred. The pre-bind store (ADR 0026) is built and the spool would reuse its storage technique. Revisit when dogfood shows messages lost to a cold handover or a briefly offline session often enough that briefs work around it.

How it answers each issue:
- **#43.** The launcher names an inbox in its brief, and the Codex session's first CrossTalk call is `attach("<that name>")`, which creates the inbox with the session as owner; peers then send to `inbox:<that name>`. If the launcher created the inbox first, it grants the session after the session's first CrossTalk call shows it in `list_agents`. Each pooled thread attaches only itself, because each call carries its own `threadId`. The session's own name is set with `rename` (ADR 0027); the inbox covers the role. Still missing: the inbox has no member until the session's first CrossTalk call, so a send before then is `no_such_agent` (offline spool would cover it). The pre-bind `agent_id` difference is not addressed.
- **#54.** Peers send to `inbox:<role>`, never to a generation-numbered name. Warm handover:
  1. The predecessor P owns `inbox:<role>` and is its responder.
  2. The successor S starts and makes its first CrossTalk call, so it is registered. P calls `grant("<role>", "<S>")`.
  3. S calls `attach("<role>")`. S is now the responder for new messages; both get the membership notice; P keeps receiving copies.
  4. P calls `grant("<role>", "<S>", owner=true)`. S owns the inbox.
  5. P answers the asks it already holds (they are keyed by P's `agent_id`) and hands any other state to S by `send_message`.
  6. P calls `detach("<role>")`. S gets the notice that P is no longer watching the inbox; S is the only member and the owner.
  7. P exits. Peers that sent to `inbox:<role>` throughout reached a member at every step.

  Cold handover: P is gone, its descriptor goes stale, and the inbox is ownerless with no members. S calls `claim("inbox:<role>")` and is owner and responder. Sends in between get `no_such_agent`.

## Rejected alternatives

- **A `rename` tool as the role mechanism (the first draft of this ADR).** Rejected by the operator for roles: it moved one name between sessions with no overlap. A `rename` tool for a session's own name was later ruled in for #43 (operator, 2026-11-09) and is ADR 0027; it is not a role mechanism.
- **Open inboxes that any session may attach to.** Rejected by the operator's second ruling: joining a live inbox would silently give a session everything sent to it and the responder role.
- **Carry "who answers" with session `claim`/`release`.** A session claim makes the caller the owner of another agent: the target becomes a subagent, only its owner may `command` it (design §7). Using it to pick the responder would hand command authority to whoever takes over a role. The `inbox:` form of `claim` reuses only the word and the "take what has no owner" rule; it grants no authority over any session.
- **Ownership hand-over by `release` then `claim`.** Between the two, the inbox is ownerless and any session can claim it. `grant(owner=true)` moves ownership in one locked operation to a session the owner chose.
- **The owner picks the responder.** One more tool and state for no case in #43 or #54; granting access already decides who can become responder, and the newest-member rule matches the handover order.
- **Inboxes in the session-name space, under the alias lock.** The alias lock has one holder, which is the opposite of an inbox with several members, and an inbox name would block a session from taking the same harness name (or the reverse). A distinct `inbox:` form keeps both sets of rules unchanged.
- **Ownership and grants in the owner's descriptor.** They must outlive the owner (an ownerless inbox is claimed, a restarted owner is owner again) and be written by a new owner, which may not write another agent's descriptor. Membership stays in descriptors because it must vanish with its session.
- **Deliver to the responder only.** The watching member would learn nothing until it took over, so a successor would start without what arrived during the overlap. The operator asked that a message reach the attached sessions. Cost accepted: a message to an inbox with k members is injected into k sessions and costs model tokens in each of them; outside a handover an inbox usually has one member, so the extra cost is mostly confined to the overlap.
- **The earliest member answers.** A handover would then need a separate step to move the answer role, and a successor would sit as a watcher while its predecessor wound down. With the newest member answering, attaching is the takeover.
- **Members agree who answers by talking to each other.** That puts reply correctness in the models' hands: two members can both answer one ask, or neither. The shim decides by a rule both can see in `list_agents`.
- **Offline delivery in this ADR.** See the sketch above: it needs the store ADR 0023 deferred, at the same cost, and nothing else in this design depends on it.
- **A retired-name-to-successor pointer, or a single-holder role alias.** The writer of a pointer makes an identity claim that does not come from transport (ADR 0004), and a single holder gives no overlap.
- **A launch environment variable for the inbox or name.** It is process-scoped; one Codex process may serve several threads (design §3), and the managed app-server, not the launcher, starts it.
- **Cross-host inboxes in v0.2.0.** Out of scope for #43 and #54; the address form leaves room for them.

## Consequences

- **Trust (ADR 0004).** Every inbox action is taken by the session itself, from transport identity; the owner check compares the caller's `agent_id` with the file. Only primary sessions act on inboxes, and an inbox can be joined only by a session in its `grants` (or by claiming it while ownerless). The exposure that remains, stated plainly: any bound same-user primary session can claim an ownerless inbox, becoming its owner and responder, inheriting its grants and receiving everything sent to it from then on, including during a cold handover before the intended successor claims it. Grants outlive the owner that gave them: a session granted once keeps access across owner restarts, hand-overs and claims until revocation exists (Open questions). Members get a notice of the claim and `list_agents` shows the owner, but an ownerless inbox with no members notifies no one. Any same-user process can also edit the inbox file directly. Both sit inside the same-user non-goal (design §1), like taking a free session name today. The skill and the MCP server instructions say to attach, grant and claim only for an inbox the user or the launch brief names; the peer-text notice already tells the model not to act on a peer's word, which covers a peer asking for a grant.
- **No impersonation through an inbox.** Replies, claims of sessions, open asks and journals stay keyed by `agent_id`. A session that attaches or claims never receives a reply to another member's ask, never inherits a session claim and never answers an ask that went to someone else. A copy opens no route, so a watcher cannot answer for the responder. Owning an inbox gives no authority over its members beyond letting them in. The fallback walk only moves the answering role to a member that already receives the inbox's messages; it never reaches a non-member.
- **Kinds and policy.** Each member's receiver runs the full chain, so `command` policy (owner only for a subagent) applies per member. A `command` to an inbox reaches only the responder; copies of `inform` and `ask` are authorized against their own kind at each watcher.
- **Remote:** see Decision rule 13. The ADR 0022 planned text is unchanged; cross-host inboxes need their own ADR.
- **Inbox files are not pruned.** An ownerless inbox with no members keeps its small file so it can be claimed later. A sweep of files with no members and no owner is left until the directory grows enough to matter.

## Open questions

- **Newest member responds, with no watch-only attach.** Recommendation: keep it. A session that wants to watch without taking over has no use in #43 or #54; add an `attach(inbox, respond=false)` form only when a case appears.
- **Reason code for an empty inbox.** Recommendation: reuse `no_such_agent`, which senders and the skill already handle, with an inbox-specific hint, instead of adding `no_such_inbox`.
- **Removing a member or revoking a grant.** Not in this ADR: neither issue needs the owner to eject a member. Since grants now outlive their owner, a revoke matters more than before. Recommendation: add `revoke(inbox, to)` when the first case appears, for example a granted session that should no longer receive a role's messages.
- **Offline spool.** Recorded as a follow-on above. Recommendation: decide it with ADR 0023's deferred inbox, not here.
