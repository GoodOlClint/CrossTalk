# ADR 0028 — Codex no-daemon sessions get an experimental opt-in queue wake, the journal stays the mailbox

- **Status:** Provisional (council 2026-11-10, revised after the chair's critique, a Codex adversarial review and the chair's final precision fixes the same day; operator consent rulings (a) to (d) recorded 2026-11-10, R191 (mark on pull) recorded 2026-11-10; the operator approved the build (steps 1 to 7) on 2026-11-10; step 2 built; the rest gated on the feasibility probes and the isolated prototype results)
- **Date:** 2026-11-10
- **Deciders:** operator (consent rulings 2026-11-10; build approved 2026-11-10) + Claude + council (five advisors, one of them Codex)
- **Implementation:** step 2 built (the shared `mailboxed` / `delivered` / `confirmed` states, the monotonic rule, the pull marks, `possibly_seen`, the drain flag, `reply` confirming, `not_collected` and the `MailSignal` extension point, harness-neutral). Step 1 built (claim handoff and owner proof, plan 3.3). Step 3 built: the per-write gate (plan 3.5) over a cgo-free driver, `modernc.org/sqlite`. Step 4 built: the queue write and the wake generations (plan 3.4), with the generation kept as one latest-state file per thread in the Codex adapter rather than in the receiver journal, and the harness-neutral post-pull hook `adapter.PullSignaler`. Steps 5 and 6 built: the Codex adapter's `Inject` picks the route and returns `mailboxed`, `MailSignal` writes the wake row, and the switch is the install flag `crosstalk install --codex-no-daemon-queue` (it creates the state-dir setting file `codex-queue-wake.on` and adds the SessionStart hook to `~/.codex/hooks.json`; `uninstall` removes both; `install --check` K10 is a warn-only line; the claim-serving shim's own `list_agents` row shows `delivery_mode: queue-wake (experimental)`; no other session's listing does). ## Context

A Codex session started with `codex --no-daemon` runs a private app-server inside its own process, with no socket CrossTalk can dial. It can send and pull messages but cannot receive them: `Register` binds it with an empty endpoint, `Inject` returns `ErrNoEndpoint`, a send is `unreachable` and an ask is `rejected/no_endpoint`. The supported workaround, a dedicated app-server plus `codex --remote` (`docs/setup.md`), has never been run live.

The only inbound surface such a process has is its local queue, `~/.codex/queue_1.sqlite`, table `queued_items`, which holds the user's queued prompts and which a watcher in the Codex process dispatches into the thread. Since a 2026-08-17 Codex migration, revision triggers make an external insert visible to that watcher. Codex source at tag `rust-v0.167.0` (`codex-rs/ext/queue/src/service.rs`, read, not run) shows a 10 s watcher that skips Running, Interrupted, Shutdown and NotFound threads, deletes an invalid or non-user row and continues, and removes a row when Core accepts the turn, before any proof the model fetched anything; the queue holds at most 100 items. Live manual inserts on 0.167.0, per trial: into an idle thread, a row carrying a plain operator-requested "hello world" prompt (not the fixed mailbox notification) started a turn; into an idle advisor thread, a fixed wake row started a turn in which the model called `receive_message` and answered with `send_message`, not `reply` (the only full nudge → pull → answer evidence; the row's removal was verified for this trial); into a busy thread, two rows stayed in the queue (one checked at 15 s, both still present later) and the messages were pulled by hand, so that trial shows persistence and a readable mailbox, not dispatch. The queue has no external-write contract and a dispatched row is a user turn. Whether a running daemon competes for the same thread is a hypothesis with no evidence; the writer lock gates ownership.

ADR 0007 keeps peer text out of operator input and says no subprocess queue is used; ADR 0004 keeps peer text out of instructions. ADR 0012 defines `mailboxed` and `collecting` for a harness with no push channel, but is unbuilt. Today the receiver journals a dispatch outcome only after `Inject` returns, and the latest outcome record wins; the MCP server serves concurrent calls, including repeated calls for one thread, and one process may serve several threads (ADR 0006). `receive_message` never returns `accepted` or `queued` entries, so a wake that pointed at a `queued` entry would point at nothing the model can pull.

A SessionStart hook fires at the first turn, not at launch (measured), and the shim starts about 1 s after Codex. An unprompted tab fires no hook. Today a session is unreachable until its own first CrossTalk call, and nothing can wake it to make that call. The owning Codex process has `~/.codex/thread-writer-locks/<thread>.lock` open (whether it holds the lock is unmeasured); the shim's parent is that process; pooled daemon shims have a different parent. The hook's `session_id` is self-asserted stdin text. ADR 0004 accepts that the same-user credential model is no isolation from hostile same-user processes.

## Decision

Gate order: first raw Codex lifecycle and hook evidence (plan step 0), then an isolated prototype of the unbuilt mailbox and claim semantics (step 0b), then product implementation only after the operator approves the plan. If those pass and the operator approves, a `--no-daemon` session may receive through a queue wake, built as follows. Step 2 is built; the remaining steps are not.

1. **Experimental and opt-in.** One host-wide setting, off by default, turned on by one install flag (`crosstalk install --codex-no-daemon-queue`, Codex only), with no per-session or per-sender switches in v1 (operator ruling (a), 2026-11-10), never described as production-ready. The supported routes (daemon, dedicated app-server) are unchanged and named first in the docs.
2. **The journal is the mailbox, and mail is pullable before any wake.** The chain order (authenticate → dedupe → hop-chain → policy → `Inject` → resolve) is unchanged. The Codex adapter's `Inject` writes nothing external and returns `mailboxed`; the receiver records `mailboxed` and only after that commits calls the adapter's optional `MailSignal` (ADR 0012's extension point), which alone writes the wake row. Mailbox states are monotonic (`mailboxed` → `delivered` → `confirmed`); a late or replayed outcome never moves an entry back. ADR 0012's `mailboxed` state is reused and built harness-neutral, with `delivered` and `confirmed` in place of `collecting` (operator ruling R191, mark on pull): a top-level `receive_message` from the bound thread marks the entries it returns `delivered`; there is no collection token, no `ack` argument and no cursor settlement. A `delivered` entry is unconfirmed: the next pull from the same thread returns it again with `possibly_seen: true`, and it becomes `confirmed` (never returned again) when a `reply` names it, at any time, or once a second pull has returned it. A call from another thread never delivers or confirms. A wake is for `mailboxed` entries only, never for `delivered` ones. A `reply` confirms the entry once the reply is accepted for sending, even if the reply's routing or send then fails. `reply` to an entry still `mailboxed` returns `not_collected`. CrossTalk never forces a tool call only to acknowledge. Nothing is `accepted` before handoff, and `queued` is not reused. Row removal by Codex is never delivery evidence.
3. **The wake carries no peer text.** One row with a fixed sentence naming `receive_message` on server `crosstalk`: no sender, no count, no message id, plus a stable CrossTalk wake id in the row's client id field. The body arrives as tool output with the existing notice and stays data under the skill, although the wake itself is user-role. The paid user-role wake turn is a named exception to ADR 0007 and ADR 0004, allowed narrowly: fixed text only, at most one open wake per thread, only while the setting is on, only for `immediate` sends from verified and local senders (operator ruling (b), 2026-11-10; "local" added at step 5 verification: a paired-host sender, and an inbox copy, never cause a wake in v1).
4. **Persisted wake generations, bounded writes.** Each wake is a journal generation per thread, recorded before the action it names: `pending`, `queued`, `admitted` (row seen gone, no pull yet), then closed as `collected`, `unknown` or `failed`. A new row is written only when no generation is open, in one immediate transaction at `MAX(queue_order)+1` with a bounded busy retry; a thread at the queue cap gets no row. A pull that closes a generation with no entries left re-checks for wake-eligible `mailboxed` entries (never `delivered` ones) that arrived after its snapshot and opens a new generation if any did, so a late arrival is not left without a wake (mailbox-only entries never count). Ambiguity resolves toward fewer paid turns: `admitted` with no pull within a bound, or `pending` on replay with no row found, becomes `unknown`; replay and bind never write a row; only a newly arriving message opens the next generation. No promise of exactly-once or of one wake per N messages. A pull that leaves entries behind says so, so one wake drains several pages. There is still no message rate limit (ADR 0014); only redundant wakes are bounded.
5. **Fail closed, revalidated per write.** Write only when the file already exists, its table layout, queue migration checksums and revision triggers match a pinned set, and the parent Codex version is at or above the floor 0.167.0, the first measured version. There is no version allowlist: the schema digest and migrations are the check, and the scheduled harness-compat run is the watchdog for behaviour (ADR 0029). The file's identity and schema are re-checked inside the write transaction, so no cached result survives a replaced or migrated database; the version is cached only per (parent pid, start time) and only while the parent's mapped executable is the file at its path. Otherwise `unreachable` with a hint naming the supported route, and existing entries stay pullable. Never write when any app-server hosts the thread.
6. **Mutually exclusive routes; who never wakes.** Checked first, as a guard: any earlier attempt for the message, on any route, ended `unknown`: `unknown`, no resend, no fallback to user input and no new wake, even when a host now exists, so one envelope never enters both paths. Otherwise exactly one of: exactly one app-server host and no owner-proven claim: unchanged. No host, unambiguous ownership, no queue capability (setting off, no owner-proven claim, gate fails): `unreachable`, asks `rejected/no_endpoint`. Capability present and `next_turn`, an unverified or paired-host sender, or an inbox copy: `mailboxed`, no wake. Capability present, `immediate`, verified and local sender, not an inbox copy: `mailboxed` and a wake. Two or more candidate hosts, or ambiguous ownership (a host and an owner-proven claim, or owner-proven claims from more than one process): `unreachable`, asks `rejected/no_endpoint`. An interrupted or paused thread stays paused. Built in step 5 as plan 3.1 records: the guard is the receiver's dedupe and dispatch claim, which never call `Inject` again for a message seen before; the other rows are one selector in the Codex harness's `Inject`, in play only while the shim serves claims and the setting is on, and an ask stays `rejected/no_endpoint` even with the capability present until step 7.
7. **Asks.** Once the feasibility probes and the live acceptance run pass, an ask to a session with queue capability is accepted in state `mailboxed`, route open and deadline armed; until then it stays `rejected/no_endpoint`.
8. **Registration and ownership.** Registration is its own must-pass goal: a session is receivable before its first message is sent to it, and once SessionStart has fired it no longer depends on the session's own first CrossTalk call (making that call a precondition would repeat today's circular dependency). A stateless SessionStart hook hands a claim to the owning shim through an authenticated exchange and leaves it durably in a 0600 file. The shim registers from the claim only when four proof obligations hold. Target: the shim's own parent owns the thread's writer lock; this proves the thread exists and is owned, not that the claim came from its hook. Live origin: the claim's sender pid is taken from the transport (the socket peer credential) and its actual ancestry is verified to reach the shim's parent; a pid or `CODEX_THREAD_ID` in the claim body is never used. Durable claim: a 0600 file written before the shim listened cannot be tied to its writer, so it stops other users only; a hostile same-user process can forge it, which ADR 0004 places outside the trust model, and the only bound is that it can bind no thread but one the parent owns. Lock ownership, by inference (step 0, probe 13: Codex uses `flock`, and the kernel names no holder, so `F_GETLK` is not a held-check): a non-blocking `flock` attempt on the thread's lock file fails with EAGAIN, the shim's parent has the file open, and no other process has it open; a second opener fails the proof closed. Claims and records are per (harness, thread): one process may serve several threads, a call carrying another thread's `_meta.threadId` binds per request (ADR 0006) and never revokes another thread's claim. A claim is revoked for its own thread only, only when the proof fails on recheck; a claim for the same thread from another process never revokes and is ignored if it fails the proof (coordinator ruling after step 0b). Without the proof the row is discovered and unbound only, and the claim never unlocks a queue write, an ask, a name pin, a `claim` or a `command` target. Whether the proof is sufficient is pinned by tests and the live acceptance run, not an operator question. An unprompted tab fires no hook; discovering it from parent-owned locks is a separate probe and not promised. Built in step 1 as plan 3.3 records: opener list by `proc_info` or `/proc`, same user only, failing closed on a process it cannot inspect; probes of one lock serialized in-process and read held, openers, held; a 3-try debounce; a revoked claim retires the agent only it registered; the hook dials only a private socket directory. A refresh (ADR 0030) carries each proven claim in the handoff and proves each one again by the target check only, dropping the binding and retiring the agent on failure; a claim not in the handoff takes the normal start scan, and the live-origin proof is not repeated because the handoff reaches the new image through an inherited descriptor no other process can write.
9. **Honest sender state.** The sender sees `mailboxed` with a hint (best effort, idle-only, a 10 s watcher interval at 0.167.0 per source, not a deadline), never delivered; the `list_agents` of the shim that holds the claim shows the row's delivery mode (descriptors do not carry it, so no other session's listing does). Crash windows across the two stores and the queue-to-daemon switch after a resume are specified in the plan, section 3.6.
10. **Small footprint.** No general SQLite abstraction; a cgo-free driver, so the signed static release holds (ADR 0015, 0017). No upstream Codex issue or request without the operator.

When built, ADR 0007 is amended in place: the fixed-text user-role wake is a named exception, and "no subprocess queue" is narrowed to "no peer text in a queue".

## Rejected alternatives

- **Peer text in the queue row.** Gives peer text operator authority (ADR 0007, 0004) and would replay with the row on resume.
- **Returning `queued` for a written row.** The pull hides `queued` entries, and a committed row says nothing about the model.
- **On by default, or production status now.** One full nudge → pull → answer on one version, and no observed dispatch for a busy thread; the interrupted, resumed, compaction, crash and ownership-transfer cases are untested; each wake is a paid turn.
- **A general wake primitive for every harness.** Premature before one harness's queue lifecycle is measured.
- **Trusting the hook's claim alone.** Its `session_id` is self-asserted; any same-user process could write a claim for a thread. The owner and lineage proof is the minimum.
- **Requiring the session's first `tools/call` before the queue route opens.** Circular: nothing can wake the session to make that call.
- **Daemon-only (do nothing).** Leaves #112 open on an untested workaround. It stays the default, and the answer if the probe or the operator says no.
- **Deleting or rewriting rows CrossTalk did not write, or unknown rows.** Never. Deleting CrossTalk's own stale wake rows is deferred from v1 (operator ruling (d)).
- **Writing the wake from inside `Inject`.** `Inject` returns before the receiver records `mailboxed`, so Codex could take the row and the model pull before the entry is visible, and a crash in that gap recovers as `unknown`.
- **Settling on the next bound call, or on a collection token, cursor or `ack`.** Codex issues tool calls concurrently; a `list_agents` alongside the pull says nothing about what the model read, and settling on it can mark unread mail `accepted` and hide it from later pulls. The causal-settlement design that answered this (a covering cursor, an echoed token) is replaced by mark on pull (R191): the pull marks `delivered`, nothing waits on later evidence, and an unconfirmed entry is re-returned once with `possibly_seen`.
- **Revoking a claim on any differing `_meta.threadId`.** One process may serve several threads; that would break per-request identity (ADR 0006) for valid subagent threads.
- **Caching the gate per process.** A database replaced or migrated by another Codex process, or a binary upgraded under a running parent, would pass a stale check.
- **A broad SQLite layer or a cgo driver.** More surface than one guarded insert needs; a cgo driver breaks the static signed release.

## Consequences

- The route depends on a private Codex store and on observed, not contracted, behaviour. A Codex release that changes behaviour without changing the schema is not caught by the gate; the harness-compat CI run re-validates each release on macOS and opens an issue on a failure (ADR 0029).
- Each wake costs a model turn and is visible to the operator as a user turn.
- A crash, turning the setting off, or a Codex upgrade can leave a CrossTalk wake row in Codex's database; a later resume may fire it once. The wake is harmless by construction (it only asks for a pull), not by cleanup. CrossTalk writes no new row in those cases, and the user docs say so (operator ruling (c), 2026-11-10). v1 deletes no wake row; stale-row cleanup is deferred (operator ruling (d), 2026-11-10).
- A `delivered` entry is unconfirmed: it is re-returned by the next pull with `possibly_seen: true` and confirmed by that second return or by a `reply`. A model that pulls and never answers still sees the entry once more; the sender's view never claims more than `delivered`.
- A lost wake leaves mail pullable but unannounced until the next arrival or a manual pull.
- An unprompted `--no-daemon` tab stays unreachable; the docs must say so.
- Building it also builds ADR 0012's shared `mailboxed` contract, which changes `receive_message` (`possibly_seen` flag, drain field, marking on pull) and the state list in design §8, adds the post-resolve `MailSignal` step, narrows ADR 0012 item 3 to mark on pull (step 6), and needs edits to design §3, §5, §6, ADR 0007, `docs/setup.md`, the FAQ and AGENTS.md.
- Implementation commits carry `Provisional-ADR: 0028`.

## Operator rulings (2026-11-10)

The operator asked for this experiment; whether to write the queue at all is decided by the probes, not asked. Flag naming and the state machine are engineering choices. The consent questions were decided on 2026-11-10 (plan section 7):

- (a) One host-wide setting, off by default; no per-session switches in v1.
- (b) Paid user-role wake turns are allowed narrowly, as an exception to ADR 0007/0004: fixed text only, at most one open wake per thread, only while the setting is on, only for immediate sends from verified senders.
- (c) A wake row already written may fire once after disable, upgrade or resume; CrossTalk writes no new row; the user docs must say so.
- (d) v1 deletes no wake rows; stale-row cleanup is deferred.
- (e) R183: a prompt the user queues in the Codex TUI is not in the queue table and is folded into the wake turn as a steer at 0.167.0; accepted and documented, not a reject condition. No claim that the user's queued item is never reordered.
- (f) R183: `kill -9` at the moment of consumption loses the wake (Codex does not redeliver); accepted and documented. The mail stays `mailboxed` and pullable; the generation ends `unknown`, with no replay.
- (g) R191: mark on pull replaces causal settlement. `delivered` at pull; `confirmed` by a `reply` (any time) or a second pull; monotonic; no token, no `ack`; a wake for `mailboxed` entries only. R189 is subsumed; debounce of a transient second opener is built at step 1 and coalescing of `failed` generation records at step 4.

## Trial record

- Council verdict: a bounded feasibility spike first, then at most an experimental opt-in capability (chair's synthesis, accepted by the coordinator). Sat: five advisors over two rounds, four Claude and one Codex; all rated the Codex executor's position strongest.
- Rests on: ADRs 0004, 0006, 0007, 0008, 0012, 0014, 0026 (provisional).
- Commits: `git log --grep 'Provisional-ADR: 0028'` (none).
- Reviews: council chair critique (six points, all fixed), a one-shot Codex adversarial review (two high findings, both fixed) and the chair's final precision fixes (evidence, authentication, route table, gate order); dispositions in plan section 11.
- Manual trials on 0.167.0 (before any product code): idle thread, a plain "hello world" row started a turn; idle advisor thread, fixed wake row → `receive_message` → `send_message` (not `reply`), row removal verified; busy thread, rows persisted and mail was pulled by hand, dispatch not shown.
- Step 0 re-run at Codex 0.171.0 (2026-11-20, operator ruling): probes 1 to 15 re-run in a disposable `CODEX_HOME`; every probe behaved as at 0.167.0, including the two flags (probe 6 wake lost on kill -9, probe 9 operator-queued prompt folded into the wake turn); a fresh 0.171.0 queue database has the pinned schema digest and migrations. That re-run first grew a version allowlist (`QueueTestedMinors`); on 2026-11-21 the list was replaced by the version floor `QueueMinVersion` 0.167.0, pinned by `TestQueueVersionFloor` (ADR 0029). Per-probe results: `docs/plans/codex-no-daemon-queue-step0.md`, section "Re-run at Codex 0.171.0".
- Step 7 live acceptance run (2026-11-20 and 21, Codex 0.171.0, macOS, a real `codex --no-daemon` session, binary built from main plus the fix in #163; the first attempt on the unpatched main build is item 1):
  1. **Owner proof failed closed on a revoked fd (found by the run, fixed in #163).** On the main build the claim of the real session was never accepted (`ownerproof: open files of <pid>: no such file or directory`), so a send was `unreachable` and no wake row was written. Cause measured: `proc_pidfdinfo` returns `ENOENT` for a revoked vnode fd of the managed daemon's `codex-code-mode-host` (the per-pid fd list succeeds, only the per-fd lookup fails), and `openersAmong` skipped `EBADF` and `EPERM` but not `ENOENT`. The fix skips `ENOENT` per fd; a failure to list a process's fds still fails closed. This first C1b is kept as a FAIL with that cause.
  2. **C1, an `ask` to the idle session: FAIL, by design.** `pickRoute` returns `ErrAskNotQueued` (`rejected/no_endpoint`) for an ask whenever the queue capability holds (plan 3.1: asks stay refused until step 7 passes). Follow-up, not built here: accept asks on the queue route (row 4 and 5 of plan 3.1) now that the other trials pass, with its own test and review.
  3. **C1b, an `inform` to the idle session: PASS on the receiver side.** Result `mailboxed`; one wake row written, taken within 3 s; one turn called `receive_message` and `reply`; receiver journal `mailboxed`, `delivered` at the pull, `confirmed`; wake generation `collected`; the reply reached the sender. The sender's own result read `unknown`; the sending shim was the older Homebrew 0.2.1 build, which has no queue code, so sender-side settlement was not shown with a current sender (see Not covered).
  4. **C2, busy session: PASS.** An inform sent mid-turn (the operator's 700-line list turn) wrote one wake row that waited in the queue until the running turn completed normally (no abort), the wake turn started 11 ms after it, one generation, then the pull and reply worked. Earlier attempts to put the session mid-turn with `hc send` text failed because the session held that input for peer approval.
  5. **C3, pull then final answer with no further call: PASS on the receiver side.** The receiver's delivery ended `delivered` (never `confirmed`; the sender, the old 0.2.1 build, read `unknown` and never `accepted`, but it read `unknown` in the reply case too, so this does not discriminate), the generation closed `collected`, and no second wake row was written.
  6. **C4, owner proof: PASS both halves.** The real session's `list_agents` row carried `delivery_mode` `queue-wake (experimental)`; the production proof run against live process ids returned proven for the `--no-daemon` parent and `ErrPooled` for a pooled `codex app-server` parent.
  7. **C5, setting off: PASS.** With the setting file removed, an ask was `rejected/no_endpoint` and an inform `unreachable` (the hint unchanged), no wake row was written and no new generation opened. Entries kept as `unreachable` stay pullable and were pulled by a later wake, as the pull contract says.
- Follow-ups from the run (none built here): (a) accept asks on the queue route; (b) observed, cause not investigated: `crosstalk uninstall codex --yes` run from a binary copy under `~/.local/bin` also stopped and removed the remote-gateway login unit (`dev.getcrosstalk.remote.plist`), whose service ran the Homebrew binary, while Claude Code still registered that Homebrew binary; `TestUninstallNamedLastHarnessRemovesUnit` requires removal when Codex is the last registered harness and `TestUninstallKeepsUnitWhileBinaryKept` keeps the unit while a registration of the binary remains, so whether this was intended cleanup or a gap in how "last" is judged for a second binary path is open; (c) `uninstall` leaves the Codex trust record for the removed hook (`[hooks.state.\"...hooks.json:session_start:...\"]`) in `config.toml`; (d) open question: the `--no-daemon` test session held `hc send` input (wrapped as a peer message) for approval, even for a trivial command, which is why C2 needed the operator to type the busy turn.
- Not covered by this run: the sender's side with a current build at both ends (an `ask` settling `accepted` after the reply, and an inform ending at `mailboxed` for a no-reply case) — the gate for asks and for calling the route usable stays open until that is run; wake lost on `kill -9` and the operator-queued prompt folded into a wake turn (the two flags from step 0, unchanged on 0.171.0); a Linux run (the route is macOS only).
- Pinning test: none yet; the feasibility probes (plan section 5, step 0), the isolated prototype (step 0b) and the live acceptance run (step 7) are the gates.
- Outcome: step 7 run once; C1 failed by design; C1b, C2, C3, C4 and C5 passed on the receiver side after the owner-proof fix in #163. Sender-side settlement with a current sender, and asks, remain open; the route stays experimental and opt-in.
