# ADR 0021 — Remote transport and enrollment: a user-started per-host gateway with pinned mTLS and two-sided pairing

- **Status:** Provisional (operator 2026-11-06); built in 0.2.0; run live on 2026-11-08 between a Mac and a Linux VM over a Wi-Fi LAN with a build from main (pairing, both directions, settle, the login unit through a reboot); not run over a tailnet, a wired LAN, or with the signed release binary
- **Date:** 2026-11-06
- **Deciders:** operator + council (Claude Opus 5.5 chair, two Codex advisors) + Claude (Opus 5.5)
- **Context source:** council decision 2026-11-06 (`~/.claude/coordinators/archive/council-decision.md`, raw positions beside it); operator rulings 2026-11-06; change plan [`docs/plans/release-0.2.0.md`](https://github.com/GoodOlClint/CrossTalk/blob/main/docs/plans/release-0.2.0.md)

## Context

CrossTalk is same-machine only: each agent's A2A server binds `127.0.0.1:0` (`internal/a2a/server.go:206`), and a sender proves who it is by holding a 0600 file on the receiver's disk (`server.go:443-481`). The operator runs Claude and Codex every day on a laptop, a desktop and a Linux homelab VM, and wants their sessions to message each other over the LAN or a tailnet (Tailscale private network). Remote means the same user's own machines only, not cloud sessions and not other people. The operator ruled that any server component is opt-in and never installed or started by default, that the login unit is in v0.2.0, that `crosstalk install` gets an optional way to turn remote on, that the default port is 7745, and that v0.2.0 assumes static IPs. The pinned a2a-go v2.7.0 client takes a custom `http.Client`, but its server interceptors see only headers, so TLS must end in front of the SDK. In Go, `tls.Config.VerifyPeerCertificate` does not run on resumed connections; `VerifyConnection` does.

## Decision

- **Gateway.** One HTTPS listener per host, run by `crosstalk remote serve` in the foreground or by an opt-in login unit (`crosstalk remote enable`, or `crosstalk install --remote`, or a yes to install's interactive question, whose default is no). Nothing is installed or started by default. It binds one configured IP (`remote config --bind`; a wildcard is refused except in all-addresses mode, below), port 7745 by default. Per-agent A2A servers stay on loopback unchanged; no shim listens off loopback and no shim spawns the gateway.
- **Forwarding.** The gateway authenticates the remote host, deletes every inbound `X-CrossTalk-*` header, sets its own (host fingerprint, the alias from its own peers file, the sending host's attested agent fields after validation), resolves the target agent in the local registry (never from a URL the caller gives), and forwards `SendMessage` and `GetTask` only to that agent's loopback A2A server with a gateway credential (`~/.local/state/crosstalk/gateway.token`, 0600). The loopback server runs the receiver chain as for any message; the gateway never injects.
- **Outbound.** A sending shim dials the peer's gateway directly with the host's client key and pins the peer's fingerprint.
- **TLS.** TLS 1.3 only; one self-signed ECDSA P-256 key and certificate per host (`~/.config/crosstalk/host.key` 0600, `host.crt`), used as both server and client certificate; pinning by sha256 of the public key in `VerifyConnection`; session tickets off; the pin re-checked against the current peers file on every request so `unpair` refuses requests on open connections; size, connection and per-host rate limits and whole-request, response and idle deadlines before parsing; unenrolled connections (only while a pairing is pending) in a separate pool of 4, each closed after 15 s; at most 16 connections still in the handshake, extra ones closed at accept. `remote serve` holds a lock so one gateway runs per host, and `uninstall --purge` refuses while it is held.
- **Pairing.** Two-sided, once per pair of hosts. `crosstalk remote pair` on host A prints a token (A's bind address and port, A's fingerprint, a 32-byte secret valid 10 minutes, single use). `crosstalk remote join` on host B reads it from stdin, checks A's fingerprint, and proves the secret with an HMAC over both fingerprints, naming the pending entry by an id in the token, B's taken by A from the handshake, so the secret binds B's key. B sends its own bind address. A keeps the secret itself (the HMAC key) in a 0600 pending file and redeems it atomically under a lock; both record each other in `~/.config/crosstalk/peers.json` (alias, address, fingerprint). Only `POST /v1/pair` accepts an unenrolled certificate, and only while a pairing is pending. A failed proof never cancels a pending pairing (attempts are rate-limited instead). Pairing again for a known fingerprint updates its alias and address.
- **Addresses.** Static IPs: a host's address is its bind address, exchanged at pairing. A moved host shows `unreachable`; pairing again is the fix. Amended 2026-11-21 (operator rulings on issue #159, R226); the rest of this bullet is the amendment and each part says whether it is built:
  - **Bind modes (built, PR c).** `remote config` picks one of two modes: one address (today's behavior) or all local addresses, chosen with `--bind all`, which stores `bind` as `::` (a dual-stack wildcard) and listens on it at the configured port. A literal `--bind 0.0.0.0` or `--bind ::` is still refused, and so is a wildcard in `--advertise`, in a pairing token and in a stored peer address; only `all` selects the mode. All-addresses mode requires `advertise`: `remote config` without it exits 2, and `LoadConfig` refuses a `remote.json` with a wildcard `bind` and no `advertise` (a hand-edited file too), so `AdvertiseAddr()` is never a wildcard. Only the canonical `::` loads as a wildcard bind: a hand-edited `0.0.0.0` or `::ffff:0.0.0.0` is refused, because Go would listen on it dual-stack anyway and a mapped form would read as a missing address. When `remote config` refuses for the missing `advertise` and this host has a tailnet address (`100.64.0.0/10` or `fd7a:115c:a1e0::/48`), the refusal prints it as a suggestion; it is never applied. A wildcard gateway never waits for an address (no re-bind loop, `AddrPoll` skips it), `remote status` and the readiness probe try both loopbacks for it (an IPv4-only host serves the wildcard on IPv4 alone), and `remote status` shows `bind` as the wildcard and `advertise` as the configured value. Going back to single-address mode is `--bind <address>` with the usual interface check; `remote enable` restarts an installed unit whenever bind or port changed, since a running all-addresses gateway answers the loopback probe of a narrower bind.
  - **Re-bind in place (built, PR a).** In single-address mode a running gateway checks this host's interface addresses every `Limits.AddrPoll` (10 s by default). When its bind address is gone it closes the listener and every connection on it, sets the state `service running, waiting for address`, and goes back into the bind retry loop (the 10 s retry of `Limits.BindRetry`, no give-up for a missing address). It recovers by itself when the address returns. It works for a foreground `remote serve` with no login unit. A port held by another program still ends the gateway after 60 s.
  - **`remote status` (built, PR a).** With the lock held and no listener of ours on `bind:port`, status reads `service running, waiting for address` when the bind address is not an address of this host, and `service running, port not bound` otherwise. `running` and `not running` are unchanged.
  - **K8 (built, PR a).** While the gateway waits for its address K8 is one warning (`WarnOnly`) naming the cause (the bind address is not on this host), saying the gateway recovers when the address returns, and naming the fix: wait, `remote config --bind` with a current address, or `remote config --bind all --advertise <tailnet address or name>` (built, PR c). A wildcard bind is never reported as missing from the interfaces, and K8 messages name it as `all addresses, port N`. K8 fails only when a login unit exists and no gateway process holds the lock.
  - **Advertise address (built, PR b).** `remote config --advertise <addr>` is the address peers dial, put in the pairing token and sent at join; `remote config` and `remote status` show it. It is stored in `remote.json` next to `bind`, and a config with no `advertise` value reads as the bind address, so single-address setups do not change. Changing it lists the peers that still hold the old address, as a changed bind does. It is required in all-addresses mode, where `remote config` suggests a tailnet IP when it finds one (built, PR c).
  - **Hostnames (built, PR b).** `--advertise`, the address in a pairing token and stored peer addresses accept an IP or a syntactically valid DNS name (MagicDNS, `.local`); empty, wildcard, multicast, zone, scheme, path, port and whitespace are refused, and a name is lowercased. Peers dial through `DialPeer`, which resolves a name on every connection, never at pair time. The fingerprint pin is the trust and is unchanged (TLS verification and the pin logic are not touched), so a changed IP behind an unchanged name needs no new pairing. A peer whose advertised name or IP really changes pairs again. The bind address stays one IP, and the no-wildcard check applies to it only. A live address refresh from a pinned peer stays deferred.
  - **Docs and help text (built, PR d).** `docs/setup.md` ("Choose an address", "When a host changes networks"), `docs/how-it-works.md`, `docs/faq.md` and the `remote` usage text describe the three address setups (fixed IP, `--advertise` with one bind, `--bind all --advertise`), what a change of network does in each, that the pin is the only trust, and that the CGO-free Linux release cannot resolve a `.local` name served only by Avahi's NSS module. The usage text recommends a tailnet advertise name or `100.64.0.0/10` address. `remote enable` takes no `--advertise`: all-addresses mode there needs the value stored first by `remote config`.
  - **Address-change nudge (planned, PR e, after a and b).** When this host's gateway address changes, sessions on this host and sessions on paired hosts get a visible message in their transcript. A paired host gets it only if it can reach the new address.

## Rejected alternatives

- **Gateway elected by `flock` inside whichever shim wins.** Ties the host's listener to an arbitrary session's lifetime; a pooled or hung holder never yields; no listener after the last shim exits (both advisors and the chair).
- **SSH-carried messages.** Needs inbound sshd on every Mac, and the sender's login key gives a shell, far more than messaging.
- **Tailscale identity as the base.** Does not cover a plain LAN; "same Tailscale login" is not device enrollment. May come later as an extra admission check, never the only one.
- **A relay on one host.** An always-on central router and a central impersonation point, against ADR 0001; not needed on a LAN or tailnet.
- **An always-on discovery daemon by default.** Forbidden by the operator ruling.
- **A certificate authority.** Pins are simpler for one user's few machines and need no issuance or revocation lists.
- **The pairing token as a command-line argument.** It would land in shell history.
- **`VerifyPeerCertificate` for the pin.** Skipped on resumed connections.
- **Address-change handling (mDNS refresh) in v0.2.0.** Static IPs are assumed by ruling; an mDNS broadcast that updates an already-paired fingerprint's address is v0.2.x and never adds trust.

## Consequences

- A new network listener exists whenever the user turns remote on. It is off by default, bound to one address, and refuses unpinned clients in the handshake.
- CrossTalk owns key and pairing code. Revocation is manual and per host: `unpair` on each side. A lost or reset key means pairing again with every peer; `uninstall --purge` lists them.
- `crosstalk install --check` gains K8; `uninstall` removes a login unit CrossTalk wrote (identified by a sha256 stored in `remote.json`), and `--purge` removes `~/.config/crosstalk`.
- macOS Local Network privacy and the firewall may prompt or block; spike S2 records what the user must do, and setup.md documents it.
- Spikes S1, S2, S3, S4, S5, S6, S7 in the change plan gate the slices; a failed S7 goes to the operator, since the login unit is in v0.2.0 by ruling.
- ADR 0006 is amended to allow the user-started gateway and its login unit; ADR 0001 to name the gateway a per-host forwarder.
