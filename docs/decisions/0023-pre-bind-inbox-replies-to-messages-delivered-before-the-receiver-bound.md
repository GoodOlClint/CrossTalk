# ADR 0023 — Pre-bind inbox: replies to messages delivered before the receiver bound

- **Status:** Provisional (operator review pending, 2026-11-07); not built
- **Date:** 2026-11-07
- **Deciders:** operator (pending review) + Claude (Opus 5.5) + Codex review
- **Context source:** issue #41 (dogfood); PR #57 (pre-bind hint); triage of #41 part (b), operator ruling to draft an ADR for a pre-bind inbox and review it before any code

## Context

A session with no CrossTalk binding can still receive an `inform`: when the target resolves to a native session and to no descriptor, the sender's shim injects the message through its own harness adapter (`internal/shim/send.go`, the `tgt.Native` branch of `deliver`; design §12 S5). `ask` and `command` to such a target are `rejected/native_inform_only`, so only informs take this path. The receiver's shim does not exist yet, or has not registered the agent, so the receiver's journal never gets the dedupe record or the reply route for that message. The message still shows in the receiver's conversation with a `message-id`. When the receiver binds and calls `reply` with that id, `inbound` finds no dedupe record and `reply` returns `no_such_message`; since PR #57 the hint says the message may predate the binding. The model then has to `send_message` the sender by name, or tries Claude's native SendMessage, which ADR 0009 bounces.

The sender already knows everything the receiver's journal would have held: the message, its own agent_id, the target's binding (harness, session_ref) and therefore the target's future agent_id (`identity.AgentID(harness, session_ref)`, a fixed hash), and the delivery state. What is missing is a way to hand this to the receiver's shim that does not let any process write reply routes into an agent's journal.

## Decision

1. **Write.** After a native inject of an inform returns `accepted` or `queued`, the sender's shim appends one entry to the pre-bind inbox of the target, keyed by the target's agent_id. Nothing is written for any other state, for a registered target (it gets the message through A2A and journals it itself) or for an inject that failed. An entry is one JSON line: `v`, the target's `agent_id`, `harness` and `session_ref`, the sender's `agent_id`, the full message (as journaled on the sender's outbound record), `delivered_at` (sender clock), the delivery state, and `mac`. A failed inbox write does not change the send result's state; the result adds a hint that a `reply` from that session may not find the message.
2. **Authenticate.** `mac` is HMAC-SHA256 over the entry's other fields in canonical order, keyed with the sender's own agent token (`~/.local/state/crosstalk/tokens/<sender agent_id>.token`, design §5). The receiver verifies it by reading the token at exactly that path for the claimed sender agent_id, as A2A own-token verification does, and compares in constant time. It also requires that the inbox file is a regular file (opened with no-follow), mode 0600, owned by the current uid, inside a 0700 directory, and that the entry's target agent_id, harness and session_ref equal the receiver's current binding. A failed check drops the entry and logs the reason; it is never replayed. The token never leaves its file; the entry carries only the MAC. This gives the entry the same strength as the sender's A2A bearer credential: it proves the writer can read that agent's 0600 token, and no more (ADR 0004 Consequences, design §1 non-goal).
3. **Replay.** When an agent registers, after journal replay and under the same name lock, its shim claims its inbox file by renaming it to a private name (so a concurrent writer starts a new file), verifies each entry, drops every entry whose message_id appears in another verified entry with a different sender or already has a dedupe record from a different sender (a message id names one message, and `reply` looks it up by id alone), and for each remaining entry whose (sender, message_id) has no dedupe record appends to its own journal (fsynced) a dedupe record with the message, the sender key = the sender's agent_id and the entry's delivery state, then opens an inform route through the receiver's normal `openRoute` with the open time set to `min(delivered_at, now)` on the journal clock. It then deletes the claimed file. Replay never injects, never re-delivers and never answers: the message already reached the conversation. A crash between the journal append and the delete is safe because the dedupe record makes a second replay a no-op.
4. **Late entries.** A sender that resolved the target as native just before it bound can write an entry after the receiver's replay. So when `reply` finds no dedupe record for a message id, it drains the inbox once more (the same claim, verify, replay) before it returns `no_such_message`. No timer and no file watch.
5. **Route lifetime and dedupe (ADR 0010).** A replayed route is an ordinary inform route: it expires `InformRouteTTL` (1 h) after the sender's delivery time, not after the bind, so waiting for a bind never extends it; and it takes one reply, through the existing obligation path, with `already_replied` and the byte-identical retry rules unchanged. An entry older than `InformRouteTTL` at replay is deleted without replay; `reply` to it gives the pre-bind hint as today. There is no ask on this path, so no ask deadline runs while a message waits for the bind. If native targets ever accept `ask`, that needs its own decision on whether the deadline runs on the asker's clock while the target is unbound.
6. **Storage and caps.** `~/.local/state/crosstalk/inbox/<target agent_id>.jsonl`, directory 0700, files 0600 created exclusively or appended with no-follow under an advisory lock. Per target at most 64 entries and 4 MiB; a write over either cap is skipped (the newest message loses its route, older ones keep theirs) with the send hint from rule 1. Every write and every replay sweeps the whole inbox directory: an entry older than `InformRouteTTL` is useless, so a file whose last write is older than that is deleted. A target that never binds therefore leaves nothing behind longer than about an hour after the last message to it, as soon as any shim sends a native inform or registers an agent. The inbox is never read by `list_agents`, `receive_message` or the bounce.
7. **Remote (ADRs 0021, 0022, planned for v0.2.0).** Only a local shim's own native send path writes the inbox. The gateway never writes it, and a remote sender cannot reach a native session (`rejected/remote_native_unsupported`), so no cross-host message takes this path. Replay accepts only an entry whose sender agent_id has a local token file; an entry naming a `remote:` key or `local-user` is dropped. `crosstalk send` and other peer-token clients never reach native sessions, so they write no entries.

## Rejected alternatives

- **Keep the hint only (status quo after PR #57).** The model is told why `reply` failed but still has to `send_message` the sender by name, which works only while that name resolves to the same session (#54) and costs a round of model work for every message sent before a bind. It is the fallback when the inbox entry is missing or dropped, not the design.
- **The receiver pulls from the sender's journal on bind.** The receiver does not know which agents sent to it, so every bind would scan every journal for outbound records addressed `<harness>:<session_ref>`. It reads another agent's private journal, couples the receiver to the sender's record format, retention and truncation, and has no answer for a sender whose journal was already trimmed. The inbox carries only what replay needs, keyed by the one id the receiver knows.
- **Trust the inbox file by mode and owner alone (no MAC).** Every same-user process can write a 0600 file in the user's state directory, including a `crosstalk send` script that is no registered agent. Without a MAC such a process could open a route that names any registered agent as the sender, which is sender identity from message content and breaks ADR 0004. The MAC makes the forger hold that agent's token.
- **Bind the receiver on delivery.** The sender's shim cannot create or register the receiver's shim; identity comes from the receiving harness per request (ADR 0006), and a binding made by another process would be exactly the cross-agent identity claim ADR 0004 forbids.
- **Key the inbox by name.** Names are per host, change at a successor (#54) and can be reused by another session; the agent_id is the fixed hash of the binding and is what the receiver's journal is keyed by.

## Consequences

- What a forged entry can do: a same-user process that can read some agent's token can open an inform route in a receiver's journal naming that agent as sender and any message id. Replay never injects, so its text never reaches the model. The route is listed in a bounce (ADR 0009) as an open inform, and a `reply` naming its message id sends the receiver's reply text to the named sender. The model replies only to ids it saw, so to redirect a real reply the forger must know a genuine message id before the receiver binds and must also suppress the genuine entry: when both are present, rule 3 drops both and `reply` falls back to the pre-bind hint. This is inside the accepted same-user non-goal (design §1, ADR 0004 Consequences); the harness's permission model stays the control on what a reply can cause.
- Design §5 (Journal) gains the inbox as a second source of dedupe and route records on registration, and §12 S5 gains the `reply` behaviour for native targets. The pre-bind hint from PR #57 stays for the cases the inbox does not cover (no entry, dropped entry, entry over the cap or older than an hour).
- The Claude and Codex paths are the same: the inbox is keyed by agent_id and written by shared shim code, not by an adapter (ADR 0008).
- Tests that gate the implementation: a native inform then a bind then `reply` succeeds and closes the route; a second `reply` with other text gets `already_replied`; an entry with a bad MAC, wrong binding, wrong mode, a symlink, or a sender with no token file is dropped; two verified entries with one message id and different senders are both dropped; an entry written after replay is picked up by `reply`; an entry older than `InformRouteTTL` is deleted and `reply` gives the pre-bind hint; caps skip the write and the send result carries the hint; a crash after the journal append and before the delete replays as a no-op.
- Implementation commits carry `Provisional-ADR: 0023`. Files: `internal/shim/send.go` (write, late drain), `internal/mcpserver/server.go` (register replay), `internal/journal` and `internal/receiver` (replayed dedupe and route), and a new small inbox package.
