# ADR 0010 — One reply per ask, routes close with their task, inform routes expire

- **Status:** Provisional (overnight 2026-11-04); llm-council verdict recorded below
- **Date:** 2026-11-04
- **Deciders:** session (overnight), llm-council
- **Context source:** Codex adversarial review of design 1.9, findings R4, R6, R7, R8 (design §13); §12 open item "reply-route lifetime"

## Context

An `ask` opens an A2A task on the receiver and a reply route in the receiver's shim. Today: every `reply(message_id, text)` call creates a fresh outbound message, so a retried tool call after a lost acknowledgement delivers a second answer (R4); a reply naming a continuation message id finds no task because only the first message id is indexed (R6); a deadline expiry changes the task state but leaves the route open, a late reply closes the route and can still report `accepted`, plain informs open routes that never expire, and the ADR 0009 bounce lists every open route without bound (R7); deadline suppression on the asker side scans journaled bodies for any `in_reply_to`, including policy-rejected ones (R8).

## Decision

1. One reply per task. The reply obligation, the idempotent-retry result and `already_replied` are keyed by the task; every message id of the task (the first message and each continuation) is a handle that resolves to it, and a `reply` naming any of them completes it. The association is rebuilt from task history on load; no new record type. Precedence (as implemented in s18b, because a successful reply is what makes the task terminal, so a plain terminal-first rule would deny the idempotent retry): a closed obligation → `ask_closed`; an existing obligation with byte-identical text → the stored result, or resume if it is still pending; different text on a terminal task → `ask_closed`; different text on an open task → `already_replied`; no obligation on a terminal task → `ask_closed`. `CompleteAsk` with the same text on an already-completed ask is idempotent so a resumed obligation does not misreport. The stored result is the durable journal obligation (body included), read before any new append under a per-agent lock; a retry that finds a pending obligation (crash mid-flight) resumes forwarding and completion rather than echoing it. Multiple intentional answers are plain `send_message` informs.
2. The terminal check runs before the obligation is journaled; the route closes only after task completion succeeds, and route closes happen outside the task store's lock.
3. Routes follow their task. An ask route closes when its task reaches a terminal state (completed, failed by deadline, canceled); the deadline timer and a reply race under the task-state compare-and-set. A `reply` to a terminal ask returns `ask_closed` with text telling the model to `send_message` its answer instead, and sends nothing. Inform routes expire one hour after their journaled open time (journal clock, re-armed on replay; `InformRouteTTL` constant). The expiry bounds journal and restart state; the bounce cap bounds the bounce text: the bounce lists every open ask route, then the ten newest inform routes, then a count of omitted informs. No pointer to `receive_message`, which excludes accepted entries.
4. On the asker's side, a reply counts as received only when a reply-receipt record exists. Validated means: the inbound reply passed policy and admission, its sender agent id equals the peer the ask was sent to, its `in_reply_to` names an outbound ask of this agent, and its `context_id` equals that ask's. Native frames never count. On replay of a journal written before this record existed, a journaled reply body from the expected peer with the same `context_id` is accepted as a legacy receipt. Deadline suppression and `replied` read receipts only.

Implementation notes (s25, 2026-11-04, Codex finding WA5/WA8/WA10): the reply obligation is a staged transaction journaled as `pending` → `completed` (task completed through the hook) → `released` (route closed) → `delivered`; each stage is appended before the next starts, a failed hook returns `unknown` with the hook error and leaves the obligation `pending`, and the normal call, the byte-identical retry and startup replay all resume from the latest journaled stage. There is no `forwarded` stage: an outbound record already `accepted` or `queued` is the forward's evidence and is not re-sent. Replay includes local-user obligations and starts only after the descriptor is published (`mcpserver.Publisher`). The legacy receipt fallback accepts only dedupe states written after admission (`accepted`, `queued`, `unknown`); `submitted`, `rejected`, `canceled`, `bounced`, `unreachable` never count. A reply through a continuation handle carries the task's first message id as `in_reply_to` (and its context id), so the asker's receipt and deadline key off its outbound ask; `askedPeer` is unchanged.

Implementation notes (s26, 2026-11-04, Codex finding WA6/WA7/WA9): retention counts an outbound ask as answered only through a receipt record from the asked peer or an admitted `crosstalk` expiry notice naming it, never through reply bodies or `in_reply_to` fields; journals without receipts keep their asks. Open routes of a non-ask kind older than `journal.InformRouteTTL` on the journal clock are treated as closed by retention, and `openRoute` sweeps expired inform routes on every inform admission. A continuation is written to task history (`submitted`) and indexed as a handle under the store lock before delivery; its settled state is a second record, a rejected continuation is removed and journaled `rejected`, a duplicate retry repairs a failed post-injection write, and `askClosed` runs again after a receive that made the task terminal. Rule 1's "no new record" therefore holds for record types but not for record count.

## Rejected alternatives

- Allow repeated replies and dedupe on the receiving side: the receiver cannot tell a retry from a second answer because each `reply` mints a new message id.
- Keep inform routes open indefinitely: unbounded growth of the bounce list and of restart state; an inform nobody answered for an hour is not a conversation the model will resume by name.
- Expire ask routes on a timer independent of the task: two clocks for one fact.
- Decide route lifetime per harness: the route is shim state, not harness state (ADR 0008).

## Consequences

- `reply` gains two error reasons, `already_replied` and `ask_closed`; design §8 and tests 5 and 13 change; `TestReplyRoutesThroughJournal` currently pins the opposite of rule 1 and is rewritten.
- The journal gains a reply-receipt record type (asker side); continuation-to-task associations are rebuilt from task history, no new record. The legacy receipt fallback on replay also requires that the body was admitted, not rejected. A `noticed` check (a journaled deadline notice from `crosstalk`) keeps a restart after expiry from re-sending the notice.
- An inform route that expired makes a later `reply` to it return `no_such_message`; the model can still `send_message` by name.
- Implementation commits carry `Provisional-ADR: 0010`.

## llm-council verdict (2026-11-04, overnight)

Five advisors (Contrarian, First Principles, Expansionist, Outsider, Executor; Sonnet) read the ADR, the Codex findings and the code; the session acted as chairman without the anonymized peer-review round (deviation recorded in the overnight report). Verdict: implement with stated changes, all folded into the Decision above: key by task not message id (First Principles, Contrarian, Outsider); durable obligation read on retry and resume of pending obligations (Contrarian, First Principles, Outsider); terminal check before the append and route close after success (Executor); `ask_closed` salvage text (Expansionist, Contrarian); receipt validation defined, native never counts, legacy fallback on replay (Outsider, Contrarian, First Principles); journal clock for expiry (Contrarian, Outsider); bounce lists asks first and caps informs, no `receive_message` pointer (Contrarian); which limit bounds which resource (First Principles). Dissent: the Executor would defer rule 4 to its own ADR because its definition was missing; the chairman kept it with the definition written in and ordered it last (commit C) so it can be dropped alone. Commit order: A ask-route close and `ask_closed` (R7); B task-keyed reply and continuation handles (R4, R6); C receipt record (R8); D inform expiry and bounce cap (R7).
