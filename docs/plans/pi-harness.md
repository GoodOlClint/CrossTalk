# Change plan: Pi harness

Status: approved by the operator 2026-11-24 (brownfield gate, issue #275, parent #272); the build starts at slice 0. Decision records: [ADR 0035](../decisions/0035-pi-harness-ships-as-an-embedded-pi-extension-that-registers-the-mcp-server.md) (scope, shipping, versioning, install), [ADR 0036](../decisions/0036-pi-session-identity-is-proven-by-the-parent-pi-process-over-the-shim-s-socket.md) (identity and the channel), [ADR 0037](../decisions/0037-pi-delivery-is-a-custom-session-message-and-raw-peer-text-only-from-a-verified-local-agent.md) (delivery and trust). Template: [OpenCode plan](opencode-harness.md). Evidence: section 2 "Measured" (2026-11-24), [spike 11](../spikes/11-harness-landscape.md).

Terms. **Pi** = the Pi coding agent, npm `@earendil-works/pi-coding-agent` (1.6.0 installed by Homebrew and measured here; Node 22.19 or newer). **Agent dir** = `$PI_CODING_AGENT_DIR` or `~/.pi/agent`, where Pi keeps `settings.json`, `mcp.json`, `extensions/` and `sessions/`. **Extension** = a TypeScript module Pi loads in its own process (through jiti, no build step) that gets the `ExtensionAPI` (`pi.on`, `pi.sendMessage`, `pi.registerMcpServer`, `ctx.sessionManager`). **Custom message** = a message added with `pi.sendMessage`, shown in the TUI under its `customType` label and sent to the model as user-role text. **Steer** = joins the running turn before the next model call; **`triggerTurn`** = whether an idle session starts a turn. **Exposure** = how Pi shows an MCP server's tools to the model: `codemode` (Pi's default: the model writes a script that calls them), `direct` (first-class tools), `deferred`, `hidden`. **Hello** = the first line the extension sends on its connection to the shim. **Peer pid** = the pid of the process at the other end of a unix socket, from the kernel (`LOCAL_PEERPID` on macOS, `SO_PEERCRED` on Linux). **Shim** = the `crosstalk mcp` process. **Receiver chain** = authenticate, dedupe, hop-chain, policy, inject. **Slice** = one test-pinned commit or PR. **K-check** = a numbered check of `crosstalk install --check`. **M** = a pre-build measurement (section 7). **L** = a live-run check (section 8).

## 1. Goal

A Pi session appears in `list_agents`, sends, and receives `inform`, `ask` and `reply` from Claude Code, Codex and OpenCode sessions in a live run. `crosstalk install pi`, `uninstall pi` and `install --check` cover it, the scheduled compatibility check (ADR 0029) includes it, and setup docs name the supported version. That is the done-when of issue #275.

Binding constraints: one Go package behind `harness.Harness` (ADR 0008); delivery through the receiver chain; a native API only, no keystrokes and no screen scraping; CrossTalk spawns and wraps nothing (ADR 0006). New here: part of the harness is a Pi extension that `crosstalk install` writes (ADR 0035).

## 3. Decisions

Each item has a recommended answer; the operator reviews all of them; the three ADRs record the architecture. Items marked *measure* have a check in section 7.

**D1. Supported line. Pi 1.x, 1.6.0 tested (ADR 0035).** `TestedMajors = {1}`; an untested minor warns in K14 and in the descriptor's `harness_version`; another major or an unparseable version refuses the hello. The compat job watches minors (ADR 0029).

**D2. Shape: a Go package plus one embedded extension that registers the MCP server (ADR 0035; operator, Q2).** `internal/harness/pi` with `ext/index.ts` embedded. Install writes `<agent dir>/extensions/crosstalk/index.ts` with the binary path and version filled in. The extension calls `pi.registerMcpServer("crosstalk", {command, args: ["mcp"], env?, exposure: "direct"})` at load, so Pi spawns the shim with its other servers. No `mcp.json` entry.

**D3. Identity (ADR 0036).** The shim listens on `~/.local/state/crosstalk/sock/pi/<parent pid>.sock`; the extension connects from `session_start` in the background (the handler returns at once: Pi awaits each `session_start` handler in turn, `runner.js:832`, and starts MCP connections in its own handler afterwards, so a blocking handler would keep the shim from ever starting); the shim accepts only a peer whose pid is its parent **and** whose parent is a Pi host (the parent's command name is exactly `pi`, which Pi sets as `process.title`, `cli/setup.js:4`, checked through `ps` like K11, plus `PI_CODING_AGENT=true`); the hello carries `{proto: 1, token, ext_version, pi_version, session_id, session_file, cwd, name}`, where `token` is a random value the extension instance generates at load and passes to this server registration only (`env.CROSSTALK_PI_TOKEN` in `registerMcpServer`), so the connection is bound to the shim that registration started. `ServeClaims` registers the session at the hello. The session id follows Pi's own rule (`session-manager.js:15`: alphanumerics, `.`, `_`, `-`; `--session-id review-1` is valid), not UUID only. Because `--session-id` is scoped to a directory (`cli/args.js:304`) and CrossTalk keys on (harness, session ref), the session ref is `<session id>@<first 8 hex of sha256(session file path)>`, or the bare id when there is no file (`--no-session`); the file path is stable across `/resume`. `Identify` claims a call only for the proven parent with a held hello. A call before the hello, or a shim whose parent is not Pi, is unbound. Trust order: after Codex and OpenCode (explicit `_meta` ids), before Claude; Claude's parent-pid claim never matches a Pi pid, so order is not load-bearing.

**D4. Discovery and end.** Every shim's `Discover` lists the live Pi sessions, not only its own: a descriptor-only row has `reachable: false` and an empty status (`internal/mcpserver/discovery.go:136-149`, exported the same way to paired hosts by `internal/shim/remote_list.go:128`), so a Pi session listed only from its descriptor would look dead to every other session. The package gets the registry directory (the `HarnessOptions.Directory` pattern of Codex and OpenCode); the owning shim keeps a status file `sock/pi/<parent pid>.status` (`connected`, `busy` or `idle`, updated on each status line and removed at exit, 0600); `Discover` returns each Pi descriptor whose shim pid and Pi pid are alive with `Reachable` = connected and the status from that file, and nothing for the others. `Register` refuses (no Pi session without CrossTalk is discoverable); no `Supersession`, since the shim ends with the session (E4). A hello for a second session id on one shim is refused and logged. Two Pi processes on one session file (measured, M4: Pi neither locks nor refuses, each has its own shim and socket and the same session id and file): the registry's live-holder rule applies (ADR 0036; `internal/registry/registry.go:144-154` keeps the live holder and returns `ErrAgentHeld` to the later claimant), so the second process's session is not listed; its shim answers the hello with an `{"error"}` line naming `agent_held` and closes the connection, and its extension shows that reason once in the footer and keeps retrying; no newest-process takeover.

**D5. Delivery mapping (ADR 0037).** `immediate` = `sendMessage(..., {deliverAs: "steer", triggerTurn: true})`; `next_turn` = `{deliverAs: "steer", triggerTurn: false}`. Never `sendUserMessage`, never `nextTurn`, never prompt-template expansion, never a system-prompt hook. Measured (E8, M3): an idle `next_turn` is shown with no turn; a busy `steer` + `triggerTurn: false` message is flushed at the `turn_end` of the running run (after that turn's whole tool batch), so it reaches the model at the next turn boundary if the run continues, and wakes nothing; `nextTurn` is memory only (a quit or `/new` before a later run loses it), which is why it is never used. **An `immediate` message to an idle Pi session starts a paid model turn**; setup docs say so.

**D6. Raw peer text (operator, Q1, ADR 0037 decision 4).** Raw text only from a verified local registered agent; remote senders, script senders and inbox copies get `mailboxed` plus the fixed wake through `MailSignal`, the body through `receive_message`. Stricter "mailbox everything" was offered for Pi's lack of approvals and not chosen.

**D7. Ack and state (ADR 0037 decision 5).** One frame per delivery, one answer per frame, a 10 s answer timeout, never re-sent. `pi.sendMessage` returns before Pi admits the message, and an extension cannot see a later rejection: the binding catches it and hands it to Pi's own listeners only (`agent-session.js:2871-2880`; M3 finding 2), so no extension-side error signal exists and the timeout is the only failure signal. What an extension can observe (M3): for `triggerTurn: true` (`immediate`, and the fixed wake) a `message_start` or `message_end` event for a custom message with `details: {crosstalk_id: <id>}`, fired in the same millisecond when idle and at the next turn boundary when busy; for `steer` + `triggerTurn: false` (`next_turn`) no event at all. So the extension answers: `immediate`: ok when the admission event arrives; `next_turn` to an idle session (`ctx.isIdle()` true when `sendMessage` returns): ok after an entry check, a `custom_message` entry carrying the id in `ctx.sessionManager.getEntries()` (in memory: Pi writes the session file only once a conversation exists), and that maps to `queued`; `next_turn` while `isIdle()` is false: the extension runs the same entry check after the send, since Pi also reports not-idle during compaction and then appends the entry synchronously (`agent-session.js:1131-1136`, `:1991`), so a matching entry confirms `queued` whatever the idle flag says; with no evidence by the deadline there is no answer and the state is `unknown` (`isIdle()` false alone proves nothing about the message). ok = `accepted` (`immediate`) or `queued` (`next_turn`); no connection = `unreachable`; `ok: false` after the write, no admission within 10 s, a drop or a malformed answer = `unknown`. An ok ack means Pi admitted the message, not that the model answered: with no model configured the fixed wake was admitted and the run started, then failed at the provider (`Unknown provider`). A busy `immediate` can be admitted after the deadline (21 s after the send in M3, while a 30 s tool call ran): the timeout has already answered `unknown`, and a late event must not re-send the frame or change a state already reported; slice 4 pins that. A synchronous stub cannot pin the asynchronous parts; the Node test drives a late admission event and a send that never produces one.

**D8. Tool exposure: `direct`.** The CrossTalk tools appear as first-class tools, so `ask`, `reply` and `receive_message` read as written in their descriptions, with no code-mode catalog in between (the OpenCode D9 concern). Cost: Pi waits up to 10 s for `direct` servers before the first prompt and then proceeds without their tools (measured, M5), so the shim must answer `initialize` first and do its slow startup work afterwards; the tool schemas take context.

**D9. Reconnect and refresh.** The extension reconnects with backoff (200 ms to 2 s) while the session lives (a connect loop that can never succeed, as with `--no-mcp` or a socket path over 104 bytes, retries silently, E6 and M4), so a shim re-exec (ADR 0030) costs one reconnect and needs no `Refreshable` state. If no shim answers within 30 s of `session_start`, the extension sets a footer status ("crosstalk: no shim", `ctx.ui.setStatus`) and keeps retrying every 2 s; it never notifies more than once.

**D10. Versioning and upgrade (ADR 0035 decision 4).** Lockstep with the binary. `PluginUpdater` rewrites the extension on the first shim of a new version (ADR 0031). The rewrite keeps the installed no-auto-refresh choice: the follow-up builds a fresh `InstallEnv` without it (`cmd/crosstalk/followup.go:58`), so `PluginStep` reads `CROSSTALK_NO_AUTO_REFRESH` from the existing file and carries it over. The follow-up marker for Pi is scoped to the agent dir: `markerKey` (`followup.go:38`) returns the bare harness name for everything but Codex, so two `PI_CODING_AGENT_DIR` profiles under one state dir would skip the second; slice 6 adds the agent-dir hash for a non-default dir, as Codex does for `CODEX_HOME`; running sessions pick it up at `/reload` (which also restarts their shim) or restart. Protocol mismatch refuses the hello with a reason the extension shows once; same protocol with an older extension works and K14 warns.

**D11. Native reply address.** None (`""`), as Codex and OpenCode.

**D12. Render.** The OpenCode envelope (preamble line plus one JSON object). Pi's package has its own `render.go`; the duplicated envelope builder with OpenCode is noted as a follow-up (lift to `internal/msg`), not done here, because that edit touches the OpenCode package (ADR 0008).

**D13. Session name.** From the hello (`pi.getSessionName()`, set by `--name`, `/name` or `pi.setSessionName`); a later change (`session_info_changed`) is sent as a name line. A `rename` pin wins (ADR 0027). An unnamed session gets the default name rule.

**D14. Not implemented:** `Supersession`, `NativeIngress`, `BackendChecker`, `DeliveryModer`, `Refreshable`, `Leftover`.

## 4. Package design

`internal/harness/pi`. Files: `ext/index.ts` (embedded extension), `ext.go` (embed, fill, marker), `listen.go` (socket, peer check, hello, frames, acks), `harness.go`, `inject.go`, `render.go`, `mailsignal.go`, `version.go`, `install.go`.

| Method | Behaviour |
|---|---|
| `Name()` | `adapter.Pi` (`"pi"`, new constant) |
| `ServeClaims` | Returns at once unless `PI_CODING_AGENT=true` and the parent pid is alive with command name exactly `pi` (the whole command, not a path or an argv pattern: `ps -o command=` and `-o args=` read `pi` on macOS and Linux, M4). Listens (0700 dir, replaces a stale file, removed at exit); per connection: peer pid must equal the parent pid, else close without reading; read one hello line (64 KiB limit, 5 s deadline); validate `token` (equals this shim's `CROSSTALK_PI_TOKEN`), `proto`, `pi_version` (D1), `session_id` (Pi's id rule); derive the session ref (D3); register through the `SessionRegistrar`; keep the connection as the delivery channel; on a later hello after a reconnect, accept only the same session id |
| `Identify` | `req.ParentPID` == proven parent and hello held → `Session{SessionRef: session_id, Name: name, Cwd, HarnessPID: parent pid}`; else `ok=false` |
| `Bind` | Same as `Identify`, plus `HarnessVersion` = `pi_version`, `HarnessEndpoint` = the socket path; not proven → `ok=false` |
| `Register` | Error: a Pi session is reachable only through its own shim |
| `Discover` | Every live Pi descriptor in the registry dir (D4): `Reachable` = the owning shim's status file says connected, `Status` = its busy or idle, from the lines the extension sends on `agent_start`/`agent_settled` (`agent_start` and `agent_settled` are the final-state events; `agent_end` fires before `agent_settled` and is not final, M3) |
| `Status` | `Loaded` = hello held; `Busy` from the last status line; `Reachable` = connection live |
| `Inject` | D6 class check first (non-verified-local → `mailboxed`, nothing written); else render, write one frame `{id, deliver: "steer", trigger, text}`, wait for `{id, ok}` (D7) |
| `MailSignal` | Frame with the fixed wake text, `trigger: true`; a failed signal changes no state |
| `Render` | Preamble plus JSON object (D12) |
| `Notice` | `msg.PeerNotice(c, fromHarness)` |
| `NativeReplyAddress` | `""` |
| `Installer`, `PluginUpdater` | Section 6 |

The extension (`ext/index.ts`, target under 150 lines): generate the token and register the server at load; on `session_start` start the connect loop in the background and return; on connect send the hello; on each frame call `pi.sendMessage({customType: "crosstalk", content: text, display: true, details: {crosstalk_id}}, {deliverAs: "steer", triggerTurn})` and answer when admission is observed (D7: an admission event for `immediate`, an entry check after every `next_turn` send, otherwise no answer); on `session_info_changed` send the name; on `agent_start`/`agent_settled` send busy/idle; on `session_shutdown` stop retrying and close. Every socket handler (data, connect, close, error) catches every error: an uncaught exception in one took Pi down in M4, so a malformed complete line is dropped and logged, never thrown. Input is buffered until a newline (a stream can split a valid line across data callbacks), and an unfinished tail is discarded on close. No rendering, policy or state.

Nothing in `internal/shim`, `internal/mcpserver`, `internal/a2a` or `internal/wire` imports the package (`arch_test.go`).

## 5. Trust and ADR 0004

Delivery is user-role text for the model (E9), the same position as Claude's channel and OpenCode's prompt; the TUI labels it `[crosstalk]` so the operator can tell it from their own typing. The rules:

1. Only `sendMessage` with `customType: "crosstalk"` and `display: true`. No `sendUserMessage`, no `expandPromptTemplates` (a peer cannot run `/reload` or any command), no system-prompt hook, no hidden message. A Go test reads the embedded extension and fails if any of those names appear; a Node test drives the extension against a stub `ExtensionAPI` and records every call.
2. The notice and preamble are the only model-facing marker; notice classes unchanged (a pulled inbox copy keeps the copy notice); `msg.PeerNotice` names Pi.
3. The peer body is a JSON string inside an object whose outer fields the receiver sets (golden and hostile-body tests, as OpenCode).
4. Raw text only from a verified local registered agent (D6).
5. The socket is in a 0700 directory and accepts only the parent pid, when that parent is a Pi host, with the token of this server registration (D3). The local-teammate notice class follows registration (`internal/receiver/receiver.go:96`), so these checks are what stand between an arbitrary launcher and that class. A same-user process can still fake all three (spawn `crosstalk mcp` under a process titled `pi` with the env it chooses); that is inside ADR 0004's same-user model, as for Claude's session files. The extension cannot verify the shim (Node has no peer-credential call); a same-user process that wins the race for the path can feed text to the session. That is inside ADR 0004's same-user model, stated in ADR 0036.
6. **No approval layer.** Pi runs tools without asking (E10), so for Pi the boundary ADR 0004 names ("the receiving harness's permissions") is absent. A teammate's raw text reaches a model that can run any command. This is the cost the operator accepted with D6 (Q1); setup docs state it in the Pi section; M1 measures one model's behaviour, which is evidence, not a boundary.
7. `ValidateAttested` allows `pi` so a paired host's Pi agent can attest; remote Pi senders are still mailboxed (rule 4).
